# v1.10.0 自动回退演练验收

日期：2026-10-18
依据：实施计划 §9 / 规格 §13（健康确认与回退）、§17–§18
被测版本：`1.10.0+49` / MSIX `1.10.0.0`；回退目标 `1.9.0.0`

## 结论

结论：PASS（修复后，且 `1.9.2` 前置修复版验证通过）。已发布版本的第一跳限制由 `1.9.2` 解决，见第 6、7 节。

- 修复前：真实升级 → 健康确认超时 → 回退部署被 Windows 拒绝，`helper-status.json` 报
  `UPDATE_ROLLBACK_DEPLOYMENT_FAILED`，退出码 `9`，系统停在 `1.10.0.0`。
- 修复后：同样流程退出码 `7`，状态 `rolledBack` / `UPDATE_ROLLBACK_SUCCEEDED`，系统回到
  `1.9.0.0`，旧版本被重新拉起，数据库表与行数完整。

## 1. 环境与方法

| 项目 | 值 |
| --- | --- |
| 系统 | Windows 11 x64 build 26200（管理员会话） |
| 起点 | 卸载 `1.10.0.0` 后安装 `1.9.0.0`（`release-artifacts/1.9.0` 的 MSIX） |
| 新包 | `release-artifacts/1.10.0/BestPlanning_1.10.0.0_x64.msix` |
| 回退包 | 同一份 `1.9.0.0` MSIX，放在更新根目录的 `baseline\` 下 |
| 执行者 | `update_helper.exe --apply <request>`（与主程序使用的同一套请求与状态机） |
| 健康确认 | 不写 `health-confirmation.json`，让助手在 60 秒后判定失败并回退 |

请求字段与正式流程一致：`schemaVersion`、`transactionId`、`fromVersion`/`toVersion`、
`.ready` 包路径与大小/SHA-256、身份/发布者/族名/架构、一次性 token、有效期、
`rollbackPackagePath`、`snapshotPath`、`dataDirectory`。快照清单为
`{"files":[]}`，因此回退只验证"包降级 + 重新拉起"，不动用户数据。

## 2. 修复前的失败（真实证据）

```json
{"schemaVersion":1,"transactionId":"rollback-drill-1.10.0",
 "state":"failed","failureCode":"UPDATE_ROLLBACK_DEPLOYMENT_FAILED"}
```

退出码 `9`（回退失败），安装版本仍为 `1.10.0.0`。

根因有两条，必须同时满足才能回退成功：

1. 回退部署用的是 `DeploymentOptions::None`：Windows 不允许用普通 `AddPackageAsync` 把
   `1.10.0.0` 降回 `1.9.0.0`（`ERROR_INSTALL_PACKAGE_DOWNGRADE`）；
2. 健康确认超时时，**刚启动的新版本仍在运行**，即使加上强制降级选项，包仍被占用
   （`ERROR_PACKAGES_IN_USE`）。

## 3. 修复

`windows/update_helper/main.cpp`：

- 回退部署改为
  `DeploymentOptions::ForceUpdateFromAnyVersion | DeploymentOptions::ForceApplicationShutdown`；
- 回退失败时把真实 `HRESULT` 写进 `helper-status.json`（此前只有错误码，无法定位是
  "降级被拒"还是"包被占用"）；
- 普通升级路径仍然使用 `DeploymentOptions::None`，不允许降级（规格 §9.7）。

## 4. 修复后的成功（真实证据）

```json
{"schemaVersion":1,"transactionId":"rollback-drill-forced",
 "state":"rolledBack","failureCode":"UPDATE_ROLLBACK_SUCCEEDED"}
```

- 退出码 `7`（回退成功），耗时 102 秒（部署 + 60 秒健康等待 + 回退）；
- 安装版本回到 `1.9.0.0`；
- 旧版本被重新拉起：进程路径为
  `C:\Program Files\WindowsApps\ShuoZhuang.PersonalPlanner_1.9.0.0_x64__v9555qkaxdyym\personal_planner.exe`；
- 数据库表结构完整，关键行数：`tasks=29`、`schedule_blocks=279`、`calendar_events=27`、
  `settings=11`、`recurrence_rules=16`、`plan_versions=50`；
- 数据库文件哈希在演练前后不同，原因是回退后启动的应用会写 WAL/设置；回退快照清单为空，
  更新过程没有向数据目录写入任何文件。

## 5. 收尾

演练结束后重新安装最终 `1.10.0.0`（含修复后的助手），并重跑安装态更新存储自检：
`ok=true`、`source=local-cache`。安装包内 `update_helper.exe` 的 SHA-256 与构建产物一致
（`9D41DBB3…`）。

## 6. 发布限制（需要产品决策）

自动回退是由**当前已安装版本内置的更新助手**执行的。已经发布的 `1.9.0.0` 包内是修复前的
助手，因此真实用户从 `1.9.0` 应用内升级到 `1.10.0` 时，如果健康确认失败，**仍然不会自动
回退**——本次修复会让"执行升级的版本已含修复"的后续升级（例如 `1.10.0 → 将来版本`）具备
回退能力。

已采用的缓解：先发布 `1.9.2+48`（只含助手修复）。用户先升到 `1.9.2`，后续 `1.9.2 → 1.10.0`
的一跳就由修复后的助手执行；该路径已实测通过，见第 7 节。

可选处理方式（若不走 1.9.2）：

1. 先发布一个只含助手修复的 `1.9.x`（低风险），让用户先升级到它；之后再从它升级到 `1.10.0`
   时回退可用。
2. 在 `1.10.0` 的 Release 说明中明确：从 `1.9.0` 升级的用户若新版无法启动，需要按文档手动
   恢复（卸载 `1.10.0` 后安装 `1.9.0`；用户数据在文档目录，不受影响），并同时提供 Setup
   手动安装路径。
3. 暂不允许 `1.9.0` 通过应用内更新升级到 `1.10.0`（只发布 Setup/MSIX 供手动安装），等
   `1.9.x` 修复版铺开后再开启自动更新。

在上述决策落地前，`1.10.0` 仍属于"发布验收未完成"。

## 7. 前置修复版 `1.9.2` 的一跳验证（2026-10-18）

为确认"先发 `1.9.2`"确实解决第一跳问题，按同一方法真实执行：

1. 卸载当前包，安装 `release-artifacts/1.9.2/BestPlanning_1.9.2.0_x64.msix`；
2. 从 `1.9.2` 包内取出 `update_helper.exe`（SHA-256 `9D41DBB3…`，含回退修复）；
3. 请求升级到 `1.10.0+49`，不写健康确认，等 60 秒超时；
4. 助手执行回退。

结果：

```json
{"schemaVersion":1,"transactionId":"rollback-192-hop",
 "state":"rolledBack","failureCode":"UPDATE_ROLLBACK_SUCCEEDED"}
```

- 退出码 `7`，耗时 97 秒；
- 安装版本回到 `1.9.2.0`，旧版本被重新拉起（进程路径指向 `1.9.2.0` 包）；
- 与第 4 节相同，快照清单为空，更新过程未写入数据目录。

结论：`1.9.2 → 1.10.0` 的自动回退可用；因此先发 `1.9.2` 的方案成立，
`1.9.0/1.9.1` 用户只需先完成一次低风险的小更新。

## 8. 1.9.2 无法通过应用内更新送达（发布后验证）

`v1.9.2` 发布后，在真实安装的 `1.9.1` 上点击「更新已就绪 → 安装」：

- 应用创建事务、保存快照、启动助手并退出，流程正常；
- 助手 2 秒后失败：

```json
{"state":"failed","failureCode":"UPDATE_INSTALL_DEPLOYMENT_FAILED","hresult":"0x80073D02"}
```

`0x80073D02` = `ERROR_PACKAGES_IN_USE`（包正在被使用）。根因：助手默认位于
`Platform.resolvedExecutable` 所在目录，也就是已安装包内（`WindowsApps`）；它从包内启动时
自己占住包文件，Windows 因此拒绝原位升级。

后果：

- `1.9.x`（含 `1.9.2`）无法应用内升级到任何新版本，`1.9.2` 也无法通过应用内更新送达；
- 修复在 `1.10.0`：`WindowsUpdateHelper.launch` 先把助手复制到
  `%TEMP%\\BestPlanningUpdateHelper\\<pid>-<stamp>\\update_helper.exe` 再启动，复制失败按
  启动失败处理，不退回包内路径；
- `1.9.x` 用户必须手动安装 `1.10.0` 一次，此后应用内更新才可用。

单元测试：`test/platform/update/windows_update_helper_test.dart`（复制到包外、重复准备幂等、
源缺失时交给启动前检查）。真实安装态：修复后的 `1.10.0` 通过安装态存储自检。
