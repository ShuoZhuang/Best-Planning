这条序列与事故现场一致：latest 的 ETag 被 state 保存，缓存实体却被 tag 覆盖，

### 1.1 一个必须解释的中间现象（避免伪造红灯）

第一次执行时四条用例都以 `Actual: <null>` 失败，原因是测试夹具自身的问题：
`http.Response` 在缺少 `charset` 时按 latin1 编码响应体，而清单标题含中文，
构造响应即抛异常，仓库把异常折叠成 `UPDATE_NETWORK_HTTP_FAILED`。
该失败与事故无关，因此先修夹具（显式 `content-type: application/json; charset=utf-8`）
再取红灯；上表是修好夹具后的真实失败，`actual` 因此从 `null` 变为 `1.10.2.0`。

`%LOCALAPPDATA%\Packages\<PFN>\LocalCache\BestPlanning\Updates` 里同时存在

  清单的 `sizeBytes`/`sha256` **完全一致**）；
- `baseline\BestPlanning_1.10.2.0_x64.msix`（18,575,088 B，SHA-256 `de8af8f7…3791c9`）；
- v1 `state.json`：`phase=upToDate`、`currentMsixVersion=1.11.0.0`、**`target=null`**；
- v1 `update-manifest.cache.json`（没有请求身份）；
- 日志：`UPDATE_BLOCKED_ROLLBACK_NOT_READY`、`baseline ready version=`（版本为空）。

把该目录整份复制到临时目录（源目录只读），用 1.11.1 的真实实现 + 真实 Ed25519 公钥 +
真实 GitHub 跑回放：


四条事故用例之外，真实数据上还额外确认了三件事：

1. `ready_pending_manifest`：启动时还没有可用的已签名清单，**不隔离**已下载的包；
2. `ready_reused version=1.11.0.0`：第二次真实检查里 19 MB 的包被完整校验后复用，下载次数为 0；
3. `manifest_cache_hit key=latest-stable status=304`：真实 GitHub 返回 304，读的是 latest
   自己的分区缓存，目标仍是 1.11.0。

同一现场还暴露出一条**本计划范围之外**的原生故障：助手状态文件记录

回退数据恢复也失败。它需要单独的安装/回退排查，不能用本次缓存与状态修复冒充已解决。
