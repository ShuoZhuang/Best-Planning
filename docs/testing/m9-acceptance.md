## 2.5 导出与备份：恢复路径（§13 第 3 条）

### 2.5.1 已有的是**真实文件系统**测试，不是替身

- **导出**：`test/platform/file_selector_adapter_write_test.dart` 真的写盘并读回校验，
  而且**刻意不使用 `Directory.systemTemp`**（文件头说明了理由：在这台机器上 Dart 往
  `C:\Users\<user>\AppData\Local\Temp` 建文件返回 errno 5，工作区内正常）。
- **备份**：`test/application/backup_service_test.dart` 用真实临时目录 + 真实 `sqlite3`
  打开候选库做 `PRAGMA integrity_check`，覆盖"包含任务、计划和计时的数据库可完整备份并恢复"。
- **导出服务**另有 7 条：JSON 保格式版本与全部事实、CSV 带 UTF-8 BOM、
  取消选择不建文件、**写入失败不留半成品文件**、只在用户选定路径创建文件、
  被拒时只向上层返回脱敏错误。

### 2.5.2 本轮补的：**"被拒之后换位置真的成功"**

原来只验到"失败时给出了『重新选择保存位置』入口、点了也真的再问一次位置"。
**但"恢复"的意思是换一个能写的位置之后这次导出要成**——那一步没有被验过。
只验到"给了按钮"是不够的：按钮点了、位置也换了，但错误还在、或者文件没写成，
用户仍然拿不到导出。

新增 `test/features/settings/data/export_page_test.dart` 两条：

| 用例 | 钉住什么 |
| --- | --- |
| 被拒之后换一个能写的位置 | 第二次**真的成功**（`已导出 1 条记录`）、失败提示与恢复入口**都消失**、恰好尝试写两次 |
| 连续两次被拒 | 仍然停在**可恢复**状态、**绝不显示"已导出"**、原始异常仍不出现 |

顺带把一处**有意的区别**固定下来（怕以后被人"修"掉）：

> **成功时会显示刚选的目标路径，失败时不显示。** 成功那次显示的是**用户自己刚在选择器里
> 选的位置**，用来确认"写到我指定的地方了"；失败时的脱敏是**结构性**的——
> `ExportWriteException` **不带任何字段**（见 `export_service.dart`），底层适配器捕获到的
> 真实路径**根本传不到界面上**，而不是靠界面记得别打印。

### 2.5.3 修掉一处真实缺陷：备份页会把**完整路径**打到界面上

`backup_page.dart` 的兜底分支原来是 `'操作失败：$error'`——把异常对象**原样**打进界面。

- `BackupService` 自己抛的都是结构化的 `BackupValidationException`（只有 `code`，安全），
  **那条分支没问题**；
- 但**兜底分支**接的是任意异常：文件被占用、磁盘满、路径无权限会以
  `FileSystemException` / `PathAccessException` 冒出来，而 Dart 这些异常的 `toString()`
  **带着完整路径**，例如：

```
FileSystemException: Cannot open file,
  path = 'F:\Documents\personal_planner.sqlite' (OS Error: 拒绝访问。, errno = 5)
```

也就是说"拒绝访问"那一步会把用户的目录结构摆到屏幕上。**导出页早就刻意避免这件事**
（`ExportWriteException` 干脆不带字段），**备份页此前没有**。

**修法**：新增纯函数 `backupFailureMessage`，把绝对路径替换成人话占位、**其余信息保留**
（用户仍要能看出是"拒绝访问"还是"网络名不再可用"，否则他只会反复点）。

**两条正则的分工也写在代码里**：带引号的路径**以引号为界**（最准确）；
不带引号的按**分号/逗号/右括号**断开——因为路径里的空格无法与"路径后的普通文字"区分开
（`'C:\a b\x' failed` 里 ` failed` 算不算路径？），宁可少吞一点，也不要把用户目录后面
那句解释一起删掉。

新增 5 条测试（含真实 `FileSystemException` 文本、UNC 路径、多路径、
盘符根、以及"没有路径的异常原文照常保留"）。

> **为什么这一组用纯函数测而不是驱动整个页面**：`BackupPage` 要的是**具体**的
> `BackupService` + `FileSelectorAdapter` + 真实数据库端口，为了造一个"写入被拒"的场景
> 去搭那一整套替身，测到的多半是替身自己的行为。这段逻辑是纯的——输入异常文本、
> 输出给用户看的那句话——**直接测它更准也更稳**。

## 4.5 收口后按用户实测反馈修的两处

用户在"M9 收口完成"之后报告了两个问题，两处都**在真实数据上定位到根因**并修掉：

### 4.5.1 「我今天完成的算法作业为什么在今日和日历界面不见了」

**根因（用他库里的数据核对出来的）**：

- 算法作业 状态是 completed；
- 它的计划块**只存在于旧版本**（ 3:51 与  1:49 两版），
  而**当前确认版是 21:18 生成的、里面没有它**；
- 机制：勾选完成 → changeStatus 发 DomainChangeKind.taskCompleted → **重排**；
  已完成的任务**不再参与排程**，所以新版本计划里不再有它的块；
- 而视图里"**当天有当前版的块就只用当前版**"这条规则（2026-10-07 为修"已完成待办重复"而加）
  让**今天**正好命中——于是那条已经做完的记录**整天消失**。
  规则 2 的 _historyInForce 只覆盖"整天已经完整过去"的日子，救不了今天。

**修法**：当天在当前版之外，**再补上"已结束任务在过去时间里的块"**。
边界刻意收得很紧（避免重新引入"同一件事显示两次"）：

| 约束 | 为什么 |
| --- | --- |
| 只收**终态**任务（status.isClosed：完成／跳过／取消） | 未完成的任务若被挪走，当前版已经在别处显示它 |
| **当前版给这个任务排过位置 → 一律不补** | 判据必须是**任务**而不是块 id——这是我第一版的错处，schedule_view_source_test 当场抓住（"同一任务、当前版 10:00、旧版 07:30"被判成两件事） |
| 只收**整段已经过去**的块（ndUtc <= now） | 未来的时间不存在"做完了" |
| 补的是"当时在用的那一版"里的**整组块** | 一版计划是对那段时间的**完整声明**，与 _historyInForce 同一口径 |

**为什么不改成"把已完成任务的块留在当前版里"**：那是**重排器**的语义
（已完成不参与排程），改它会动摇"计划只包含还要做的事"这条口径。
这是**视图**该补的历史显示。

新增 3 条测试（正好显示一次 / 当前版仍排着它时不多出一条 / 未来时间上的不补）。

> **我自己在这次修复里犯过一个错并留了记录**：第一版只按**块 id** 去重，
> 于是"已完成的同一任务在当前版 10:00、旧版 07:30"会被**两个都显示**——
> 正是用户此前报过的"已完成待办重复"。既有的两条回归测试立刻把它抓了出来。
> 另外我第一版的**测试夹具**也写错了（注入的"现在"是本地 00:00，
> 而那一块在本地 10:00，即**还在未来**），因此"补过去"这条规则本来就不该生效；
> 是加临时 print 才看清的。

### 4.5.2 「时间范围应该选哪个亮哪个，现在是自定义范围常亮」

**根因**：四个按钮里「自定义范围」写死成 FilledButton.tonal，另外三个是 OutlinedButton
——于是**无论当前范围是什么，都是它亮着**。用户选了「本周」，界面上却是「自定义范围」亮着，
看不出自己当前看的是哪一段。

**修法**：新增 _rangeKindFor，**由当前区间反推它属于哪个预设**（今天／本周／本月／自定义），
按钮样式随它变。

**为什么不记一个 _selectedKind 字段**：区间可以被别处改掉（_setRange 由四个入口共用），
记字段就得在每个入口手动同步，漏一处就会出现"按钮亮着但范围不是它"。
**以区间为唯一真相**，高亮与实际查询的那段不可能漂移。

新增 2 条测试覆盖"被拒之后换位置真的成功"之外的恢复路径（见 §2.5.2）。

但"点不了"不等于"没验"——这条链路有**四环**，我把每一环的证据列清楚：

| 环 | 内容 | 证据 |
| --- | --- | --- |
| ① **系统能识别点的是哪个激活器** | MSIX 清单声明 `ToastNotificationActivation` 的 `ToastActivatorCLSID` **并且**声明对应的 `comServer`（`ExeServer` + `Arguments="----AppNotificationActivationServer"`） | **在生产包里实际读过清单**：交付包 `1.6.2.0` 的 `AppxManifest.xml` 里两个扩展都在，CLSID `7D40D6B0-AC23-4E16-9F0F-21C8AEF635B4` |
| ② **清单里的 GUID 与代码里的一致** | 不一致就永远唤不醒 | `test/platform/windows_notification_activator_config_test.dart`："清单里声明的激活器 CLSID 与代码里的 GUID 一致" |
| ③ **AUMID 用真实的，而不是回退常量** | 用错 AUMID 通知会挂在别的身份下 | 同上文件两条："给了真实 AUMID 就用它，绝不用回退常量"、"没有真实 AUMID 时才回退（只对免安装 EXE 成立）" |
| ④ **payload 交回应用后导航到正确去处** | 点了要真的跳到那条任务，而不是只把窗口带到前台 | `test/app/notification_tap_navigation_test.dart`（用替身端口触发 handler，走**装配完整的外壳**）；payload 的编解码另由 `notification_payload_test.dart` 覆盖 |

**因此第 7 条缺的是"用户对着通知点一下"这个动作本身，不是这条链路的正确性。**

**要补上它**：在装好的应用里新建一个几分钟后提醒的任务，等到通知弹出，**点它**，
确认跳到那条任务而不是只把窗口带到前台。**用户 2026-10-08 已验收通过。**

> 准确的说法是：**四环里三环已有自动化证据、第一环在真实生产包里核对过**，

## 4.7 收口后发现并修掉的一个**测试**缺陷（不改变产物）

在做验收复核时全量套件出现了一次 **`1028 -1`**：

```
test/platform/app_lock_service_test.dart
  连续错误验证采用 1、2、4 秒递增等待，成功后重置
  TimeoutException after 0:00:30.000000: Test timed out after 30 seconds.
```

**根因**：这一条用的是**生产默认**算法 `Pbkdf2.hmacSha256(iterations: 600000)`。
纯 Dart 下 600k 次 PBKDF2-HMAC-SHA256 每次派生要好几秒，而这条用例要
`enable` + `verify` ×4 + `disable` 若干次——**单文件实测 48 秒**，超过
`package:test` 的 30 秒默认超时。

**为什么现在才炸**：套件从 870 条长到 1030 条，机器负载也变了，那点余量没了。
`git status` 确认这个文件**不在本次改动里**（最后一次改它的是 `57a66b7`），
所以它**不是**这次引入的，是**既有的脆弱测试被时长压垮**。

**旁证：其余四个 app-lock 测试早就注入了 `iterations: 1`**，
只有 `app_lock_service_test.dart` 被漏掉了——是同一写法的遗漏，不是设计选择。

**修法**（**只改测试，不改产品**）：

| 用例 | 原来 | 现在 |
| --- | --- | --- |
| 凭据不存明文、元数据正确 | 真跑 600000 次 | 注入 `iterations: 17`，断言元数据跟着算法走 |
| 延迟递增序列 | 真跑 600000 次 | 注入 `iterations: 1`（它只关心延迟） |
| —— | 无 | **新增**一条毫秒级常量断言 `defaultIterations == 600000` |

**为什么新增那条常量断言**：原用例里 `expect(stored, contains('"iterations":600000'))`
其实**并没有**在守"生产默认是 600000"——它守的是"存储里的迭代数等于所给算法的迭代数"。
现在把这两件事分开：元数据断言留在原处，**默认值由常量断言守**。
后者更直接（改小默认值立刻红），而且不用花 18 秒。

**实测效果**：

| 项 | 修前 | 修后 |
| --- | --- | --- |
| 该文件单独跑 | **48 秒**（且超时失败） | **毫秒级** |
| 全量套件 | 1:21，**偶发 `-1`** | **0:40**，连跑 **3 次全绿** |
| 测试条数 | 1030 | **1030**（+1 条常量断言） |

**产物未受影响**（**这一点核对过，不是推断**）：`data\app.so` 的 SHA-256 与当前构建
**逐字节一致**（`BBBFE383…`），因为本次改动**只在 `test/` 下**。
因此**不改 MSIX 版本、不重打包**——`version-policy.md` 的第四段是给"同一批次重打包"用的，
而这次连打包都没发生。

> **教训值得写下来**：一条"跑得比较慢但能过"的测试是**定时炸弹**——它的通过与否取决于
> 套件规模与机器负载，而不是代码正确性。修它的正确做法**不是**把超时调大，
> 而是让用例**只依赖它真正要验的东西**。
