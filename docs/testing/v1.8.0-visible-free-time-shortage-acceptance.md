## 1. 故障形状与根因证据

### 1.1 已复现的缺陷（RED → GREEN）

**缺陷 A：未来周期实例作为普通任务泄漏进本次规划**

- 复现夹具：`test/application/visible_free_time_shortage_regression_test.dart`
  → `**未来周期实例不得泄漏成普通任务**（真实故障形状）`
- 触发条件：`RecurringTaskService.ensureCycles` 按**滚动七天**生成实例。本地周四 12:00
  起算的七天窗口跨越两个本地周，于是库里同时存在本周与下周两个实例。
- 修复前实测（RED）：

  ```text
  Expected: not contains 'recurring:anonymous-1:2026-10-12'
    Actual: [ 'ordinary-a',
              'recurring:anonymous-1:2026-10-12',
              'recurring:anonymous-1:2026-10-05' ]
  ```

  即：下周实例确实作为一件"普通任务"进入了 `problem.tasks`。
- 泄漏路径（与计划 §1.3 的推断一致，但**触发条件不同**）：
  `RepositoryScheduleProblemSource.load()` 只把 `_recurringInputs()` 返回的**本周**实例
  task id 从普通输入里删除；`ensureCycles` 为滚动七天补出来的下周实例因此留在普通映射里。
- **与计划推断的一处修正**：计划写"它的 `availableFromUtc` 落在规划窗口终点或之后"。
  实测该实例的 `availableFromUtc` 为 `null`（`recurring_task_service._taskFor` 只设
  `dueAtUtc = period.endUtc`），因此它**不是**被窗口准入挡住的，而是被"只按本周实例换输入"
  这条更窄的过滤漏掉的。这一区别决定了修法：必须按 **task id 批量剥离全部实例**，
  而不是靠窗口终点判断。

**缺陷 B：截止之后的日子分走按日预算（零安排的根因）**

- 复现夹具：同文件 → `**截止之后的日子不得分走按日预算**（零安排根因的回归门槛）`
- 触发条件：`even`（均匀分布）周期目标，210 分钟，截止＝本周末（周日本地 24:00），
  而规划窗口有**七天**。
- 修复前实测（由阶段证据取得，逐层核对）：

  ```text
  DSHDEBUG evenPlan recurring:…:2026-10-05 target=210
    add={10-8:30, 10-9:30, 10-10:30, 10-11:30, 10-12:30, 10-13:30, 10-14:30}
    cap={10-8:570, 10-9:840, 10-10:840, 10-11:840, 10-12:840, 10-13:840, 10-14:840}
  BLOCKS=… 120 分钟（10-09 两段 40、10-10 一段 40、10-11 一段 40）
  UNSCHEDULED=recurring:…:2026-10-05:90:
    dailyLimitReached(30/0)+lockedPlanOccupied(null/null)
  calendarGapMinutes=5610
  ```

  逐层结论：
  - `calendarGapMinutes = 5610`，**日历空闲充足**；
  - 候选数 `11726`，**候选非零**；
  - 均分器把 210 分钟摊成**每天 30 分钟**，其中 `10-12`／`10-13`／`10-14` 三天
    **在任务截止之后**——候选生成按 `dueAtUtc` 过滤，这三天永远产不出候选；
  - 真正能排的四天每天只拿到 30 分钟，`10-8` 当天的可用时段只剩约 9 分钟，
    于是引擎只排进 120 分钟，剩下 90 分钟被报成 `dailyLimitReached`
    ——**而那一天其实还有 300 分钟以上的空闲**。
- **这就是"可见空闲却报容量不足"的零安排根因**：不是容量不够，是预算被
  不可用的日期吃掉。
- 修复后实测（GREEN）：同一夹具
  `selectedMinutes=210`、`shortageMinutes=0`、`unscheduled` 为空、`conflicts` 为空。
