## 1.12 Task 13：识别无法利用的短空档

**判据**（`lib/scheduling/unusable_gap.dart`）：一段空档比"当时还没完成的任务里**最小**的
那个片段"还短，因此谁也放不进去（规范 §2.6 的"20 多分钟的空白"）。

- 用 **`min` 而不是 `max`**：只要**有任意一件**任务放得下，这段空档就不是浪费的。
- 用 **`minChunkMinutes` 而不是剩余时长**：还剩 180 分钟但最小片段 30 分钟的任务完全可以
  放进一个 30 分钟的空档；按剩余时长判断会把它误判成坏空档。
- 只统计**没排完的**任务：已排满的任务不需要空档，把它算进来会抬高最小片段。
- **两类明确的排除**（全局不变量第 6 条"休息不是浪费"）：保护时间覆盖的空档、
  比 `breakMinutes` 短的空档。
- **只看块之间的缝，不看一天的头尾**：起床前与睡前的空白不是"排程失败"，
  把它算成浪费会让排程器为了填满而把任务排到深夜。
- 重叠或相接的块**先合并**：两块首尾相接时中间的缝是 0 分钟，不合并会造出一堆零长度空档。

**进评分**：`ScoringFactor.unusableGap` ＋ `SchedulingWeights.maximumUnusableGapPenalty`
（-500）。与既有的 `fragmentation` 是**两件不同的事**——后者惩罚"这一块比最大片段短多少"
（**块的形状**），前者惩罚"这次放置在周围留下多长的、谁也放不进去的缝"（**空档的可用性**）。
一个 45 分钟的块完全正常，而它前后各留 20 分钟的缝才是问题。有一条用例专门钉住
"改变坏空档深度不会影响 fragmentation 的取值"。

**判据用"最深的一段"而不是"总分钟"**：一次放置通常只影响紧邻的两段缝，
"总分钟"会把一天里早已存在的坏空档也算进来，于是评分反映的是"当前计划有多碎"而不是
"这一个候选有多碎"——前者是常量，无法用来比较候选。

**踩到的坑（值得记）**：`重叠的块先合并` 那条用例我按"块数"直觉断言 `hasLength(1)`，
但合并后唯一的空档是 90 分钟，对 30 分钟的最小片段**完全可用**，因此它**不该**出现在
坏空档里。探针打出 `PROBE gap=10:30..12:00 min=90 smallest=30` 之后才看清
**代码是对的、夹具错了**。现在用两个最小片段（30 与 120）分别断言同一段空档的两种结论
——这才是"游标推到了 10:30"的真正证据，因为游标若停在 10:00，空档会变成 120 分钟
（两种阈值下都可用）。

**仍未完成的部分**：`unusableGapPenaltyPermille` 现在**由引擎计算并填入**
（`ScheduleEngine._unusableGapPermille`：候选两侧、短于"最小待办片段"的缝的浪费分钟数，
折算成千分比），`ScoringFactor.unusableGap` 也接进了 `CandidateScorer`。
但**生产权重 `SchedulingWeights.v1.maximumUnusableGapPenalty` 是 0，因此这一项暂不生效**。

这不是"还没接上"，而是一次**实测后的撤回**，原委已写进 `SchedulingWeights` 的注释：
打开它（-500）之后 `schedule_engine_test.dart` 的两条既有用例变红——
`golden week keeps breaks between chunks and reports the shortfall`（缺口 30 → 90）
与 `任意两个任务块之间保留休息，不区分任务类型`（间隔 10 → 60）；
调到 -120 仍然红，调到 0 就全绿。

**根因**：候选评分**没有时域视野**。这一项只看候选紧邻的两段缝，于是引擎会把块往后推以
"离开"一段短缝，却在更远处制造出更大的缺口——单看一处它是改善了，整体上休息反而被吃掉。
规范 §11.4 要求"不制造坏空档"是**在一个局部修复方案上**比较的（第 6 条排在被移动块数与
总位移之后），而方案级比较正是 `LocalRepairPlan.compare`——它尚未接进引擎（见 §1.11）。

**因此这次交付的边界是**：判据（`unusable_gap.dart`）、引擎侧的千分比计算、
评分因子与权重字段**全部实现并有用例**；权重保持 0 直到方案级比较接上。
为了让"按千分比折算"那段代码不因权重为 0 而失去覆盖，新增了
`SchedulingWeights.testing({required int maximumUnusableGapPenalty})`——
用例用它验证折算与夹紧，并**另有一条用例断言 `v1` 里那一项就是 0**，
免得日后有人在没修好根因的情况下把它改大。



## 1.11 Task 12：最小改动局部修复的**选择顺序**（部分完成）

**已实现**：`lib/scheduling/local_repair.dart` 的 `LocalRepairPlan.compare`，按规范 §11.4
的字典序比较两份候选：

1. 移动的其他块数量最少；
2. 所有被移动块的总位移分钟最少；
3. 目标块距离 `notBeforeUtc` 最近；
4. 全部相同时按块签名——**保证顺序确定**，否则同一次输入会产生两份不同提案，而"应用哪一份"
   取决于内存里的哈希顺序。

修复前的状态：引擎只有"单块贪心 ＋ 单一总分"，一个 900 分的移动惩罚项把"少动"和"少走"揉在
一起。于是**三次小改动**（每次都略微提高总分）整体上可能比**一次大改动**动得更多——规范第 3、
4 条要的是整体量，不是单块增量。

**两条被测试当场抓到的实现缺陷**（都记在代码注释里）：
1. 第一版把参照位置塞进结果对象（`withReference`），于是同一个对象在不同调用点算出的位移不同
   ——测试直接给出 `Expected: <30> Actual: <0>`。现在参照一律走**显式参数**：
   参照是"跟谁比"，属于比较的输入，不属于结果本身。
2. 测试夹具的 `block(id, hour: 9, minutes: 30)` 把 `minutes` 同时当成"时长"和"从整点起的
   偏移"，于是想要 09:00–09:30 却造出 09:30–10:00，位移算成 0。现在开始偏移与时长分成两个
   参数（`offsetMinutes` 与 `minutes`）。

**仍未完成的部分（如实记录）**：比较器**还没有接进引擎**。规范 §11.4 的字典序要在
"先在当天做向后级联、当天放不下才考虑后续日期"的**可行域**上比较，而那个级联搜索尚未实现；
`ScheduleProblem` 也还没有携带"确认计划的块位置"作为参照（需要新增一个字段，并由
`RepositoryScheduleProblemSource` 从 `confirmedBlocks` 填充）。
本轮交付的是**比较规则本身**及其确定性保证，不是完整的局部修复。
这一条会与 Task 13（坏空档）一起在 Task 15 的全链路回归里复核。


## 1.10 Task 11：延后改为 proposal 绑定的类型化请求

**修复的缺陷**（规范 §2.5）：今日页把分钟换算成 `RequestedMove.atInstant`，排程输入再把该块
以 `locked: true` 钉在**精确目标时刻**。目标点一旦被固定日程、保护时间或另一个锁定块占用，
方案直接失败——它不会去找目标之后最近的合法时段。而且一次失败还可能留下待处理内存意图。

**三处改动**：

1. **类型化请求**（`pending_moves.dart`）：新增 `DeferUnit { minutes, hours, days }`、
   `DeferPlanBlockRequest`、`PlanAdjustmentRequest` 与纯函数 `deferNotBeforeUtc()`。
   `days` 走**本地日历日 ＋ 保留本地钟点**，不是加 24 小时——柏林 03-28 本地 03:00
   延后 1 天得到 03-29 **01:00Z**（UTC 只前进 23 小时）。这条有用例逐值钉住，
   并且**同时断言"加 24 小时得到的不是它"**，免得日后有人"顺手简化"成 `add(Duration(days: 1))`。
2. **下界语义**（`repository_schedule_problem_source.dart`）：被延后的块**不再进**精确锁定那条
   路径；改为把该任务的 `availableFromUtc` 抬到 `notBeforeUtc`，块留在可移动集合里由引擎在
   下界之后重新放置。合并用 `_laterOf` 取较晚的那个——**不是覆盖**，否则一次延后会把用户原本
   设的可用起点抹掉。同一任务多块被延后时取**最晚**的下界。
3. **生命周期**（`pending_moves.dart` ＋ `router.dart`）：请求由 `beginAdjustment` 建立、
   生成路径在 `finally` 里 `endAdjustment()` 销毁。"生成失败"这条路径也走 `finally`，
   因此**不存在"一次失败留下内存意图、下一次普通生成又把它应用一遍"**。
   路由用例现在断言的是"请求已销毁"而不再是"意图还留着"。

**对话框**（`_DeferDialog`）：分钟／小时／天三档分段选择，快捷值与自定义范围逐值对齐
规范 §11.1 的表格，确认区显示"原时间 → 最早目标时间"。

**踩到的坑**：第一版把 `TextEditingController` 建在 `showDialog` 外面、在 future 完成时
dispose——实测 future 完成时退场动画还没跑完、`TextField` 仍在树上，退场帧直接撞上
`A TextEditingController was used after being disposed`。改成对话框自己持有控制器
（`StatefulWidget`），在**它的** `dispose` 里释放。

**仍未完成的部分**：`notBeforeUtc` 目前只通过"抬高任务可用起点"生效，**当天向后级联、
少动优先、当天放不下才考虑后续日期**这些选择策略属于 Task 12（规范 §11.4 的字典序），
还没有实现。Task 11 交付的是"精确点 → 下界"这一步以及请求的生命周期。

"保护时间入口"在这里补齐（此前建完之后没有任何地方能再找到它）。

**顺带修掉一个会当场崩的真实缺陷**：学期下拉的选项原本按"每门课一条"生成，于是
**同一学期有两门课就会让同一个 value 出现两次**，而 `DropdownButton` 的断言要求 value
恰好命中一项——直接抛
`There should be exactly one item with [DropdownButton]'s value: term-autumn`。
这正是"同名不同 id 各占一行"那条用例发现的（一门课一行时看不出来）。
修法是在列表推导里按 id 去重（`seenTerms.add(id)`）。

**与 Task 9 的分工**：聚合查询的 SQL 行为由 `course_series_repository_test.dart` 用真库守着；
本任务的用例只钉**页面**——列什么、怎么显示、点进去带什么 id、空状态说什么。


## 1.8 Task 9：课程管理的查询与事务服务

**只读端口**：`CourseSeriesRepository`（`listCourses` / `findCourse` / `currentTermId`），
实现是 `DriftCourseSeriesRepository`。**聚合的键是 `logicalCourseId`**，不是标题。
三个过滤条件缺一不可：`logicalCourseId IS NOT NULL`（手工日程不属于课程管理）、
`exceptionOfId IS NULL`（例外行不是系列锚点）、`recurrenceRuleId IS NOT NULL`。

**学期从 `timetable_import_batches.term_id` 反查**：`calendar_events` 上没有 `term_id`
列，学期是批次上的属性。这不是绕路——同批次的课天然同属一个学期。
`currentTermId()` 落在学期之间时返回**最近一个已开始的学期**，而不是 `null`：
假期里打开管理页应当看到刚过去那一学期的课，而不是一个空页面。

**单双周还原**：`intervalWeeks == 2` 时用"起点相对学期第一周周一的周偏移奇偶"判定单双。
学期未知时**保守地报 `every`**——把单周误报成"每周"只是少一层筛选，
误报成"双周"会让用户以为这周没课。

**写入端口**：新增 `CourseWriteGateway.deleteSeriesWithExceptions(Set<String>)`，
由 `DriftCalendarRepository` 实现。**为什么不复用 `CalendarEventDeletion.deleteEvent`**：
那个只删锚点行，而"删除整个课程"要删多个片段**连同它们的例外行**且必须在一个事务里。
顺序是**先删例外再删锚点**——`exception_of_id` 是指向 `calendar_events(id)` 的外键，
反过来锚点一删、例外变孤儿，`PRAGMA foreign_keys = ON` 会让整次删除失败。

**`CourseManagementService`** 的六条命令（规范 §10.2）与三条范围语义：

| 命令 | 落到什么 |
| --- | --- |
| `editOccurrence` | 一条例外，**不动规则本身** |
| `editFollowing` | 系列拆分（截断旧规则 + 新系列） |
| `editWholeCourse` | **全部**片段锚点逐个 `replaceSeries` |
| `pauseFrom` | 按周截断到"停用日所在周的上一周周日"，保留历史 |
| `previewDelete` | 片段数 ＋ **具体次数**（用户要看懂的是"还剩多少次课"） |
| `deleteCourse` | 全部锚点一次交给网关 |

**两条刻意的设计决定**：
1. **`CourseEditScope` 与 `EventEditScope` 分开**。后者的 `entireSeries` 是"一个锚点与它的
   重复规则"，而这里需要的是"当前学期内该 `logicalCourseId` 的全部片段"。两者在单片段课程上
   恰好等价，在单双周（两条规则）上完全不同——复用会让"改整个课程"只改到单周那一半。
2. **`pauseFrom` 用截断实现，而不是加一个"暂停"状态位**：`calendar_events` 与
   `recurrence_rules` 都没有那样的列（那需要一次 schema 变更），而"从某天起不再出现"用截断
   表达既准确又与展开器天然一致。已经结束的片段**不再截一次**——那会凭空记一条重排原因。


## 1.7 Task 8：自定义保护时间的编辑、显示与排程

**数据表示**：`CalendarEventKind.protected`（Task 7 加的列），**不另建平行时间模型**
（规范 §9.1）。展开、例外、冲突检测、"仅本次／此次及以后／整个系列"全部复用固定日程那一套
——`CalendarService.save()` 只多了一个 `EventDraft.kind`。

**排程映射**（`RepositoryScheduleProblemSource`）：同一次 `occurrencesBetween` 按 `kind`
拆成**互为补集的两份**，`fixed` 进 `fixedIntervals`、`protected` 进 `protectedIntervals`。
写成补集而不是两次独立过滤，是为了让"某条记录两边都进"在类型上就不可能发生
（规范 §8 审查问题 4）。课后缓冲只作用于 `fixed` 那一份。

**统计排除**：`AnalyticsDao._fixedEvents` 只收 `kind == fixed` 的 occurrence。
保护时间仍出现在**保护时间**那一节（那个口径由 `_protectedWindows()` 与规则来源给出）。

**Task 8b（补做的欠账）**：`AnalyticsDao` 新增 `_protectedInstances(filter)`，
读同一批 occurrence 里 `kind == protected` 的那一份，产出
`AnalyticsProtectedInstance`（**精确 UTC 区间 ＋ 用户标题**），
经 `AnalyticsDataset.protectedInstances` 进入 `AnalyticsService` 的
`_protectedInstances` 展开器，于是**保护时间总量、休息保护情况、休息总结、与保护时间重叠的
计划分钟**四处口径同时把用户自建的保护时间算进去。

**为什么新增一个模型而不是复用 `AnalyticsProtectedWindow`**：后者表达的是
"每天 12:00–13:00 都是保护时间"（本地分钟窗 + 三态 `isWeekend`）。把一条只覆盖某一天的
一次性保护投影成"每天 14:00–15:00"，统计里会凭空多出六天的保护时间——
数字错了，而且错的方向恰好是"看起来休息得更多"，最不容易被发现。
`AnalyticsProtectedInstance` 直接带 UTC 区间，与数据库的存储口径一致。

**踩到的坑**：给四个内部辅助函数加参数时我用了脚本化的 `.Replace`，
它把 `_protectedInstances` 的**形参名**也一起改成了 `protectedInstances`，
导致四处 `referenced_before_declaration`。更麻烦的是 `_restSummary` 等函数里已有
局部变量叫 `instances`，与形参**同名遮蔽**。最终把形参统一改名为 `customInstances`、
局部变量保留 `instances`，并用 `analyze` 逐轮确认。**又一次证明：这种跨函数改名不该用
脚本正则在多行文本上做。**


**显示**：`RepositoryScheduleViewSource` 把 protected occurrence 映射为
`ScheduleItemKind.protectedTime` + `ScheduleSpecialCategory.protectedTime` 配色，
**与规则来源的保护时间同色**；`areaId` 置空（它没有归属），`isCompleted` 恒 false
（它不是待办）。

**顺带修掉的一个真实缺口**：`fixedEventId()` 原本只认 `ScheduleItemKind.fixed`，
于是用户自己建的保护时间在日视图里**既不能改也不能删**——建完之后没有任何入口
（规范 §9.3 明确要求支持同样的三个范围）。现在它同时接受 `protectedTime`，
而**规则来源**的保护时间因为 id 不是 `fixed:<eventId>`（而是 `protected:<kind>`）
仍正确地拿不到入口。既有那条"保护时间不提供删除入口"的用例因此**没改一字**仍然通过，
新加了一条反向用例钉住"自定义保护时间可以改与删"。

**新建入口**：`/calendar/protected/new`（Task 5 已把选择器的第四张卡指到这里）。
编辑器用了 Task 5 建立的 `PlannerEditorScaffold`——**这是该骨架的第一个真实使用者**，
也是我在 Task 5／6 记下的"迁移未完成"的第一块补齐。

**仍未完成的部分**：`ProtectedTimeListPage`（计划 Task 8 的 Files 里列了它）**没有实现**。
理由是规范 §9 没有要求独立列表页，而"管理保护时间"的入口按 Task 10 的安排与"管理课程"
一起放在日历页工具栏里；现在建一条保护时间后可以在**日视图**里改与删（已可用），
周视图里的时间轴也照常显示。这一条记在这里，Task 10 会一并处理。


## 1.6 Task 7：schema v9 与日历事项种类

**唯一结构变化**：`calendar_events.kind TEXT NOT NULL DEFAULT 'fixed'`（规范 §14）。
`plannerSchemaVersion` 与 `AppDatabase.schemaVersion` 同步为 9。
生成物一律由项目既有命令产出，**没有手改一个字**：

```powershell
& G:\best-planing\.tooling\fx.ps1 pub run build_runner build --delete-conflicting-outputs
& G:\best-planing\.tooling\fx.ps1 pub run drift_dev schema dump lib/data/database/app_database.dart drift_schemas/
& G:\best-planing\.tooling\fx.ps1 pub run drift_dev schema generate drift_schemas/ test/drift/app_database/generated
```

**踩到的两个真实坑（都被既有测试当场抓到）**

1. **`migrator.addColumn` 不会带默认值**。它生成的是 `ALTER TABLE ... ADD COLUMN kind TEXT`
   ——**不带 DEFAULT**，于是 v8 里已有的每一行 `kind` 都是 `NULL`，而生成的读取代码写的是
   `... as String`（非空），一读就抛 `Null check operator used on a null value`。
   第一版用了 `alterTable(TableMigration(...))` 想一次到位，实测**仍然留 NULL**
   （`columnTransformer` 没有作用到 `addColumn` 那条替身路径上）。
   最终实现是**两步**：`addColumn` + 显式
   `UPDATE calendar_events SET kind = 'fixed' WHERE kind IS NULL`。
   为什么不让这一列可为空：规范 §9.1 要求它非空，而"允许 NULL"会让每个读取点都要判空。
2. **`drift_dev schema generate` 会重写 `generated/schema.dart`**，把 `switch` 里的
   旧版本分支**全部删掉**（只剩新版本），既有用例立刻报
   `Unknown schema version 1. Known are 9`。恢复办法是从 git 还原该文件，
   再手工补上 `import 'schema_v9.dart'`、`case 9:` 与 `versions` 里的 `9`——
   **其余部分是生成物，只有这三行需要补**（drift 没有提供增量开关）。

**三处既有断言必须随版本更新**（都是"版本号写死"的地方，不是行为变化）：
- `schema_migration_test`：`versions.last` / `plannerSchemaVersion` 8 → 9；
- 该文件 7 处 `migrateAndValidate(db, N)`（N=4/5/6/7）：数据完整性核对必须跑到**当前**版本，
  否则它校验的是一张没有 `kind` 的表；
- 标题为"v6 迁移后旧表结构完全未变（无新增列）"的用例改成
  "v6 迁移到 v9 后旧表只多了 v9 的 `calendar_events.kind`"：先比对 v6 列前缀
  （一个不少、顺序不变），再要求多出来的部分**恰好**是 `['kind']`。
- `pre_migration_backup_test`：`plannerSchemaVersion` 8 → 9。

**`kind` 的默认方向**（`CalendarEventKind.fromStorage`）：未知值回落到 `fixed`，
**绝不回落到 `protected`**。认不出的值当成固定日程最多是"这段时间被占着"，仍然可见可编辑；
当成保护时间会让一段时段突然变成硬禁区，而用户没有任何线索。


## 1.5 Task 6：日期与时间的类型化选择器

**新增组件**：`lib/design/planner_date_time_fields.dart`
- `PlannerDateField` → `showDatePicker(builder: plannerPickerBuilder)`，暴露 `DateTime`；
- `PlannerTimeField` → `showTimePicker(builder: plannerPickerBuilder)`，暴露 `TimeOfDay`；
- `LocalDateRangeController`（`ChangeNotifier`）承担规范 §8.2 的**时长联动**三条规则。

**规范 §8.1 的"不显示格式字符串"如何成立**：字段是只读按钮，值是类型化的。
`EventEditorForm` 里的 `_parseLocal` / `_parseDate` 与 `DayViewPage` 里的
`_parseLocalDateTime` / `_formatLocal` **全部删掉**——生产路径里再没有任何日期或时间的
字符串解析。测试也从 `enterText(..., '2026-10-03')` 改成真的走选择器：那种写法本身就是
这条缺陷的镜子，留着它就等于没修。

**时长联动三条规则**（`LocalDateRangeController`，各有用例）：
1. 改开始时间 ⇒ 保持原时长并联动结束时间；
2. 用户手动改过结束时间后 ⇒ 只在"新的结束不晚于开始"时才自动修正；
3. 结束不晚于开始时 ⇒ `endsNotAfterStart` 如实报出，由界面**明确询问**
   （日视图对话框给"若跨到次日，请把结束日期改到次日"），**不做静默猜测**。

### 过程中撞到的四个真实问题（都被测试抓到）

1. **`SelectableText` 在手势竞技场里赢过外层 `InkWell`** —— "点日期文字"打不开选择器。
2. **`SelectionArea` 会抢焦点**：它装的 `SelectableRegion` 自带 `FocusNode`，
   于是 Tab 过来后焦点落在选区上，**Enter 什么都不做**。`TextButton` 外层套它同样如此。
   → 最终放弃"字段内文本可选中复制"。**规范 §8.1 的"仍可复制"这条没有完全达成**，
   这是刻意取舍：§9 把键盘操作列为硬要求，可复制是便利。已写进组件注释。
3. **`MaterialApp` 不配 `locale` 时选择器按钮是英文**（`Cancel` / `OK`）。
   只配 `localizationsDelegates` 不够——不钉 `locale` 就跟随系统语言，测试环境是 `en`。
   线上由 `PlannerApp` 钉死，测试必须照抄那一行。
4. **表单变高后保存按钮落到视口外**：`calendar_event_route_test` 用的默认 800×600
   测试视口不真实（真实窗口 1280×720）。改成 1280×720 并 `ensureVisible`，
   与 `task_editor_route_test` 测同一件事时用的尺寸一致。

**顺带修掉的一个布局缺陷**：字段的标签原在按钮外、提示在按钮下，三段合起来比 `Wrap`
单元格高 2 像素（`RenderFlex overflowed by 2.0 pixels`）。改成标签与值都放进按钮里的
`Column(mainAxisSize: min)`——**结构性**消除，而不是调一个刚好够用的魔法数字。

**尚未完成的部分（诚实记录）**：`PlannerEditorScaffold`（Task 5 新增）**还没有**被
`EventEditorForm` 与日视图对话框改挂上去。规范 §7.2 的"所有编辑器共用同一个骨架"因此
仍未达成；迁移放在 Task 8（保护时间编辑器）里与新建页面一起做。


## 1.4 Task 5：新建入口与侧栏归属

**侧栏归属表的唯一位置**：`lib/app/planner_rail_index.dart` 的
`plannerRailIndexForLocation(String)`。它返回 `int?`——**可空是关键**，因为规范 §7.1

**保护时间不再去设置页**：`_openNewItemEntry` 对 `protectedTime` 现在去

## 1.3 Task 4：托盘左键的纯消息表

**消息表的唯一位置**：`windows/runner/tray_icon_message_policy.h` 的
`ActionForTrayMessage(UINT)`（纯函数，不依赖 Flutter、引擎或 `TrayIcon`）。
`TrayIcon::HandleMessage` 只做一件事——把 `lParam` 交给它，再按结果分派。

| 消息 | 动作 | 说明 |
| --- | --- | --- |
| `WM_LBUTTONUP` | `kOpen` | **本次修复的缺失项**（§2.3） |
| `WM_LBUTTONDBLCLK` | `kOpen` | 本来就处理；双击因此是两次独立的"打开" |
| `NIN_SELECT` | `kOpen` | v4 协议的鼠标激活 |
| `NIN_KEYSELECT` | `kOpen` | v4 协议的键盘激活 |
| `WM_RBUTTONUP` / `WM_CONTEXTMENU` | `kMenu` | 右键**只**开菜单，绝不打开窗口 |
| 其他 | `kNone` | 不吞掉普通窗口消息 |

**"双击不会变成打开又隐藏"靠什么成立**：表里没有任何"切换"概念，两次点击都是 `kOpen`；
幂等性落在 `TrayIcon::RestoreMainWindow()`——它先 `IsIconic` 再 `SW_RESTORE`、
不可见才 `SW_SHOW`、最后无条件请求前台。第二个 `kOpen` 面对的是已经可见的窗口，
因此它只把它带到前台，不会隐藏。

**前台被拒不算失败**（§6.2）：`SetForegroundWindow` 返回 `FALSE` 时调用

恢复与显示在前两行就已经完成，所以即使抢焦点被拒，窗口也已经回来了。

## 1.2 Task 3：通知的唯一对账入口

**唯一的对账入口**是 `NotificationService.reconcile()`（`lib/application/notification_service.dart`）。
`syncNextSevenDays()` 保留为它的**弃用别名**，只为不改动既有用例的调用点；新代码不得再用它。

调用点（规范 §5.2 要求"启动、唤醒、计划应用、任务状态变化和设置保存都调用同一个幂等
reconcile"）：

| 触发 | 位置 |
| --- | --- |
| 启动 | `main.dart` 的 `unawaited(resyncNotifications())` |
| 计划被应用 | `main.dart` → `PlanApplicationService.onPlanChanged` |
| 任务/日历排程输入变化 | `main.dart` → `onScheduleInputChange` |
| 设置保存 | `main.dart → PlannerApp → router → PlanningRulesPage.reconcileNotifications` |

**总开关关闭时为什么不读计划**：`reconcile` 在 `enabled == false` 时**提前返回**，只按 id 前缀
取消；`_desiredNotifications()` 根本不会被调用。这条有专门的计数器用例
（`总开关关闭时**不读计划**`）——`PlanRepository.current` 的调用次数必须是 0。

**取消规则**（这是本任务真正的设计决定）：

```
类别关闭                    → 取消（用户明确要求）
类别开启、但已不在期望集合   → 取消（过期事实：计划已改，这条提醒已无意义）
类别开启、且在期望集合       → 保留
```

**为什么不能只用"它不在期望集合里"来判断**：写第一版时正是这么写的，测试当场抓到——
"关掉截止提醒"把任务开始、固定日程、冲突三类**一起取消了**。原因是那三类在
`_desiredNotifications` 里没有来源（测试只装配了任务块），期望集合里本来就没有它们，
于是被当成"过期事实"。把"用户关了通知"与"计划里暂时没有它"混成一个判据，代价是
**关一类会顺手清掉别的类**。现在按类别逐个判断，并用 `NotificationKind` 枚举而不是字符串
前缀承载这个判断（`_categoryOf` / `_categoryEnabled`）。

**顺带修掉的一个真实缺陷**：`RecurringNotificationService` 在 1.7 就写好了、也有测试，
但**生产里从来没有被构造过**——周期目标提醒在真实运行中永远不会出现。现在由
`main.dart` 构造，并经 `RepositoryRecurringCycleReader`（只读适配器，新增）从周期仓储取候选；
它与另外四类走同一次 `reconcile`，总开关关闭时**一次都不评估**。

**页面侧**（§5.3）：保存是"落库 → 对账"两步，**对账没返回就不显示"设置已保存"**；
对账失败显示"设置已保存，但系统通知清理失败，可重试"加「重新同步」按钮，后者**只重跑对账、
不重复落库**。未装配对账入口时保存照常成功，但不会假装同步过。


## 1.1 Task 2：UTC → 本地时区的唯一边界

**边界位置**：`lib/features/calendar/week_view/schedule_timeline_plan.dart` 的
`weeklyTimelinePlan()`。它一次算出每列的本地日期与每条的本地分钟区间
（`PlannedDayEntry.startMinute/endMinute`），`WeekViewPage._timeline()` 只调用它一次，
`TimelineDayColumn` **完全不再接受 `toLocal`**——它拿到的已经是分钟。

修复前的三处换算：窗口用一次 `toLocal`；`TimelineDayColumn` 算位置时 `_local(item.range.startUtc)`；
卡片格式化时 `_hhmm(_local(_clockAt(startMinute)))`——把本地分钟包成 `DateTime.utc` 再换一次。
Asia/Shanghai 下第三次换算多减 8 小时（柏林 4 小时），因此**位置是对的而文字是错的**。
新测试因此同时钉位置与文字：只钉位置抓不住这条缺陷（修复前位置本来就对）。

**顺带修掉的两个真实缺陷**（同一根因，规范 §4.1 最后一条要求）：

1. **列边界不再是"UTC 加一天"**。旧代码用 `weekStart.add(Duration(days: n))` 当列边界，
   那是加**经过时长**；Berlin 的 2026-03-29 只有 23 小时，列边界会漂到 01:00。
   现在每列的本地日期按本地日历推（周起点的本地日期 ± n 天），日边界用
   `localMidnightUtc()` 反解出那一刻的 UTC。
2. **`localWallClockToUtc` 的墙上时间必须构造成 `DateTime.utc`**。第一版写成裸
   `DateTime(...)`，它带主机时区，`toUtc()` 会先减掉主机偏移——本机（Asia/Shanghai）
   实测"本地午夜"变成 `08:00Z`，整列区间全错、卡片落到列底。这个坑只在真实时区下暴露，
   恒等转换的测试永远看不到它。

跨午夜因此是**先按本地日裁剪再换算**：23:30–00:30 在第一列拿到 `23:30–1440`、
第二列拿到 `0–30`，不再两列都显示"23:30 到列底"。
