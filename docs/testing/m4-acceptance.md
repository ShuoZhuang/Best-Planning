## 1.1 「跳过本次」按用户 2026-10-07 的定义实现（规格：`2026-10-07-m4-skip-current-block.md`）

用户给的六条要求与**逐条落地位置**：

| 用户要求 | 落地 | 证据 |
| --- | --- | --- |
| 1 当前块从今日时间线移除 | 被跳过的块从 `lockedBlocks` 与 `existingBlocks` **两处都排除** | `pending_skips_test.dart` 断言两处都不含它 |
| 1（补充）但**不把时段锁成禁区** | **没有**把它加进 `fixedIntervals`／`protectedIntervals` | 同名文件里专门一条："跳过**不会**把旧时段锁成禁区" |
| 2 任务仍是未完成待办、剩余时长不变 | 任务照旧留在 `tasks` 里；剩余时长**不在装配层重算**（已专注部分由既有专注重算扣减） | 断言 `status == open`、`remainingMinutes` 不变、`requiredMinutes` 等于原剩余 |
| 3 重找截止前空档 | 交给既有引擎（它已按 `dueAtUtc`／`availableFromUtc`／优先级排程） | 装配层只负责"把块拿掉"，不自己挑时间 |
| 4 默认预览；信任自动调整时直接应用 | 复用既有的 `PlanGenerationFlow`（"默认预览、信任才自动应用"只此一处实现） | 路由按 `autoAdjustStore.enabled && planApplication != null` 分流 |
| 5 **不能无条件塞到明天** | 跳过**不碰** `availableFromUtc`／`dueAtUtc` | 专门一条断言：这两个字段在跳过前后不变 |
| 6 排不下报"待安排／有逾期风险"并说明缺多少 | 复用既有 `proposal.unscheduled` 与预览的「未安排」分组（M4 P5 刚补齐） | `plan_preview_test.dart` 的「未安排」用例 |

**三个动作保持分开**（用户明确要求）：

| 动作 | 实现状态 |
| --- | --- |
| **跳过本次** | **已实现**。只记块 id（`pending_skips.dart`），不碰截止时间、不碰任务状态 |
| **延后到明天** | **未实现**（改 `availableFromUtc`，是另一个动作） |
| **取消任务** | **未实现**（改 `TaskStatus.cancelled`，是另一个动作） |

**粒度是"块"而不是"任务"**：同一任务今天有两段时，跳过一段不影响另一段（有专门用例）。

**一处最容易被忽略、也最容易出错的转换**：页面交回的是**视图条目**（id 形如 `block:<块 id>`），
而排程输入要认的是**计划块 id**。路由必须翻译。若直接塞视图 id，
`pendingSkips.forBlock('<真实块 id>')` 永远匹配不上——**症状是"点了跳过没反应"，而且不报错**。
`today_route_test.dart` 有一条专门挡这个：断言记进 `pendingSkips` 的是 `b1` 而不是 `block:b1`。

## 2. 本轮实际改了什么

### 2.1 `ScheduleViewItem` 增加 `taskId`（P1）

今日页要能"开始专注／完成／查看详情"，就必须从一条安排找到它**属于哪个任务**。
此前任务 id 只藏在 `id` 的 `block:` 前缀之后（那是**计划块 id**，不是任务 id），
页面要用它得拆字符串或反过来查计划——两种做法都会让视图层重新认识领域结构。

现在数据源在构造任务块时顺带带上 `taskId`（那里本来就有 `block.taskId`），
固定日程与保护时间为 `null`——**这正是今日页判断"该不该显示任务动作"的依据**。

**顺带修掉一个埋着的坑**：今日页 `build` 里会把条目**按当天裁剪区间后复制一份**
（`ScheduleViewItem(...)` 重建）。这份副本此前只带了 `isCompleted` 等字段；
本轮加的 `taskId` 如果忘了带，症状会是"按钮不见了"而不是报错——最难查的那种。
已在复制处补上，并留了注释。

### 2.2 今日页执行动作（P2）

| 卡片状态 | 动作 |
| --- | --- |
| **当前**安排（`start <= now < end`）且是未完成任务 | 卡片上直接给 **「开始专注」「完成」** 两个按钮 |
| 其它条目 | 一个 **`PopupMenuButton`** 菜单：查看详情／延后／请求调整／锁定 |
| 固定日程、保护时间 | **不给**任务动作（没有所属任务，点了无处落地） |
| 端口为 `null` | **不渲染**对应入口（渲染一个点了没反应的按钮比不显示更糟） |

**为什么主动作必须做成按钮**：§8 的退出条件是"开始专注不超过两次点击"（进页面 1 次 +
点按钮 1 次）。收进菜单就变成 3 次，直接违反退出条件。

「当前」用**半开区间** `[start, end)` 判定：否则相邻两条会同时是"当前"，
一屏出现两组「开始专注」。

### 2.3 重排提示可关闭（P4）

新增 `_ReplanNotice`（顶部 banner）+ `dismissedProposalId` / `replanProposalId` / `onDismissReplan`
三个可选参数。**关闭只隐藏提示，不取消方案**——页面本身不做任何"丢弃方案"的动作。

**刻意用 `proposalId` 而不是 `bool` 记录"已关闭"**：用 `bool` 会让"关掉一次之后就再也不提醒"，
而 §8 要求"重新生成的新方案仍会提醒"。测试把这两条都钉住了。

### 2.4 路由装配（P3）

`/today` 接上三条回调（与 `TaskDetailPage` 同一套做法：**页面不认识路由**）：

- `onStartFocus` → `context.go('/focus/<taskId>')`（仅当装配了 `focusService`）；
- `onComplete` → `taskService.changeStatus(taskId, completed)`；
- `onOpenDetail` → `context.go('/tasks/<taskId>')`。

## 4. 明确未完成的部分（不勾选）

### 4.1 「延后到明天」与「取消任务」未实现（用户定义里**分开的另外两个动作**）

用户 2026-10-07 明确要求三个动作分开。本轮只实现了「跳过本次」：

- **「延后到明天」**：用户**明确要求**明天再做 → 设置新的 `availableFromUtc` 为明天。
  **未做**。它与"跳过"的区别是真实且可观察的：跳过**不碰** `availableFromUtc`
  （因此新时间可能是今天稍后），而延后到明天**必须**改它。混成一个动作就会让
  "跳过"变成"无条件顺延到明天"，正是用户第 5 条明确禁止的。
- **「取消任务」**：整个任务不再需要完成 → `TaskStatus.cancelled`，退出排程。**未做**。
  它与"跳过"的区别同样实在：跳过**必须保持** `open` 并继续参与重排（有用例断言）。

这两项**不是"没做完"的残留，而是用户定义里各自独立的动作**，需要各自的界面入口与测试。
「跳过本次」本身已完整。

### 4.2 §8「保护时间变化」这一类目前不会有内容（**如实说明**）

§8 要求预览按"新增、移动、拆分、未安排、保护时间变化"五类分组。五类的**分组与标签都已实现**，
但"保护时间变化"这一类**当前不会出现内容**：`PlanDiffer` 比较的是两侧的 `PlannedBlock`，
而保护时间是**按规则算出来的区间**、不在 `PlannedBlock` 里，因此差异器看不到它的变化。

要让这一类真的有内容，需要把"规则变化导致的保护时间差异"也算进 `PlanDiffer`——
那是对排程差异器的扩展，超出"调整预览的信息呈现"这一范围。**分组留着，内容暂时为空**，
并在界面上一如既往地显示「无」。**不假装它有数据。**
