## 2. 本轮实际改了什么

### 2.1 几何抽成纯函数（`timeline_layout.dart`）

`TimelineMetrics`（可见窗口、每分钟像素、最小块高）、`timelineWindowFor`（有效范围）、
`layoutTimelineDay`（并排）、`minuteRangeInDay`（跨午夜兜底）。**不依赖 Flutter**，
因此可以穷举边界——这是本里程碑最容易出错、又最难靠肉眼看出来的一块。

### 2.2 并排用**团（clique）**而不是贪心

**这是本节最关键的决定。** §9 要求"同时发生的项目并排显示，不允许相互覆盖后只剩一个可见"。
直觉做法是"与已放下的块比较、找第一个空位"，但它对**交叉区间**会算错：

```
A 09:00–11:00
B 09:30–10:00
C 10:30–11:30     ← A 与 C 也重叠
```

三者**两两重叠**，必须三列。贪心很容易只给出两列，于是 A 与 C 各占一半宽却仍然左右重叠
——正是 §9 禁止的那种画面。团的做法给出确定答案：`{A,B,C}` 一团、三列各 1/3。

**每个团独立算列数**：拥挤的上午不该把整个下午也压窄（有用例钉住）。

### 2.3 视图切换与持久化

`WeekViewPreferenceService`（设置键 `calendar.weekViewMode.v1`，**读失败一律回默认**
`compact`）。切换用 `ChoiceChip` 而不是 `SegmentedButton`——M2 发现后者每个分段会在语义树里
产生两个同名节点（屏幕阅读器念两遍），任务页筛选栏也因此换成了 `ChoiceChip`。

**默认必须是紧凑**：§9 明确"不能强迫用户接受时间轴密度"，老用户升级后界面不该突然变样。

### 2.4 复用而不是新造

- 颜色：`scheduleCategoryCardStyle`（与紧凑模式、今日页、单日页同一个派生器）；
- 数据：同一个 `ScheduleViewSource`；
- 切换的"默认预览／信任才应用"那类判断：本里程碑没有新增。

**刻意不在时间轴里支持拖动**：§9 只要求时间轴能看见时长与节奏；"拖到某一天"在按小时排列的
视图里语义不同（拖到几点？）。保留紧凑模式作为唯一的拖动入口，不发明一套新的拖放语义。

## 3. 过程中真发现并修掉的一个缺陷：150% 缩放下卡片溢出

`week_timeline_test.dart` 的 150% 用例**先红后绿**，红了两次：

1. 第一版高度阈值写成固定 `34`，150% 下误判成"放得下"，`Column` 溢出 8 像素；
2. 改成随文本缩放走的 `30 × scale` 之后**仍然溢出**——一查才发现：一张最短的卡片只有
   39 像素高，而 150% 下单是**标题一行**就要约 24 像素，两行加内边距需要约 47，
   **无论怎么排版都放不下**。

**修法**（取舍写明）：整页其余部分（列头、图例、切换、详情页）**照常跟随系统缩放**，
只有这几十像素高的卡片把文本缩放**封顶在 1.3**；放不下时**让位给标题**，
而起止时间在 Tooltip 里始终完整，不丢信息。

> 一个"越放大越用不了"的时间轴不算可操作——这正是 §9 把缩放写进退出条件的原因。

## 4. 明确未完成 / 刻意不做

### 4.1 时间轴不支持拖动移动

见 §2.4。紧凑模式仍是唯一的拖动入口。若以后要在时间轴里拖动，需要先定清
"拖到几点算落点"（现在是"拖到哪一天"），属于**新的交互语义**，不在本里程碑偷偷加。

### 4.2 「时间轴默认滚动到有效范围」只做到"范围只显示有效部分"

§9 说"时间轴默认显示用户有安排的有效时间范围，允许滚动查看全天"。
**已达成的**：可见窗口（刻度与布局的取值域）就是有效范围，而不是整天 0:00–24:00；
对于典型的一天，这直接让内容铺满视口，不需要滚动。
**没有做的**：也**没有**把整天的 0:00–24:00 作为可滚动内容（当前内容高度等于窗口高度）。
若某天有 23:00 之后的安排，窗口会覆盖到它；但用户**不能**手动滚到"这一天完全没安排的时段"。

**为什么这样取舍**：§9 的**用户结果**是"看见空档、冲突、任务时长和全天节奏"。
"空档"在有效范围内已经可见（块与块之间的空白），而把整天空转时段也画出来会让时间轴变长、
且对"今天还剩多少时间"没有帮助。**若你要求真的能滚到整天，我再加上**——那是一处小改动，
但我不会把它算成"已做"。
