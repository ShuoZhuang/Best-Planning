## 2. 本轮实际改了什么

### 2.1 修掉一个真缺陷：统计页的领域占比用了**第二套颜色**

**缺陷形态**（`lib/features/analytics/chart_view.dart` 的 `chartPalette` + `chartColorAt(index)`）：

- 统计页的「领域占比」按**下标**取色——第 1 个领域拿第 1 个色、第 2 个拿第 2 个；
- 今日页、日历页、领域管理页用的是 `resolveAreaColorArgb(storedColor, sortOrder)`
  ——用户选过的颜色，没选过就按排序位从调色板取默认色。

后果：**同一个领域在两个页面显示成不同颜色**，用户没法把两张图对上。
而 §11 原文写着"图表不得重新分配颜色"。

**修法**：让统计页也用**同一个解析器**，为此把颜色从数据层一路带上来：

1. `AnalyticsAreaFact` 增加 `storedColorArgb` / `sortOrder`（**不在这里解析成最终色**：
   解析规则属于表示层，"哪些颜色可用"是 `area_palette.dart` 的事，领域模型不该知道调色板）；
2. `AnalyticsDao` 在构造领域事实时填入 `row.color` / `row.sortOrder`；
3. `DomainTimeMetric` 同样带上这两个字段，由 `_domainDistribution` 从领域事实查得；
4. `analytics_page.dart` 的「领域占比」改用 `Color(resolveAreaColorArgb(...))`。

**为什么这个缺陷难以发现**：两张图不会同时出现在屏幕上，而"颜色"本身没有真值——
只要每一页自己**内部一致**，看起来都正常。这正是 §11 要把它写成退出条件的原因。

### 2.2 自定义范围换算抽成纯函数并补边界测试

原来 `_selectCustom` 里的换算**内联在 State 方法里**，因此"末日含当天"这条口径
**一个测试都没有**。现在抽成顶层的 `analyticsRangeForSelectedDays`，10 条测试覆盖：
末日含当天（半开区间）、单日、跨月、跨年、12/31、闰年 2/29、反向区间、零长度、UTC。

> **过程中我自己踩了一次坑并记在注释里**：第一版把函数插在了 State 的方法之间，
> 于是它成了**类的方法**，测试里根本找不到（`Method not found`）。
> 只跑集成路径是发现不了这个的。

## 3. 图表对比度与明细替代（本轮补齐，规格：`2026-10-07-m7-chart-contrast.md`）

### 3.1 先量，再定口径

现有饼图把**白色标签直接画在切片上**。按 WCAG 相对亮度实测，同一张饼的八种颜色里
**只有三种**能到 4.5:1；「领域占比」用的**领域调色板**更糟：

| 颜色 | 白字对比度 |
| --- | --- |
| `#f06f7a` | 2.89:1 |
| `#2f86ff` | 3.51:1 |
| `#53c7a5` | 2.08:1 |
| `#f2b35d` | **1.85:1** |

**换成深色也不成立**：逐色试过，取 `dark #142131` 与 `black` 中的较优者，
`#3567D4`（4.04）与 `#8B5CC7`（4.45）**仍不达标**。

**结论：切片上的文字没有一种固定前景色能满足全部切片色——这不是调色能修的，必须改呈现方式。**

### 3.2 定下来的口径

| 元素 | 判据 |
| --- | --- |
| **文字**（标签、数值、轴名） | ≥ **4.5:1**（WCAG 正文），对它所处的背景 |
| **图形本身**（饼图区、柱、折线） | ≥ **3:1**（WCAG 非文本／图形对象）。它不是文字，套 4.5 会得出"所有浅色都不能用"的荒谬结论 |
| **不只靠颜色区分** | 每个数据点必须有一处**文字**给出名称与数值 |

### 3.3 改法

- **饼图切片上不再写字**（`PieChartSectionData.title: ''`）；
- 图表下方统一加一行**图例**：色块 + 「名称 数值」，文字落在正常表面上；
- 横向条形图**不重复**加图例——它本来就逐行写了名称与数值。

### 3.4 一个必须记下来的反直觉发现

**`meetsGuideline(textContrastGuideline)` 对着旧代码也是通过的。**

原因：fl_chart 把切片标题画在 `CustomPaint` 的**画布**上，而 `textContrastGuideline`
遍历的是**语义树上的文字控件**——它看不见画布里的字。因此：

> **"整页通过对比度检查"不等于"图里的字看得清"。**

这正是这条退出条件必须单独做的原因，也是我在验收记录里把它标为"未完成"而不是
"看起来还行"的原因。为了让"为什么必须改"有可复算的依据，测试里留了一条**直接量白字与
领域色比值**的用例（它在旧实现上会红，今天不会——因为它量的是那个已被移除的画法）。

### 3.5 测试清单（本轮新增 14 条）

`test/features/analytics/chart_contrast_test.dart`：四档材质 × 饼图／条形图共 8 条
`meetsGuideline` 检查、图例给出名称与数值、图形对表面 ≥ 3:1（逐色断言）、
白字不达标的历史依据、全零显示空状态、单点不崩且可读、值为 0 的项不占图例。

## 4. 本轮的工作方式（一处建了规格，两处没有）

M7 的审计结论是：**§11 的五条里三条已实现且已有测试**，缺口是三个很具体的点。
处理方式**按缺口性质分开**，我不把它们说成一样：

| 缺口 | 有没有先建规格 | 为什么 |
| --- | --- | --- |
| 领域占比的第二套颜色 | **没有** | 缺陷形态明确（按下标取色 → 改用共享解析器），改法只有一条，且 §11 原文就是判据 |
| 自定义范围的边界测试 | **没有** | 只是把已有换算抽出来补测试，不改行为、不需要新口径 |
| **图表对比度与明细替代** | **有**（`2026-10-07-m7-chart-contrast.md`） | **必须先定口径**：图是面积／柱／线，WCAG 的正文 4.5:1 不直接适用。不定口径就只能随手加一条断言糊过去 |

**这一步的教训**：后两条的差别不是"工作量大小"，而是**判据是否已经存在**。
判据已在（§11 原文）就直接修；判据不存在（图形的对比度阈值）就先写规格定下来。
