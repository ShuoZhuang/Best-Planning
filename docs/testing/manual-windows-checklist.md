# Windows 手工验收清单

Task 20 的交付物之一。本清单用于在 Windows 桌面上逐项确认自动化测试覆盖不到的行为，
并作为需求规格第 18 节验收清单的证据来源。

**使用方式**：每项填写「通过 / 不通过 / 不适用」并在证据栏留下截图、日志路径或构建号。
任何「不通过」项不得标记首版完成。不要在没有实际执行的情况下预填结果。

**当前状态（2026-10-03 复核更新）**：本清单**尚未执行**——下面每一格的结果仍然是空的，
**不要在没有实际执行的情况下预填结果**。但清单本身的两处前提已经变化，本轮据代码与提交逐条更正：

1. **原先把大量条目标为「当前不可达」（无路由、无写入方、控制器被禁用），这些标注现在几乎全部
   已经过期**——那些能力在后续提交里陆续接通（重复日程、单次／系列编辑与删除、拖动、特殊日、
   专注、统计、四类通知、通知点击、应用锁启动拦截）。**逐条更正并附上提交号与用例名**，否则执行
   清单的人会照着旧标注去跳过已经可测的条目。
2. **原先唯一仍然不可达的 `9.5 永久清除个人数据` 也已接通**（`3a85f19`）：那一块界面与
   `DataErasureService` 本来就在、也各有测试，缺的只是组合根不构造它、`router.dart` 不传
   `erasure`。现把"删库"改为**延迟到下次启动执行**（与恢复那条路径同一个套路），入口随之
   接通。**验证它时必须走"执行 → 重启 → 确认数据已空"三步**，因为删除本来就安排在下次启动——
   只点一次按钮就看界面，会得出错误的结论。因此本清单**已没有"不可达"的条目**了。

**需求规格 §18 的勾选状态另见 `docs/testing/spec-18-acceptance.md`**（逐项给出自动化证据）。
**对应关系**：§18 的 **18 项已由自动化证据勾选**，只剩「普通任务可在一分钟内完成快速录入」
一项需要本清单 `2.1`／`2.2` 的人工计时（"一分钟内"是操作耗时主张，自动化证明不了）；另外
`9.5`（永久清除）与 `10.1`（生成计划途中杀进程）虽然对应项已按自动化证据勾选，仍是**值得人工
走一遍**的场景。因此**手工验收仍是首版发布的前置条件**。

## D. 通知验证：含**冷启动**那一支（对应第 9 节）

```powershell
$db = Join-Path ([Environment]::GetFolderPath('MyDocuments')) 'personal_planner.sqlite'
Get-Content "$db.diagnostics.log" -Tail 12
```

**冷启动的步骤（顺序不能反）**：

1. 启动应用 —— 它会把"截止提醒"排在**现在 +1 分钟**（前提：有一个截止时间在未来 24 小时内的任务）；
2. **在这一分钟内把应用关掉**（上一条命令的第二个）；
3. 等通知**在应用没运行时**弹出来；
4. **点它**，然后再读一次诊断日志。

**三种痕迹的含义**（前两种才算通过）：

| 日志行 | 含义 |
| --- | --- |
| `通知被点击（应用在运行）：route=…` | 点击交给了**运行中的实例** |
| `冷启动由通知拉起：route=…` | 应用没运行，Windows 拉起它**并交付了 payload** |
| `冷启动未拿到通知 payload（…）` | **每次普通启动都会出现**，只有在"点了通知但没跳转、且只有这一行"时才算问题 |

## E. 数据与崩溃检查

```powershell
$db = Join-Path ([Environment]::GetFolderPath('MyDocuments')) 'personal_planner.sqlite'

# 任务与截止时间（due_at_utc 是微秒时间戳；需要本机有 sqlite3）

# 崩溃：**务必看这两个字段再谈归因**（本会话两次栽在没看它们上）
Get-WinEvent -LogName Application -MaxEvents 200 |
  Where-Object { $_.Id -eq 1000 -and $_.Message -like '*personal_planner*' } |
  ForEach-Object {
    $lines = $_.Message -split "`r?`n"
    $path  = ($lines | Where-Object { $_ -like 'Faulting 应用程序路径*' })
    $pkg   = ($lines | Where-Object { $_ -like 'Faulting 包全名*' })
    "$($_.TimeCreated) | $path | $pkg"

```

**判定规则**：`Faulting 包全名` 为空的崩溃来自**未打包副本**（`可运行程序\*`、Debug、release 快照），
**不是**安装版。

## 附二：「一分钟内快速录入」怎么做人工计时（§18 唯一未勾选项）

**这一项为什么不能自动化**：它断言的不是"功能存在"，而是**操作耗时**——"普通任务可在**一分钟内**
完成快速录入"。自动化测试能证明录入链路可用，**证明不了人花多久**。因此必须人来掐表，并把
**秒数**记进清单，否则这一项永远只能空着。

### 步骤（约 3 分钟，含准备）

1. **准备计时器**（二选一）：
   ```powershell
   # 方式 A：让 PowerShell 掐表（回车开始、再回车结束）
   $sw = [System.Diagnostics.Stopwatch]::StartNew()
   Read-Host '按回车开始计时'
   $sw.Restart()
   Read-Host '录完任务后按回车'
   $sw.Stop(); "耗时：{0:N1} 秒" -f $sw.Elapsed.TotalSeconds
   ```
   方式 B：手机秒表。
2. **把应用切到任务页并停在那里**（不要先打开别的页面 —— 这一项测的是"从想录入到录完"，
   不含寻找入口的时间，而 §18 的原意是"快速录入"这条通道本身）。
3. 掐表开始时，**连续完成 3 次普通任务录入**（每次都从"新建任务"开始，填标题 + 预计时长，
   保存）。**三次都要计时**，不是只测一次——单次容易因为手生/顺手而失真。
4. **记录三个秒数**（例如 18 / 12 / 11 秒）与**是否含鼠标操作**（键盘/鼠标混用照实写）。
5. **判定**：**三次都在 60 秒内**即通过；只要有一次超过就写"不通过"并给出秒数——
   **不要因为"通常是快的"就写通过**，这一项的验收口径就是那个 60 秒。
6. 把结果写进清单 `2.1`／`2.2` 的结果格（写秒数，不要只写"通过"），并在此处留一行汇总。

### 建议的通过判据（写下来才不会事后各说各话）

| 项 | 判据 |
| --- | --- |
| 单次录入耗时 | ≤ 60 秒 |
| 次数 | 连续 3 次，取**最慢**的一次与 60 秒比较（不是平均值） |
| 起点 | 已在任务页，从点"新建任务"开始 |
| 终点 | 任务出现在列表里 |

> **为什么取最慢而不是平均**：需求原文说的是"**可在一分钟内完成**"，即最坏情况也要能满足；
> 平均值会把一次 90 秒的糟糕体验藏起来。
