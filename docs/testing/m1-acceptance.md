## B. 关键边界：为什么"已完成"优先于"已安排"

`test/features/tasks/task_list_filter_test.dart` :: `4. 已完成任务即使有未来计划块，仍归入已完成`
钉住了这条：完成即完成，**即使还残留未来时间块**也不回到"已安排"。这条边界在你的真实数据里
**正好会发生**（见 D 节），因此它不是纸面规则。

## E. 关于"不单独抬版本或发布安装包"的口径纠正

**事实**：工作树里当前是 `1.6.1+36` / MSIX `1.6.1.0`，并且已经构建、安装、启动验证过。

**它是怎么来的**：上一版路线图把每个批次当作**独立发布版本**，于是按当时的 `版本号规则.md`
为"统计修复"抬了 Patch 段。

**新路线图下的口径**：M1～M9 **同属 `1.6` 发布线**，里程碑不是版本号，也不单独发布
（§3、§4、§14）。因此：

- `1.6.1+36` / `1.6.1.0` **只当 `1.6` 发布线的中间开发候选**，供本机验证使用；
- **它不是 M1 的对外交付**，M1 不产生 GitHub Release、不写成"正式发布"；
- 第二段 `1.6` **不再变动**；最终版本的第三段、MSIX Revision 与构建号 `+N` **只在 M9 收口时**
  按届时基线与"MSIX 必须严格高于已安装版本"确定；
- 中间里程碑期间只生成内部验证构建（§3、§14）。

这条纠正同时写进了 `docs/release/version-policy.md`，免得下一个人按旧口径再抬一次版本。
