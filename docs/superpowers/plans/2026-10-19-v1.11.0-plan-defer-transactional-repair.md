# 1.11.0「延后本次」事务化完整修复实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 1.11.0 内把「延后本次」改造成可恢复、可验证、可解释、可并发保护、可精确撤销的块级调整工作流；任何失败都保持当前计划与执行事实不变。

**Architecture:** 延后不再依赖 `PendingMoveDrafts` 中的单个瞬时字段，而是创建带基线版本、目标块快照、修订号和过期时间的持久调整操作。生成、预览、确认、取消、重试和撤销全部以 `adjustmentId + revision` 为身份，通过统一硬约束判定器和同一 SQLite 事务完成状态转换；界面只消费服务结果，不保存第二份业务状态。

**Tech Stack:** Flutter/Dart、Drift/SQLite schema 11、GoRouter、现有 `ScheduleEngine` / `PlanValidator` / `PlanApplicationService`、`TimeZoneDatabase`、Windows 桌面端测试与发布门禁。

**Spec:** `docs/superpowers/specs/2026-10-12-stable-block-provenance-design.md` 与 `docs/superpowers/specs/2026-10-17-algorithm-20-complete-planning-design.md`。本计划对二者中“调整只活到生成结束”“`applyProposal` 不需要调整事务”“固定 5 分钟粒度”等已被生产证据推翻的部分作 1.11.0 限定修订；其他冻结决定继续有效。

**Status:** `READY FOR IMPLEMENTATION`。这份文件定义修复和验收，不代表代码已经完成。任何完成比例必须以文末 Definition of Done 和实际验收记录计算。

**How to use:** 评审时先看“冻结的产品语义”“已确认缺陷台账”和“事务不变量”，再按 Task 1–14 执行。Task 1–4 先建立测试、模型、持久化和时间语义；Task 5–14 接入生产链、事务、撤销与发布门禁。文件中的提交命令只 stage 本任务列出的路径，执行者仍须先检查当前工作树。

## Global Constraints

- 本计划的全部生产改动、迁移、界面、测试和发布证据都属于 **1.11.0**；不得拆到 1.11.1、1.12.0 或用“后续优化”规避验收。
- 语义版本保持 `1.11.0`；构建号在正式发布时统一决定。实施期间不得擅自把 `pubspec.yaml` 改成别的语义版本。
- 算法语义最终统一为 `DeterministicScheduleEngine.algorithmVersion == '20'`；只能在最后门禁任务中改常量，旧算法提案必须被拒绝。
- 数据库版本保持 schema 11。本工作树正在实施的执行事实、周期片段和持久预览也使用 schema 11；本计划必须合并进同一份尚未发布的 v10→v11 迁移，不得再造 schema 12。
- 当前工作树存在其他 1.11.0 未提交改动。实施者只能增量修改本计划列出的重叠位置，不得重置、覆盖、清理或格式化无关文件。
- 所有区间均为半开区间 `[startUtc, endUtc)`；存储与比较使用 UTC，日历日、星期、按天延后和 DST 解析使用 `timeZoneId`。
- “延后本次”只改变一个尚未开始、尚未完成、未锁定的正式计划块；不得修改任务截止时间、任务级 `availableFromUtc`、同任务其他块的语义或完成状态。
- 用户明确调整的优先级低于已执行/正在执行事实、固定日程、保护时间、睡眠、锁定块和任务硬约束，高于软偏好、精力匹配、均衡与坏空档评分。
- 精力、期望时段、学习偏好和坏空档都是软目标，不能把存在硬合法位置的调整判成无解。
- 调整未兑现、输入过期、搜索未决、结构异常、并发冲突或校验失败时一律零写入；`allowPartial` 不得绕过明确调整。
- 日志、错误码和自动测试输出不得记录任务标题、备注、真实 UUID、数据库路径或完整时间表。用户界面可显示用户自己的标题；诊断日志只记录稳定脱敏摘要。
- 不新增联网权限、云端服务或第三方求解依赖。
- 每个任务遵循红灯→最小实现→绿灯→相关回归→提交；任何 `NOT RUN`、人工推测或旧安装包都不能记为通过。

- [ ] **Step 3: 固定允许转换**


## 冻结的产品语义

### 入口资格

“延后本次”只对同时满足以下条件的 `ScheduleItemKind.task` 显示为可点击：

1. 条目来自当前确认计划，具有真实 `planVersionId` 与持久 `blockId`；
2. 任务存在且未完成、未删除、未归档；
3. 块的 `startUtc > nowUtc`，即尚未开始；
4. 块不是锁定块，也没有执行开始证据；
5. 块仍属于当前确认版本，且没有处于另一项调整的 `applying` 状态。

固定日程、保护时间、课程、历史块、正在进行块、已结束块、已完成任务、锁定块和仅存在于待确认预排中的块不显示该入口。若上下文菜单需要保持布局一致，可以显示禁用项，但必须给出“已开始／已完成／已锁定／计划已变化”等具体原因，不能点击后才静默失败。

### 延后量与目标下界

- 单位保留“分钟／小时／天”。
- 分钟快捷值：5、10、15、30、60；自定义范围 1–240。
- 小时快捷值：1、2、3、6、12、24、48、72；自定义范围 1–72。
- 天快捷值：1、2、3、7；自定义范围 1–7。
- 超过 7 个本地日属于修改任务计划边界，不再伪装成一次块级延后；界面提供“前往任务设置”，不接受 8–365 天的假成功输入。
- 分钟和小时先计算绝对下界，再按**目标所在本地日的实际粒度**向上对齐。
- “天”表示本地日历日：在相同时区中把原本地日期加 N 天，保持原钟面时间，再按 DST 规则解析并对齐目标日粒度；不是固定加 `N × 24h`。
- DST 不存在时间向前推进到第一个有效本地时刻；重复时间选择较早的 UTC 实例，但最终不得早于原时刻和用户要求下界。该策略必须由 `TimeZoneDatabase` 的一个公开函数实现并测试。
- 对话框显示“原时间 → 最早可开始时间”，并明确“实际位置可能更晚”；它不能承诺精确占用该时刻。

### 规划范围

默认七日生成窗口不因普通生成改变。延后操作使用专属有效窗口：

```text
adjustmentWindowEnd = max(defaultWindowEnd,
                          endOfLocalDay(notBeforeLocalDate + 1 day))
```

由于 UI 最多允许延后 7 个本地日，该窗口最多覆盖默认窗口之外一个用于完整放置的本地日。装配层必须加载该窗口内的固定日程、保护时间、睡眠、逐日规则、课程过渡、确认块与周期限制；不得只扩大时间戳却遗漏未来占用事实。

### 局部修复与全局回退

1. 先以当前确认计划为基线，在目标块原本地日执行受约束的向后级联；
2. 当天不存在合法方案时，搜索调整有效窗口中的后续本地日；
3. 局部方案必须通过与普通候选完全相同的硬约束判定；
4. 局部成功时不得再调用全局搜索；
5. 局部失败才允许进入算法 20 的有界全局搜索，并继续携带同一 `adjustmentId` 与兑现要求；
6. 全局搜索失败、预算耗尽、未兑现目标或增加相对基线的新缺口时，保留旧计划并返回结构化原因。

### 预览、确认与取消

- 调整请求在生成结束后不能清除；它至少活到应用成功、明确取消、过期或被判 stale。
- 预览必须持久化，应用重启后仍可恢复；进程崩溃不能把一次待确认调整变成普通生成。
- “重新生成”复用原 `adjustmentId`，递增 revision 并重新读取当前目标块；不得丢失延后单位、数量或原始意图。
- 输入、基线计划、目标块、算法版本或调整 revision 变化时，当前预览立即标记 stale，禁用确认并提供“按原意重新生成”。
- 返回、关闭预览或点击取消均调用显式取消接口；应用被系统强制退出时保留 active 状态，下一次启动提示恢复或放弃。
- 确认按钮在请求期间禁用；所有路由回调都是 `Future` 并被 `await`，异常转换成结构化状态，不允许未处理 Future。

### 应用、幂等与撤销

- 应用以 `adjustmentId + adjustmentRevision + previewRevision + basePlanVersionId + inputHash + algorithmVersion` 为完整令牌。
- 同一令牌重复确认返回同一已应用计划，不创建第二个版本；不同令牌竞争同一基线时只有一个 CAS 成功。
- 调整状态、预览状态、旧计划 superseded、新计划、块、执行关联、周期片段关联和审计日志在同一 SQLite 事务中提交。
- 通知重排、托盘刷新等数据库外副作用在提交后执行，通过 outbox/重试状态记录；失败不能把已提交结果伪装成“应用失败”。
- 应用成功后提供精确撤销。撤销恢复计划块、执行实例当前版本关联、`execution_block_links` 和未开始的 `execution_fragments`；不删除完成证据，不倒退已开始事实。

## 产品级验收矩阵

| 场景 | 必须结果 | 禁止结果 |
| --- | --- | --- |
| 未来普通任务延后 10 分钟 | 新位置不早于原开始 +10 分钟；预览后确认生效 | 点击无响应、原位“成功”、直接改库无预览 |
| 延后 2 小时 | 下界按绝对时长算并吸附目标日粒度 | 把 2 小时当 2 个网格或固定 5 分钟 |
| 延后 1 天跨 DST | 本地日期 +1、保持钟面意图、按冻结 DST 策略解析 | 无条件 +24h 导致钟面漂移 |
| 延后到不同粒度日 | 使用目标日本地 policy | 沿用源日粒度 |
| 目标不存在/改变 | 结构化 targetMissing/targetChanged，零写入 | 普通生成兜底、移动别的块冒充成功 |
| 历史/开始/完成/锁定/非任务 | 无可点击入口，服务再次拒绝 | 先允许再静默失败 |
| 高精力时段不足但其他时段合法 | 可安排到其他硬合法时段并解释软偏好折中 | 因软偏好报“可用时间不足” |
| 当天有位置 | 先尝试受约束局部级联，少动块 | 无理由挤到其他工作日或重排整周 |
| 当天无位置、后续周末有位置 | 搜索调整窗口内后续日期，硬约束一致 | 只看工作日、忽略周末空闲 |
| deadline/allowed weekday/日上限冲突 | 拒绝并显示准确首要原因 | 绕过硬约束或统一写“时间不足” |

## 事务不变量

实现和评审必须逐条验证：

1. 任意时刻最多一个 `confirmed` 当前计划；历史版本不可物理覆盖。
2. 一个 adjustment 最多一个 applied receipt、一个 appliedPlanVersionId、一个有效 undo receipt。
3. preview 只能由创建它的 operation 使用；accepted preview 不可再次绑定另一计划。
4. adjustment `applied` 必然能找到 plan、apply receipt 和 event；反向也成立。
5. 新 plan 的每个 task block 都通过完整 hard validator；目标 lineage 通过 fulfilment。
6. 任何失败前状态和失败后状态，在计划/块/执行关联/片段方面相同；允许新增脱敏 failure event，但不能改业务真相。
7. 通知/outbox 失败不回滚已提交计划；提交前失败不产生 outbox。
8. undo 不删除 execution evidence；只重定向尚未开始的当前关联。
9. UTC 存储和本地 policy/day 计算边界明确；不得用系统当前时区代替任务时区。
10. 任意 mutable collection 在跨层前复制为不可变视图；不得让 UI 修改领域对象。

## 崩溃、恢复与回滚决策表

| 崩溃点/异常 | 下次启动判定 | 自动动作 | 用户看到 |
| --- | --- | --- | --- |
| adjustment 创建前 | 无记录 | 无 | 原页面，可重试 |
| active 已写、生成前 | active | 提示继续/放弃 | “尚未生成预览” |
| generating 中、无 preview | generating 且无完整 preview/hash | CAS 回 active | “上次生成中断，可重新生成” |
| preview 写一半 | transaction 回滚，无完整 active preview | 回 active/failed | 不展示残缺预览 |
| previewReady 后退出 | active preview + previewReady | 原样恢复 | 可继续确认或取消 |
| apply 事务提交前 | 无 receipt，状态由回滚保持 previewReady | 恢复预览 | 可再次确认 |
| apply 事务已提交、UI 未收到 | applied receipt 存在 | 恢复 applied | “计划已更新”而非再应用 |
| outbox 处理失败 | plan applied，outbox pending | 后台退避重试 | 非阻断状态说明 |
| undo 提交前失败 | undo receipt 未完成，计划不变 | 允许重试 | “未撤销” |
| undo 已提交、UI 未收到 | restore plan + completed receipt | 恢复 alreadyUndone | “已撤销” |

数据库迁移和发布回退遵循 forward-only：1.11.0 schema 11 一旦写入，不允许旧版二进制打开并降级 schema。需要回退应用版本时，先恢复兼容 schema 11 的修复构建；不得在用户机器上自动删表或恢复旧数据库文件。测试数据库可用隔离副本演练，不接触真实数据。

## 明确禁止的捷径

- 禁止在 `router.dart` 的 `finally` 清除 adjustment。
- 禁止继续用 singleton 的 `_adjustment` 或 unbounded `_previews` 维持业务真相。
- 禁止通过修改整个任务 `availableFromUtc` 来实现“本次”延后。
- 禁止目标缺失时调用普通生成并把其结果当作调整成功。
- 禁止只在 apply 最后一步检查兑现；预览前和展示前同样必须检查。
- 禁止将精力、偏好、均衡、坏空档升级为硬约束。
- 禁止把全部失败归因于“可用时间不足”或由 UI 猜原因。
- 禁止以固定 5 分钟、系统时区、窗口首日规则处理所有日期。
- 禁止捕获任意数据库异常后返回幂等成功；必须验证完整 token/receipt。
- 禁止先提交计划再同步通知，并把通知失败当成计划失败。
- 禁止撤销时删除完成、进度、执行或历史审计证据。
- 禁止用 mock-only service test 声称 router 端到端已覆盖。
- 禁止把本计划剩余项移到 1.11.1/1.12.0 后仍宣布 1.11.0 完成。
