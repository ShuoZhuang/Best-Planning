# 1.11.1 更新清单隔离、回退基线与状态恢复修复实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:test-driven-development` for every production change, `superpowers:systematic-debugging` when a red test differs from this incident model, and `superpowers:verification-before-completion` before reporting any task complete. Execute tasks in order; do not skip the red-test evidence in Task 1.

**Goal:** 修复 1.10.2 客户端在已发现或已下载 1.11.0 后错误显示“已是最新版”、安装被永久阻塞于“回退基线未就绪”、重启后目标状态丢失等问题，并使更新检查、回退基线、缓存、恢复和界面在并发、断网、304、崩溃及旧状态迁移下保持一致。

**Architecture:** 用“带请求身份的分区缓存”取代全局单文件缓存；把 ETag 与对应缓存项原子绑定；让更新状态机遵守目标单调性并能从磁盘重建；把回退基线变成可观察、可重试、可严格校验的独立子状态；所有入口共用 single-flight 编排，不通过弹窗打断用户。已发布的 1.11.0 不改写，修复发布为 `1.11.1+53` / MSIX `1.11.1.0` / tag `v1.11.1`。

**Tech Stack:** Flutter/Dart、Windows MSIX、GitHub Release 静态清单、Ed25519 清单签名、SHA-256、现有原生 update helper、现有 JSON 原子文件存储。

## 1. 事故结论

### 1.1 用户可见现象

同一台已安装 1.10.2 的机器先后出现了两组相互矛盾的状态：

1. 首次检查正确发现并下载 `1.11.0.0`，但安装入口显示 `UPDATE_BLOCKED_ROLLBACK_NOT_READY`；
2. 重启并成功准备 1.10.2 回退包后，设置页却显示：
   - 当前版本：`1.10.2.0`；
   - 最新稳定版本：`1.10.2.0`；
   - 当前阶段：已是最新版；
3. GitHub 上实际 latest release 是 `v1.11.0`，且 1.11.0 MSIX 已经完整下载在本地；
4. 因状态被错误清空，界面不再承认已下载的 1.11.0，用户既不能安装，也无法从界面理解为什么退回了 1.10.2。

### 1.2 已确认的直接根因

当前实现让两类语义不同的请求共享同一个 `update-manifest.cache.json`：

- `fetchLatest()`：询问“stable 通道现在最新是什么”；
- `fetchForTag(v1.10.2)`：询问“1.10.2 的不可变历史清单是什么”，用于建立回退基线。

真实触发顺序如下：

```text
latest 请求返回 200 / 1.11.0
  → 全局缓存写成 1.11.0
  → 状态保存 latest 的 ETag
  → 1.11.0 包下载完成，phase=ready

后台建立回退基线
  → tag v1.10.2 请求返回 200 / 1.10.2
  → 同一个全局缓存被覆盖成 1.10.2

下一次 latest 检查携带先前 latest 的 ETag
  → GitHub 对 latest 返回 304
  → 代码从全局缓存读取 1.10.2
  → 1.10.2 被错误解释为 latest
  → relation == same
  → target、下载进度与安装入口被清空
  → phase=upToDate
```

这不是 GitHub Release 缺失，也不是单纯的界面缓存；错误数据已经进入领域状态机。

### 1.3 现有测试为什么没有发现

2026-10-20 对以下四组现有测试执行了基线验证，共 49 项，全部通过：

```text
test/infrastructure/update/file_update_manifest_cache_test.dart
test/infrastructure/update/http_update_manifest_repository_test.dart
test/application/update/update_baseline_service_test.dart
test/application/update/update_orchestrator_test.dart
```

它们只分别验证“latest 的缓存”“tag 的基线”“单次 304”“单次版本比较”，没有覆盖以下跨组件顺序：

```text
latest(1.11.0) → tag(1.10.2) → latest(304) → 状态机保留 ready(1.11.0)
```

因此，现有绿灯只能证明各组件在隔离条件下工作，不能证明共享缓存与并发组合正确。

## 3. 不可违反的产品与安全决策

### 3.1 用户体验

1. 软件联网后可自动检查并下载；安装必须由用户点击左下角更新入口发起。
2. 不新增更新弹窗、确认弹窗或强制抢焦点窗口。
3. 后台准备回退基线期间，用户可以继续使用软件，也可以继续下载目标版本，但不能开始安装。
4. 点击安装时若基线未准备好，应立即触发/加入同一个基线任务，并把入口变成“正在准备安全更新”；不能只吐出内部错误码。
5. 网络恢复后自动重试；手动“重试”立即重试，但不能产生多个并发下载。
6. 已下载且验证通过的目标包不得仅因缓存、304 或状态文件问题被删除或重新下载。

### 3.2 发布与版本

1. 这是纯缺陷修复，版本为 `1.11.1+53`，MSIX 为 `1.11.1.0`。
2. 不修改、不删除、不替换已发布 `v1.11.0` 的 tag 或资产。
3. 不把这次修复冒充为 `1.11.0.1`：代码发生变化，按版本规则必须抬 Patch，而非只抬 MSIX Revision。
4. 数据库 schema 仍为 11；算法版本仍为 20；包身份、Publisher、PFN 不变。
5. 若 `+53` 在实施前已被其他正式构建占用，使用下一个全局单调递增构建号，并同步全部版本台账；不得复用构建号。

### 3.3 安全与合规

1. 只访问既有 GitHub 仓库固定地址和白名单资产域；不新增遥测、设备标识或用户数据上传。
2. 每份远端清单必须经过结构校验、来源校验和 Ed25519 验签。
3. 每个安装包必须经过长度、SHA-256、包身份、目标版本和发布者校验；安装前再次验证。
4. 日志不得保存 URL 查询串、Authorization、Cookie、用户路径中的个人目录名或完整异常堆栈。
5. 任何旧缓存迁移失败都只能触发“重新拉取”，不能触发“已是最新版”。
6. 所有状态/缓存写入继续使用同目录临时文件加原子替换；不得原地覆盖 JSON。
7. 任何错误都不得绕过回退基线安全门；也不得要求普通用户手工删除缓存作为正式解决方案。

## 4. 目标数据模型

### 4.1 请求身份必须是一等类型

新增 `lib/domain/update/manifest_request_key.dart`：

```dart
enum ManifestRequestKind { latestStable, releaseTag }

final class ManifestRequestKey {
  const ManifestRequestKey.latestStable();
  const ManifestRequestKey.releaseTag(String tag);

  final ManifestRequestKind kind;
  final String? tag;

  String get storageKey;      // latest-stable / tag-v1.10.2
  Uri get canonicalUri;       // 固定 latest URL 或固定 tag URL
}
```

要求：

- tag 在构造时通过现有严格正则；非法 tag 不产生文件名；
- `storageKey` 只能由枚举与已验证 tag 生成，不能使用远端 URL 或任意字符串；
- `==`、`hashCode` 和 JSON 表达稳定；
- latest 与任何 tag 永不相等。

### 4.2 缓存项原子绑定请求身份与 ETag

新增 `ManifestCacheEntry`，至少包含：

```text
schemaVersion = 2
requestKey
canonicalRequestUrl
confirmedAtUtc
etag
canonicalDigest
sanitizedResolvedOrigin
envelope
```

`etag` 不再由 `UpdateState` 作为下一次 HTTP 请求的权威输入。仓库必须从同一个 `ManifestCacheEntry` 同时读取 envelope 与 ETag，保证二者不会错配。

`sanitizedResolvedOrigin` 只允许保存 `scheme + host + path`，禁止 query 和 fragment。正常界面只显示“GitHub 稳定通道”或“GitHub 发布 v1.10.2”，诊断导出也不得恢复被删掉的查询串。

### 4.3 磁盘布局

`UpdateStorageLayout` 增加：

```text
Updates/
  manifests/
    latest-stable.json
    tags/
      v1.10.2.json
      v1.11.0.json
  update-manifest.cache.json.legacy-quarantine   # 只在需要留证时生成
```

迁移原则：

- 旧 `update-manifest.cache.json` 没有 request key，不能猜它属于 latest 还是 tag；
- 首次启动 1.11.1 时，将其原子改名为 legacy quarantine 或安全删除；
- 绝不把旧内容自动复制进 `latest-stable.json`；
- 迁移失败不影响应用启动，latest 下次无条件拉取；
- quarantine 最多保留一份，且必须经过日志脱敏。

### 4.4 基线状态与安装事务分离

新增显式基线准备状态，不再只靠 `rollbackNotReady` 布尔量推断：

```dart
enum BaselinePhase { absent, preparing, ready, retryWaiting, failed }

final class BaselinePreparationState {
  final BaselinePhase phase;
  final MsixVersion requiredForInstalledVersion;
  final int attempt;
  final DateTime? nextAttemptUtc;
  final UpdateFailure? lastFailure;
}
```

`RollbackBaseline` 只表示“当前已安装版本的已验证回退包”。更新前业务数据快照属于具体安装事务，由 `UpdateInstallService` 生成并写进 update request；不要再用注释声称下载基线时已经具备快照。

### 4.5 UpdateState 迁移

状态 schema 从 v1 抬至 v2，但必须实现显式 v1→v2 迁移：

- 保留 `phase`、`target`、`receivedBytes`、`baseline`、失败、重试和事务字段；
- `manifestEtag` 迁移为仅诊断字段或删除，不再驱动请求；
- 根据 v1 baseline 是否存在只设置 `BaselinePhase.absent/ready` 的候选值，随后必须走严格复核；
- 迁移后立即原子写回 v2；
- 单字段损坏时优先保留可独立验证的 target/baseline 线索，不得因为 schema 改版直接重置整份状态；
- 无法安全解释的字段清空并记录稳定错误码，不记录原始路径内容。

## 5. 状态机硬约束

实现和测试必须共同守住以下不变量：

### INV-01 缓存身份

`304(requestKey=X)` 只能使用 `cache[X]`；`cache[Y]` 即使签名有效也不能替代，其中 `X != Y`。

### INV-02 ETag 原子性

发送 `If-None-Match` 的值必须与用于处理 304 的同一缓存项一起读取。不存在“从 state 取 ETag、从另一个文件取 envelope”的路径。

### INV-03 目标单调性

只要本机仍是 1.10.2，且已有签名验证过的 1.11.0 target/ready 包：

- 较旧、相同或来源不明的 latest 结果不得清除 target；
- 只有以下事实可以清除：本机已安装版本 ≥ target；或一份新鲜、签名有效的 latest 清单明确把 target 列入 `revokedVersions`；或用户执行明确的“放弃此更新”动作（当前产品没有该动作）。

### INV-04 明确撤回优先于单调性

若新鲜签名清单明确撤回 target：

- 禁止安装；
- target 状态改为 revoked，而不是 upToDate；
- `.ready` 移到隔离位置或按既有安全删除策略处理；
- UI 显示“此更新已撤回，正在等待新版本”，不得显示“已是最新版”。

### INV-05 已验证文件优先于易损状态

状态文件只是线索。启动时若存在与签名清单相符的 `.ready`，应收养为 ready；若无法证明身份则隔离，不能直接执行，也不能静默删除。

### INV-06 基线版本一致

允许安装 target 的基线必须满足：

```text
baseline.version == installed.version
文件存在
长度匹配
SHA-256 匹配
包身份匹配
包版本 == installed.version
发布者 == 当前应用发布者
```

### INV-07 单次基线任务

启动、开关、手动检查、手动下载、自动检查和点击安装可以同时触发 `ensureBaseline()`，但进程内最多只有一个真实基线任务；所有调用方 await 同一 Future。

### INV-08 失败可恢复

基线失败必须持久化失败码、attempt 和 nextAttemptUtc。联网恢复、到达退避时间或用户点击重试均可恢复；成功后必须清除匹配的旧失败与 blocker。

### INV-09 安装过程中的上一版保留

升级健康确认完成前，旧基线包与更新前快照不得被新基线覆盖或清理。健康确认成功后，已安装目标包才能晋升为下一次更新所需的 current baseline。

### INV-10 不重复下载

磁盘已有大小和哈希正确的目标 `.ready` 时，重新发现同一 target 必须复用；不得从 0 重新下载。

**New source API:**

```dart
Future<ManifestFetchResult> fetchLatest({bool forceRefresh = false});
Future<ManifestFetchResult> fetchForTag(
  String tag, {
  bool forceRefresh = false,
});
```

调用者不再传任意 ETag。仓库流程固定为：

1. 构造 `ManifestRequestKey`；
2. 从 `cache[key]` 读取 envelope + ETag；
3. 若非 force refresh 且缓存有效，发送对应 ETag；
4. 304 时只读取同一个 key；
5. 对应缓存缺失/损坏时，只允许无条件重试一次；
6. 第二次仍 304，返回 `manifestNotModifiedWithoutCache`，不能返回 upToDate；
7. 200 响应验签成功后原子写回同一个 key；
8. 返回值携带 request key 与 canonical request URL；最终重定向 URL 只保留脱敏 origin。

**Concurrency requirement:**

- 同一个 key 的并发 fetch 合并为一个 in-flight Future；
- 不同 key 可并行，但各写各的文件；
- 任意完成顺序都不能相互覆盖。

**Required tests:**

```text

tag 200→latest 200→tag 304 返回对应 tag 缓存
latest 304 找不到 latest 缓存时无条件重试
tag 304 不能读取 latest 缓存
同 key 并发只发一个网络请求
不同 key 反序完成仍各自正确
诊断来源不含 query 与 fragment
forceRefresh 不发送 If-None-Match
```

**5.1 latest 结果合并规则**

引入纯函数（名称可调整，职责不可合并回巨型 `_runCheck`）：

```dart
UpdateDiscoveryDecision reconcileDiscovery({
  required InstalledPackage installed,
  required UpdateState current,
  required VerifiedManifest incomingLatest,
});
```

决策顺序：

1. 验证 incoming 的 source key 必须是 `latestStable`；
2. 处理显式 revokedVersions；
3. 若 installed ≥ current target，则清理已完成目标；
4. 若 incoming target > current target，升级 target；
5. 若 incoming target == current target，刷新清单元数据但保留下载/ready；
6. 若 incoming target < current target 且 current target 未被明确撤回，保留 current target，并把本次检查记为 `temporarilyUnconfirmed/staleLatest`；
7. 只有当前没有更高 target 且 incoming == installed 时，才能进入 upToDate。

```text
读取 installed package
→ 迁移/读取 state
→ 复核 state 指向的 target 文件
→ 枚举受控版本目录中的 .ready
→ 根据已验证 latest/tag 清单收养、保留或隔离

→ 原子持久化
→ 才允许调度自动检查
```

- 文件必须位于 `UpdateStorageLayout` 内；
- 版本目录名可解析且严格高于 installed；

- 长度、SHA-256、包身份全部通过；
- 多个可用版本只选择最高且未撤回者，其他保留至清理阶段；
- 无法证明身份的文件改名为 `.quarantine`，绝不执行。

| 旧客户端迁移 | v1→v2 fixture | 事故机器升级 | 无需删缓存，target 恢复 |
| ready 收养 | startup reconciliation | 保留 ready 后删 state 再启动 | 不重下，可安装 |
| 基线严格验证 | baseline tests | 篡改副本演练 | 任一校验失败均阻止安装 |
| single-flight | concurrency tests | 连点重试 | 只有一个真实下载 |
| 联网恢复 | scheduler/controller tests | 断网→联网 | 自动恢复且无弹窗 |
| 安装事务 | install/health/helper tests | 已签名 MSIX 覆盖升级 | 可成功升级或可靠回退 |
| 无弹窗 UI | architecture/widget tests | 桌面会话观察 | 仅左下角非模态入口 |
| 诊断脱敏 | diagnostics tests | 查看/复制日志 | 无 query/token/完整用户路径 |
| 发布不可变 | publisher tests | GitHub release 复核 | 已有 tag/资产不可覆盖 |

## 8. 发布前故障注入

下列场景每项都要在验收台账中有 PASS/FAIL/NOT RUN 和证据路径：

1. latest 清单 200，tag 清单 200，latest 304；
2. latest 缓存被截断；
3. tag 缓存被替换成另一有效签名版本；
4. ETag 变化但响应体仍旧；
5. CDN 返回旧 latest 200；
6. 下载 target 中途断网；
7. 下载 baseline 中途断网；
8. target ready 后 state 写坏；
9. baseline 同长度篡改；
10. 点击安装瞬间 baseline 被替换；
11. 磁盘空间只够 target、不够 baseline；
12. 两次快速点击重试；
13. 启动自动检查与手动检查同时触发；
14. 应用在每个原子写边界退出；
15. target 被清单明确撤回；
16. 1.10.2→1.11.1 成功，健康确认成功；
17. 1.10.2→1.11.1 安装后健康确认失败并回退；
18. 1.11.0→1.11.1 正常升级；
19. 自动更新关闭时启动不产生网络；用户手动检查后可完整升级；
20. 日志和诊断内容脱敏检查。

## 10. 执行顺序与停线条件

必须按以下阶段推进：

```text
Phase A 证据：Task 1
  ↓ 红灯确认
Phase B 数据边界：Tasks 2–4
  ↓ latest/tag 隔离 + v1 迁移通过
Phase C 状态与安全：Tasks 5–8
  ↓ 单调性、恢复、基线、安装生命周期通过
Phase D 界面与系统链路：Tasks 9–11
  ↓ 无弹窗、真实组合根、诊断脱敏通过
Phase E 发布：Task 12
```

任一条件触发停线，不得继续发布：

- 新测试无法复现真实事故且原因未解释；
- v1 状态迁移导致 target 或 baseline 无条件丢失；
- stale latest 仍能把 ready 改成 upToDate；
- 安装入口存在绕过严格基线校验的路径；
- 已签名 MSIX 安装/回退未验收；
- GitHub tag 或资产发生覆盖；
- 日志仍包含临时 URL query；
- 全量测试或静态分析失败；
- 工作树包含无法解释的无关改动。
