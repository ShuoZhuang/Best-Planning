# Best Planning 用户体验总改进路线图

> **交给执行 Agent：** 本文是 `1.6` 发布线的总路线图。全部改进属于同一个发布批次，内部拆成 M1～M9 九个实施里程碑；里程碑不是版本号，也不单独发布。执行当前里程碑时，必须先读取对应规格与实施计划，再使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 逐项实施。所有检查项均使用 `- [ ]` 跟踪，未满足退出条件不得进入下一里程碑。

**目标：** 把当前“功能已经很多，但陌生用户仍需要猜测”的 Windows 测试版，改成一款能够安装、理解、安排、执行、复盘并安全保留数据的正式软件。

**执行结构：** 总路线图决定问题顺序、里程碑边界、依赖、验收指标和最终发布门槛。每个里程碑独立完成设计、编码、测试和人工体验，但不单独抬版本、不单独制作正式安装包；M1～M9 全部通过后，统一生成一个 `1.6.x` 正式版本。任务、计划和实际投入继续使用现有领域模型，界面不得另造一套状态事实。

**技术栈：** Flutter Windows、Dart、Drift/SQLite、GoRouter、Windows MSIX、现有本地 OCR 与通知能力。

## 1. 当前基线

### 1.1 产品基线

- 主要用户仍是同时处理学业、科研、竞赛、学生工作和个人生活的大学生。
- 软件为 Windows x64、本地优先、单用户产品，不要求注册和联网。
- 计划默认覆盖未来七天，同时检查更远截止日期。
- 自动调整默认先预览再确认；“信任自动调整”保持可选且默认关闭。
- 任务、固定日程、课程、保护时间、专注记录和统计已经有生产代码，不得以重建项目代替修复现有流程。
- 手机 App、账号同步、多人协作、在线大模型排程不在本路线图内。

### 1.2 代码基线

- 当前开发工作树：`G:\best-planing\.worktrees\native-implementation`。
- 当前开发候选：`1.6.1+36`，MSIX `1.6.1.0`。它是 `1.6` 发布线的中间状态，不代表某个里程碑完成后就单独正式发布。
- 当前分支存在未提交的任务状态筛选、统计修复和版本资料改动。任何 Agent 开工前先运行 `git status --short --branch`，不得重置、覆盖或删除这些修改。
- 任务状态筛选已经有专项计划，路径为 `docs/superpowers/plans/2026-10-07-task-list-status-filters.md`。

### 1.3 已确认的主要问题

1. 任务页与今日、日历中的任务事实不一致，用户容易误判数据丢失。
2. 新建任务一次暴露过多字段，保存按钮离主要输入太远；领域、项目、开始时间和拆分方式不够醒目。
3. 今日页擅长展示，但缺少足够直接的执行动作。
4. 七日日历适合看事项数量，不适合判断真实时间间隔、空档和冲突。
5. 领域与项目的关系虽然有说明，实际控件仍然要求用户猜测。
6. 统计页的颜色、文字可读性和指标口径没有完全回答“时间花到哪里、计划是否现实”。
7. 课表导入已经有流程，但图片读取失败、识别修正和部分失败恢复仍会让用户卡住。
8. 新手教程偏阅读，未真正带用户完成首个任务、课表导入或第一份计划。
9. 已安装版本的 Windows UI Automation 只暴露 `FLUTTERVIEW`，键盘、屏幕阅读器和自动化可达性不合格。
10. 构建成功不等于正式发布；人工验收、覆盖安装、通知点击、哈希和 GitHub Release 仍需逐批完成。

## 2. 执行方法选择

### 方案 A：一次性重构全部页面

优点是表面上进度集中，缺点是任务状态、日历、统计和设置会同时变化，无法判断回归来自哪里；安装包也很难给出可信的验收结论。否决。

### 方案 B：按用户闭环拆成可安装批次

每一批只解决一个完整问题，例如“看懂任务状态”或“在今日页完成任务”，完成后就打包安装。批次之间通过已有仓库接口和领域对象衔接，不共享半成品 UI。采用此方案。

### 方案 C：先统一视觉，再处理流程

能较快改善截图观感，但任务丢失感、长表单、导入失败和不可访问问题仍然存在。视觉修正只跟随相关里程碑，不单独抢占优先级。

## 3. 全局约束

所有批次必须遵守以下规则：

- 本地优先：任务、课表图片、统计和偏好默认不上传。
- 单一事实来源：任务状态来自任务与当前确认计划；统计颜色来自领域颜色服务；实际投入来自实际记录。
- 不静默越过固定日程、保护时间、锁定时间块、连续任务和每日上限。
- 用户主动设置优先于学习偏好；临时例外不改写长期设置。
- 新建任务继续采用“详细新建并展示默认值”，不得恢复独立快速收集箱。
- 领域先于项目选择，项目只能属于一个领域，项目列表按已选领域过滤。
- 任务最早开始时间必须成为排程硬边界，任何计划块不得早于它。
- 允许拆分与必须连续必须在新建、详情、计划预览中保持同一口径。
- 今日、日历和统计使用同一领域颜色；保护时间与无领域任务分别使用专用颜色。
- 玻璃材质保留“无、克制、激进、极致”四档，但可读性优先于透明效果。
- 不删除或覆盖用户现有数据库；需要迁移时必须先写迁移测试和回滚说明。
- 不改包身份和签名证书；私钥、PFX、真实数据库、备份和课表原图不得提交到 GitHub。
- `.cer` 公钥证书可以随 Release 分发。
- 本路线图经用户明确决定，M1～M9 全部并入 `1.6` 发布线，不因完成单个里程碑改变 Minor 版本，也不为里程碑分配 Patch 号。
- 里程碑期间只生成内部验证构建；最终对外版本保持 `1.6.x`。最终 MSIX 必须严格高于届时本机已安装的版本；第三段、MSIX Revision 和构建号 `+N` 只在最终发布构建时按现有版本规则确定，不得改变第二段 `1.6`。
- 最终 `1.6.x` 必须同时提供便携目录、ZIP、已签名 MSIX、`.cer`、安装脚本、安装说明、SHA-256 和对应用户指南。

## 6. 里程碑 M2：可访问与可读基线

## 7. 里程碑 M3：新建任务与领域项目闭环

**优先级：** P0。

### 已有能力

详细新建表单、默认值、领域选择、领域过滤后的项目选择、项目新建、最早开始、截止时间、可拆分/必须连续、片段长度和期望时段已经存在。本里程碑只调整信息层级、操作距离和缩放表现，不改这些字段的领域模型。

### 用户结果

用户在一个详细新建页面中看到默认值并按需修改；最常用字段无需滚动三屏，保存按钮始终可见。领域与项目的关系在操作中自然成立，不再依赖说明文字补救。

### 表单结构

首屏固定显示：

- 标题。
- 预计时长。
- 领域。
- 项目（位于领域之后，并按领域过滤）。
- 最早开始时间。
- 截止时间。
- 是否允许拆分。

“更多设置”展开区显示：

- 优先级与精力要求。
- 拆分后的最短、最长片段，或必须连续时长。
- 期望时段。
- 标签与备注。

“计入个人生活时间”属于领域属性，只在领域管理中设置，不作为单个任务的重复字段。

保存区使用固定底栏，同时显示缺失字段和当前关键约束摘要。

### 领域与项目规则

- 新建任务时立即可选领域，不得先保存再编辑。
- 选择领域后才显示该领域下的项目。
- 新建项目必须选择领域；默认继承任务当前已选领域，但用户可以修改。
- 切换领域后，如果原项目不属于新领域，清空项目并给出明确说明。
- “领域”表达长期责任范围；“项目”表达有边界的阶段性成果。界面用一行短说明和实例解释，不使用长段落。
- 领域页把无文字开关改为“计入个人生活时间”，颜色圆点改为带标签的“颜色”按钮。
- 项目分区必须在首屏可见，或使用“领域／项目”两个明确标签页。

### 周期事项边界

- 普通任务不新增模糊的“周期任务”开关。
- 有固定上课或会议时间的周期事项进入固定日程或课表导入。
- 需要重复完成但时间可移动的事项，单独设计“重复任务”前必须另立规格，不在本批偷偷加入。

8. 预览将创建、更新、跳过和冲突的日程。
9. 一次性提交；失败时整批回滚。

- 无法解码图片时显示文件名、支持格式和“更换图片”，不得只显示系统异常文本。

## 16. 总体验收指标

整个路线图只有满足下列条件才算完成：

| 指标 | 通过标准 |
| --- | --- |
| 首个任务 | 使用默认值，60 秒内保存成功 |
| 首份计划 | 全新用户能通过引导完成创建或导入、生成、预览和应用 |
| 状态可信 | 任务、今日、日历对同一任务的完成与安排状态一致 |
| 今日执行 | 开始当前任务不超过两次点击，完成后各页面同步 |
| 重排控制 | 默认先预览；取消不改数据；自动模式不突破硬约束 |
| 周日历 | 能按真实时间比例观察时长、空档和重叠 |
| 课表导入 | 用户提供的代表性截图可识别、修正、预览并原子提交 |
| 统计 | 计划与实际分开，颜色一致，范围边界可复算 |
| 可访问性 | 键盘主流程走通，UI Automation 有独立节点，Narrator 能读出状态与错误 |
| 数据安全 | 失败导出可恢复，损坏备份不覆盖数据库，覆盖安装不丢数据 |
| 发布 | 每版都有可安装 MSIX、便携包、说明、哈希、台账和 GitHub Release |

## 17. 决策记录与变更控制

新增需求只有满足以下步骤才能进入路线图：

1. 写明解决的用户问题，而不是只写界面做法。
2. 指定进入哪个批次；如果破坏批次边界，就新建后续批次。
3. 说明对排程、数据、隐私、版本和安装包的影响。
4. 涉及上传本地数据、突破硬约束、自动修改任务原文、改变统计口径或更换包身份时，必须重新取得用户明确确认。
5. 更新对应规格、实施计划、测试和验收清单；不能只改本文的一行。
