# 算法 20：完整约束规划、特殊日与学习偏好设计规范

**状态：** 已冻结，等待实施

**冻结日期：** 2026-10-17

**代码基线：** `DeterministicScheduleEngine.algorithmVersion == '19'`，HEAD `d5951f10`

**产品基线：** 1.8.0；本规范不决定下一个产品版本号

**替代关系：** 本规范继承算法 19 已通过的能力，并取代旧文档中尚未实施、与现状冲突或语义不完整的算法规则。旧验收记录不删除。

## 1. 目的与完成标准

算法 20 不是继续给贪心放置器添加例外。它把排程拆成可以单独验证的层级：输入事实、硬约束容量、跨日分配、日内放置、有界交换、方案选择、结构化解释、安全应用。学习偏好和特殊日只通过明确端口进入这些层，不能在界面或诊断阶段临时猜测。

实现完成后必须同时满足以下结果：

1. 只要硬约束下存在可行方案，引擎不能因为精力、期望时段、日期平局或局部贪心而留下缺口。
2. “可用时间不足”只能由形状感知的容量证明产生；日历看起来有空但受连续长度、起止范围、星期、每日上限限制时，要显示具体限制。
3. 同一输入产生逐值相同的计划、原因、候选扩展建议与排序。
4. 普通重排优先保留已确认块；用户明确延后某一块时，只在必要范围内级联移动。
5. 工作日与周末没有固定倾向。日期选择取决于截止风险、真实负载、可落地容量和用户明确设置。
6. 特殊日与临时延长日是可保存、可撤销、可审计的事实；它们不能静默改动睡眠或计划。
7. 学习偏好有可靠样本、进度、确认状态和作用范围；它永远是软偏好，不能压过硬约束和用户手动设置。
8. 提案失效、搜索预算耗尽、硬无解、结构异常和软偏好未满足必须分开处理。
9. 所有写入都通过输入重放、统一校验和事务边界；失败时保持上一版计划不变。

## 2. 范围

### 2.1 本规范包含

- 普通任务、周期目标、确认计划块、块级延后和自动重排的统一排程内核。
- 逐日规则、工作日/周末差异、睡眠、保护时间、固定日程、课程过渡与每日上限。
- 容量形状、坏空档、片段、负载均衡、周末使用、稳定性与确定性。
- 特殊日、临时延长日、次日恢复休息、提前入睡和降低次日负载。
- 学习偏好的证据采集、分析、确认、持久化、排程消费、进度和清除/重启。
- 预览、结构化原因、候选操作、应用前校验、撤销和审计。
- 数据迁移、隐私、性能、属性测试、黄金测试与 Windows 发布门禁。

### 2.2 本规范不包含

- 联网求解服务、账户同步、多人协作或云端模型。
- 自动删除任务、自动完成任务、自动取消课程或保护时间。
- 用一次晚睡改变长期起床时间。
- 未经确认自动创建临时延长日。
- 数学意义上的全局最优证明。算法承诺在固定预算内返回最佳已知合法方案，并准确区分“已证明无解”和“搜索尚未证明”。
- 与排程内核无关的独立界面缺陷，例如托盘左键、通知进程、课程编辑、日历卡片对齐、早餐标题和日期/时间选择器；它们继续由各自修复文档追踪，不能借算法 20 顺带改动。

## 3. 术语与唯一口径

| 术语 | 定义 |
| --- | --- |
| 本地日 | 由 `TimeZoneDatabase` 和 `timeZoneId` 得出的 `DateTime(y,m,d)`；星期、每日上限、周界均按它计算 |
| 硬空闲 | 规划窗口扣除固定日程、保护时间、睡眠、课程过渡和锁定块后的区间并集 |
| 任务合规容量 | 硬空闲继续应用任务最早开始、截止、允许星期、连续/拆分、每日任务上限后的容量 |
| 可落地容量 | 合规容量继续应用粒度、最短片段、休息、已选块和连续形状后的实际可放分钟 |
| 形状签名 | 可用区间的长度多重集、最长连续段、可用日期和可容纳片段数量，不只是总分钟 |
| 基线计划 | 本次生成开始时已确认且仍有效的计划块集合 |
| 稳定性成本 | 被改变块数、删除/重建数、总位移分钟、来源关联丢失数构成的字典序向量 |
| 坏空档 | 不属于保护/固定休息，长度不足以容纳任何剩余任务合法最短片段的空档 |
| 硬无解 | 穷尽允许搜索边界后，硬约束下不存在满足全部需求的方案 |
| 搜索未决 | 达到状态数或时间预算，尚未证明有解或无解 |
| 软受限 | 任务可安排，但精力、期望时段、均衡、坏空档等软目标未完全满足 |
| 特殊日 | 用户显式保存的按日本地事实，可以覆盖当天结束时间并带恢复策略 |
| 临时延长日 | 正常计划无解后，系统提出、用户显式确认的一次性特殊日；只能延后当天睡眠开始，不能延后次日起床 |
| 学习证据 | 带本地日期、领域、任务、时段、结果指标、特殊日标记和来源的不可变观察记录 |
| 已确认偏好 | 用户确认后可参与排程的领域级或全局软偏好；建议本身不等于已生效规则 |

全部时间区间使用半开语义 `[startUtc, endUtc)`。相邻区间不重叠。UTC 只负责存储和区间运算，不能直接用于星期、工作日/周末、活跃日或周界判断。

## 4. 输入事实与优先级

### 4.1 事实层级

从高到低依次为：

1. 已执行、正在执行、已完成事实。
2. 固定日程、课程、保护时间、睡眠最低线、用户锁定块。
3. 任务截止、最早开始、允许星期、连续要求、片段上下限和每日硬上限。
4. 用户对本次计划的明确操作，包括指定块延后、特殊日、临时延长日候选选择。
5. 用户长期手动设置，包括工作日/周末规则、精力窗口和专注片段设置。
6. 已确认学习偏好。
7. 系统默认值。

低层不能覆盖高层。学习偏好与默认值只能参与软目标；高精力任务在其他合法时段仍然可排。

### 4.2 任务优先次序

任务先按硬可行性稀缺程度分组，再按以下字典序排序：

1. 已逾期且仍可执行的未完成分钟。
2. 截止前剩余可落地容量与需求之比，越小越早处理。
3. 可用日期数，越少越早处理。
4. 连续任务优先于同条件可拆分任务。
5. 截止更早。
6. 用户优先级：紧急、高、中、低。
7. 剩余分钟较大但可选位置较少者优先。
8. 稳定任务键，最终以规范化任务 ID 排序。

优先级不能把硬不可行任务塞进非法时段，也不能让一个高优先级任务无限拆碎后挤掉能完整完成的同级任务。方案比较首先最小化各优先级的未安排分钟，再比较软质量。

## 5. 分层排程架构

```text
Repository / Settings / DayException / PreferenceEvidence
  -> PlanningInputAssembler
  -> InputAdmission + Normalization
  -> DailyPolicyMap + HardAvailability
  -> ShapeAwareCapacityLedger
  -> ScarcityOrderedDayAllocation
  -> IntradayPlacement
  -> BoundedRepairSearch
  -> LexicographicPlanSelection
  -> FinalDiagnostics + ExtensionCandidates
  -> ScheduleProposal
  -> Replay + Validation + TransactionalApply
```

每一层只能消费上一层公开输出；容量、原因和预览不得各算一套。

### 5.1 输入准入

输入装配必须在进入引擎前完成：

- 排除窗口外任务、未来周期实例和已完成任务，并保留结构化准入原因。
- 计算每个任务真实剩余量，已完成、已确认、锁定和本次新增分钟各扣一次。
- 为窗口涉及的每个本地日解析完整 `DailySchedulingPolicy`。
- 将特殊日覆盖叠加到指定日期，不扩散到邻日。
- 把已确认学习偏好按领域映射到对应任务；无领域任务只能使用全局偏好。
- 捕获一次 `nowUtc`，之后所有阶段不得调用系统时钟。
- 对所有数据库读取使用显式稳定排序。

### 5.2 硬约束判定顺序

候选依次通过：规划窗口、当前时刻/最早开始、截止、允许星期、固定/保护/睡眠/课程过渡/锁定占用、连续或片段形状、任务单日上限、全局单日上限、片段休息、执行中冻结。失败时记录每条拒绝证据；主原因由固定优先表选出，不能取“最后一次失败”。

### 5.3 形状感知容量

容量账本为每个任务、每个本地日保存：

- `hardFreeMinutes`
- `constraintEligibleMinutes`
- `placeableMinutes`
- `longestContiguousMinutes`
- `slotCountByChunkSize`
- `remainingTaskDailyLimitMinutes`
- `remainingGlobalDailyLimitMinutes`
- `rejectionCountsByCode`

连续任务只有存在完整连续段时才计容量；可拆分任务按粒度和最短片段计算，最终短尾只能使用现有明确规则，不能把任意小空隙都算成可用。重叠阻塞区间求并集后只扣一次，但原因保留全部来源。

### 5.4 跨日分配

跨日层只分配任务在每个本地日的分钟预算，不决定具体时刻。规则如下：

- 截止压力和稀缺日期先于负载均衡。
- 在不增加更高层缺口时，比较放入后的最大日负载率和超目标水位总量。
- 周末没有奖励；如果周末更空，它会自然胜出。工作日更空时同理。
- 周期目标同时最小化自身节奏偏差和全局负载差异。
- 预算只分给截止前、星期允许、形状可落地且日上限未满的日期。
- 日期完全同分时使用稳定周期轮换键，避免永远偏向周一或窗口第一天。
- 日内放置失败后，预算退回账本并重新分配；不能拿着过期预算直接报缺口。

### 5.5 日内放置

同一天内按以下顺序比较候选：合法、兑现预算、复用来源块原位、截止压力、用户明确期望时段、领域学习偏好、精力匹配、同任务连续性、类别切换、片段数、坏空档、开始时刻、稳定 ID。

精力和学习偏好只能决定合法候选之间的先后。它们不能使其他时段失去候选资格。

### 5.6 有界交换与方案选择

初次放置后执行有界修复搜索：

1. 选择未安排分钟最多且最稀缺的任务。
2. 枚举可落地位置、一次搬移、一次交换和受限级联。
3. 每个新状态先过增量硬校验，再计算方案目标。
4. 只保留每个状态签名下字典序最优方案。
5. 队列顺序和候选顺序固定；不得用随机数、进程 `hashCode` 或未排序集合。
6. 达到预算时返回最佳合法部分方案并标记 `searchBudgetExhausted`；不得谎称硬无解。

算法 20 使用一个明确的确定性 `SearchBudget`，包含最大状态数、最大队列宽度、最大修复深度和每状态最大分支数。预算判断只能依赖已访问状态等输入派生计数，不能读取墙钟；否则相同输入会因机器负载不同得到不同提案。生产默认值必须经基准测试冻结；不得保留不被生产调用的悬空参数。界面可在引擎外设置运行看门狗，但看门狗触发时必须取消并丢弃本次结果、显示重试，不得把当时的中间方案包装成可应用提案。

### 5.7 字典序方案目标

所有模式先比较：硬违规数、结构异常数、指定操作未兑现数。之后分别处理：

**初次生成：** 各优先级未安排分钟向量、逾期分钟、最大日负载率、超水位总量、周期节奏、片段浪费、偏好损失、坏空档、确定性签名。

**普通重排：** 前述完成度指标后，先比较改变块数、删除/重建数和总位移，再比较负载与软质量。

**明确块调整：** 目标块必须兑现，且不能增加相对基线的新缺口；随后最小化非目标块改变数、非目标位移、目标额外位移和其他软损失。

后一项改善不能补偿前一项恶化。不得恢复加权总分。

## 6. 稳定性、来源身份与局部修复

已确认块必须用持久化块 ID 进入稳定性层。提案块继续使用本次生成 ID，并通过 `continuedFromId` 指向来源。`referenceBlocks`、`existingBlocks`、`lockedBlocks` 和冻结集合必须使用同一持久化 ID 族做匹配。

`computeFrozenBlockIds(...)` 抽成纯函数，输入为基线块、当前时刻、执行状态、锁定状态、用户钉住集合和目标调整，输出稳定排序的不可变 ID 集合。测试直接断言以下边界：已执行冻结、执行中冻结、显式锁定冻结、目标调整块不被冻结、未锁定未来块可移动、来源缺失时阻断而不是猜测。

块级延后先执行 `localRepairCascade`；局部修复成功且通过方案比较时不启动全局搜索。失败后才能进入有界全局搜索。全局搜索失败、预算耗尽或新缺口增加时保留原计划，产生可解释预览，零写入。

## 7. 空档、休息与“不制造坏空档”

坏空档是软质量，不是新的硬约束。强制禁止所有坏空档会把本来可完成的计划判为无解，因此采用方案级比较：在完成度、截止、明确调整和稳定性相同的方案之间，先减少无法被剩余任务使用的空档数量，再减少其总分钟。

20 分钟左右的间隔按以下规则处理：

- 如果它是用户保护时间、课程过渡或片段休息，保留并显示来源。
- 如果存在最短片段不超过该间隔的剩余任务，可作为候选容量。
- 如果没有任务能合法使用，不伪装成“可用时间”；统计中列为碎片空档。
- 引擎不能为轻微精力得分制造多个碎片空档。
- 坏空档减少不能导致未安排分钟增加、截止恶化或额外移动已确认块。

## 8. 特殊日与临时延长日

### 8.1 持久模型

特殊日必须作为本地日期事实保存，至少包含：ID、本地日期、类型、创建来源、原睡眠开始、临时睡眠开始、固定次日起床、最低睡眠分钟、恢复选择、可空的恢复本地日期、状态、创建/更新时间、撤销时间、触发提案 ID 和审计说明。三个睡眠时刻使用“相对特殊日本地 00:00 的分钟偏移”，允许临时入睡和次日起床大于 1440，例如次日 01:00 为 1500、次日 07:30 为 1890；不得只存 0–1439 的钟面分钟后用整数大小猜跨日关系。恢复日期随特殊日事实保存，用于撤销恢复效果和排除学习样本，不另造一条会与用户特殊日冲突的同日记录。

类型至少区分：用户主动特殊日、排程提出的临时延长日。状态为 `draft/confirmed/revoked/expired`。草稿不影响排程；只有 `confirmed` 且日期匹配时进入 `DailySchedulingPolicy`。

### 8.2 临时延长日提出条件

系统只有在正常放置、有界重分配和修复仍不能满足需求后才可以提出临时延长日。候选不得跨过触发任务截止，不得突破用户绝对最低睡眠，不得与固定或保护日程重叠，也不得把次日起床推迟。

默认绝对最低睡眠为 6 小时，可由用户设置，但不能由学习系统修改。长期目标睡眠与绝对最低睡眠分开保存。

限制规则：

- 同一计划最多提出并采用 1 个临时延长日。
- 不允许连续两个本地日延长。
- 滚动 7 天最多允许 0、1 或 2 次，默认 2 次。
- 新增容量先分配给触发延长建议的任务；剩余容量才能参与普通排程。
- 候选最多显示 3 个，按新增可落地分钟、睡眠损失、截止改善和日期排序。
- 系统找不到满意候选时，用户可强制选择任一仍满足硬边界的日期和结束时间；硬边界不能被强制绕过。
- 用户拒绝某一输入哈希下的相同建议后，本次输入不再弹出；输入事实改变后才允许重新建议。

### 8.3 交互边界

计划预览只显示一张建议卡，不自动弹窗。用户点击后才打开候选选择；确认前不保存日例外、不改计划。确认时把特殊日事实、恢复效果、新计划版本、计划块和审计日志交给一个统一提交端口，并在同一个 SQLite 事务中应用。应用层禁止先写特殊日再调用计划仓储。取消或应用失败后所有相关表都保持原值。

### 8.4 固定起床与恢复

一次晚睡不能延后次日起床。确认特殊日时同时给出独立恢复选项：

- 次日创建一段恢复休息保护块；
- 次日晚间提前入睡；
- 不创建恢复块，但降低次日可移动任务负载。

每项单独预览和确认。用户可以不选恢复方案；系统只显示风险，不暗中改变作息。

“取消次日可移动任务”只移除次日计划块，任务回到待安排状态，保留剩余时长和原截止；以后只能在原截止前重新安排。不得删除或完成任务。

## 9. 学习偏好

### 9.1 当前缺陷必须一次处理

算法 19 的偏好链路虽有 26 条专项测试通过，仍存在单位混用、分钟差显示成百分比、无手动移动生产证据、无专注片段建议、领域证据全局应用、确认状态被刷新覆盖、清除后无法重启、特殊日排除不全、夜间桶错误、旧建议残留和偏好未直接进入 `ScheduleProblem` 等问题。算法 20 不允许沿用这些语义。

### 9.2 证据模型

每条证据保存：事件 ID、领域 ID、可选任务 ID、事件种类、本地开始/结束、观察本地日、计划分钟、实际专注分钟、完成分钟、暂停分钟、中断次数、是否完成、是否特殊日、来源版本和元数据。

事件至少包括：专注完成、专注中断、手动移动、建议接受、建议拒绝。没有领域的记录进入 `global` 样本，不得静默丢弃；但全局样本不能反推某个领域偏好。

时段桶按本地时间定义为：`morning 05:00–12:00`、`afternoon 12:00–18:00`、`evening 18:00–23:00`、`night 23:00–05:00`。跨桶会话按实际分钟拆分或归入占比最大的桶，规则必须唯一并有跨午夜测试。

特殊日、临时延长日和恢复日样本默认排除。用户可在证据详情里看到排除原因。

### 9.3 指标与门槛

时段偏好不能使用原始专注分钟直接比较。每次会话先计算限定在 `[0,1000]` 的整数效果分：完成比例、有效专注比例、计划偏差和中断惩罚均用固定整数公式；没有足够字段的旧证据标记为 `legacyInsufficientMetric`，不能与新分数混算。

建议门槛保持可审计：同一领域至少 20 条有效证据、覆盖至少 14 个本地活跃日、至少两个时段各 5 条；最佳时段相对次优时段的中位数差达到 150/1000，且自助法置信下界达到冻结阈值后才生成建议。具体统计实现不能用平台相关随机数；重采样序列使用固定种子和稳定排序。

专注片段建议使用实际连续有效专注长度分布，至少 20 条有效会话、14 个活跃日；建议值取 5 分钟粒度的稳健中位数，并夹在用户片段上下限内。它只调整新任务默认片段或对应领域软目标，不改任务总预计时长。

### 9.4 建议状态机

状态固定为 `suggested/edited/confirmed/rejected/disabled/superseded`。分析刷新遵循：

- 同一证据版本生成同一建议 ID。
- `confirmed/rejected/disabled` 不能被刷新降回 `suggested`。
- 用户编辑值保存为 `edited`，再次确认后才生效。
- 新证据使建议明显变化时，新建议引用旧建议并把旧建议标记 `superseded`。
- 已不满足门槛的未确认建议撤回；已确认偏好继续有效，直到用户撤销或新确认替代。
- “清除学习结果”清空确认规则和建议，但不等于永久关闭。学习总开关单独保存，用户可重新开启。

建议与确认规则使用现有 `preference_rules` 表作为唯一持久化事实源。`Settings` 只保存学习总开关、自动采用开关及一次性迁移标记，不再保存第二份规则 JSON。旧设置中的全局偏好首次迁移成功后写为 `subjectKey=global`、`source=legacy` 的规则；迁移必须幂等，不能双写或重复生成。

### 9.5 排程作用域

偏好按 `subjectKey` 保存。领域偏好只作用于该领域任务；全局偏好只作为无领域任务或缺少领域偏好时的回退。多个领域互不覆盖。

`ScheduleProblem` 必须携带不可变的 `PreferenceSnapshot`，按任务提供期望时段、软精力窗口和偏好片段。排程器不能从设置仓储读取，也不能把某个领域的高效时段改写成全局高精力窗口。

用户长期设置优先于学习偏好。确认偏好只影响下一次生成或明确重排；页面提供“立即重新生成计划”，不能静默移动当前计划。

### 9.6 进度与解释

学习偏好页面按领域显示：有效记录数/20、活跃日/14、各时段样本数、被排除数、预计还缺什么。未达门槛时不能只显示一句空状态。确认前显示证据范围、指标单位、作用领域和对下次计划的影响。

## 10. 结构化诊断与用户操作

`UnscheduledTask` 必须携带标题快照或通过稳定标题端口解析；预览不显示裸 UUID。失败原因至少区分：总容量不足、连续长度不足、最早开始限制、截止限制、允许星期限制、任务单日上限、全局日上限、固定占用、保护时间、睡眠、课程过渡、锁定块、休息规则、搜索预算耗尽、结构异常和输入失效。

每条原因包含需要分钟、合规容量、可落地容量、最长连续段、受限日期和主要阻塞来源。预览根据原因提供可执行入口，例如修改片段、修改截止、查看保护时间、选择临时延长日；不能用预览层按任务属性猜原因。

硬无解在应用前拦截。允许部分应用只针对可解释、用户明确授权的任务缺口；结构异常、搜索未决、过期输入、未兑现明确调整和校验失败一律零写入。

## 11. 安全、迁移与隐私

- 新增特殊日表需要 schema v11；升级前沿用现有预迁移备份，迁移只新增表和索引，不改写既有任务、日历、计划或证据行。
- 旧偏好证据保留但标记为旧指标，不能假装已满足新门槛。
- 旧已确认偏好迁移为全局软偏好并显示“来自旧版本”；用户确认保留或清除前不自动扩散到领域。
- 特殊日撤销采用状态变更，保留审计记录；用户执行数据清除时随其他个人数据一起删除。
- 普通日志不记录任务标题、备注、真实 UUID、睡眠详情或证据内容。诊断导出需用户主动触发并对 ID 做稳定脱敏。
- 不新增联网权限或第三方求解依赖。

## 12. 性能与确定性预算

目标机器上的七日窗口基准夹具必须满足：普通计划 p95 不超过 500ms，大型夹具（200 任务、300 基线块）p95 不超过 2s。确定性状态预算耗尽时返回 `searchBudgetExhausted` 和最佳合法方案；界面墙钟看门狗触发时取消计算、丢弃结果并允许重试，不能应用中间状态。具体性能阈值若因基线机器不同调整，必须记录机器、Flutter/Dart 版本和原始结果，不能只改断言。

相同规范化输入连续运行 100 次，提案 JSON、诊断顺序、扩展日候选和方案签名逐值相同。输入列表随机打乱后结果仍相同。

## 13. 发布门禁

算法版本从 19 升到 20 只能发生在最后一次门禁提交中。门禁要求：

- 新增和迁移测试全绿；从每个历史 schema 升级到 v11 后数据逐值保持。
- 排程单元、应用、页面和端到端测试全绿。
- 属性测试、确定性测试、黄金夹具和性能基准通过。
- 特殊日、临时延长日、学习偏好、块级延后和可见空闲五条真实工作流有自动化覆盖。
- Windows 新构建完成冒烟；旧安装包或未重建 EXE 不能作为验收证据。
- `flutter analyze` 无问题，格式检查零改动，工作树只包含计划内文件。
- 验收文档记录实际命令、退出码、测试数、构建哈希和未执行项；禁止把 `NOT RUN` 写成通过。
