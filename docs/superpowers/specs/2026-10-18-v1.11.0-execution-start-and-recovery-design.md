## 1. 用户目标与发布边界

用户反馈：当天原定的三项任务均未执行。安排时知道要做什么，也知道计划时间，到了时间却没有进入学习；错过开始时间后，后续安排缺少恢复入口，复盘也无法准确解释启动障碍。

本轮目标是帮助用户开始一段工作，并在错过安排后处理剩余工作。第一轮提供完整流程：

```text
已确认的一次安排
  → 今日页显示可开始卡片
  → 立即开始 / 先做5分钟 / 稍后提醒 / 调整安排
  → 实际开始、暂停和结束记录
  → 剩余工作同步
  → 必要时给出局部调整预览
  → 按原始承诺与实际记录复盘
```

一次个人经历用于发现问题，不作为“功能已改善拖延”的证据。本轮不承诺检测玩手机、推断注意力或保证任务完成。

发布约束：

- `1.10.0` 继续完成离线安装器、自更新落盘修复及其既定验收。本文件不得加入该版本的工作清单。
- `1.11.0` 在 `1.10.0` 收口后实施，复用届时稳定的任务、计时、通知、重排、备份和更新安全接口。
- 包身份、Publisher 保持兼容；新增记录自动迁移，不要求用户手动转换数据。
- 本轮包含可见新功能，按 `docs/release/version-policy.md` 属于 Minor。只有实际出现破坏兼容性的变更，才重新评估 Major。
- 本文件不修改 `pubspec.yaml`、版本守卫或发布台账。版本一致性在本轮发布准备时统一处理。

## 2. 已确认范围

| 范围 | 交付行为 |
| --- | --- |
| 轻量启动 | 从今日页直接开始或选择先做5分钟，不要求进入独立专注页面 |
| 延迟恢复 | 错过开始时间后仍可开始、补记、稍后提醒或安排剩余工作 |
| 实际记录 | 记录具体一次安排的实际开始、有效投入、暂停、结束与数据来源 |
| 局部调整 | 延迟影响后续安排时，复用现有引擎生成可解释预览 |
| 基础复盘 | 准时启动率、平均启动延迟、延迟恢复率，以及缺失记录数量 |
| 可选障碍记录 | 临时有事、任务太难、精力不足、忘记、其他；可以不填 |

本轮不包含手机监控、应用封锁、强制全屏、强制弹窗、积分惩罚、云端分析、自动改变作息、重写排程求解器或全新复盘图表系统。后续是否有效，以实际记录和用户反馈判断。

## 3. 现有能力与真实缺口

以下结论来自编写时对工作树的读取，实施前需要基于 `1.10.0` 最终提交重新核对。

| 位置 | 已存在能力 | 本轮需要补齐 |
| --- | --- | --- |
| `lib/features/today/today_page.dart` | 当前安排动作、开始专注、延后本次、跳过本次等入口 | 直接启动、5分钟体验、未记录开始和恢复状态 |
| `lib/application/focus_service.dart` | 开始、暂停、继续、结束、补录、崩溃后确认 | 会话与具体安排关联、直接使用的启动入口、可靠进度同步 |
| `lib/data/repositories/drift_focus_entry_store.dart` | `time_entries` 持久化计时数据 | 与执行实例的关联、记录来源与更正；读取旧数据保持兼容 |
| `lib/application/pending_moves.dart` | 块级延后，分钟/小时/天，按原计划开始时间换算 | 新增“从点击时刻起”的提醒/恢复意图，不能改变旧延后语义 |
| `lib/application/pending_skips.dart` | 跳过一个块，任务继续参与重排 | 新流程使用提案作用域的意图；取消预览必须取消本次草案 |
| `lib/application/planning_service.dart`、`plan_application_service.dart` | 生成提案、输入校验、调整兑现检查、应用计划 | 携带执行实例来源及实际投入版本，防止过期提案覆盖新进度 |
| `lib/data/repositories/drift_plan_repository.dart` | 计划版本、历史块、撤销后创建新版本 | 跨计划版本的执行实例关联，不能拿块 ID 当永久身份 |
| `lib/application/notification_service.dart` | 通知总开关、类别、免打扰及对账 | 执行提醒的持久去重和过期抑制，避免重启后补发一堆通知 |
| `lib/application/task_service.dart` | 修正剩余时长、按累计投入重算 | 新执行入口自动同步进度且不重复扣减，不覆盖人工修正 |
| `lib/main.dart` | 计时结束回调中记录证据并触发重排信号 | 关键业务写入不能依赖可吞异常的附加回调 |

两个具体注意点：

1. 现有 `FocusSession` 有 `taskId`，没有永久执行实例身份。同一任务一天两段、跨版本重排和拆分后，单靠 `taskId` 不能确定实际启动属于哪段。
2. 当前 `onFinished` 装配会发重排信号，不能因此推定普通任务剩余分钟已经同步。任务详情里的“按专注记录重算”是另一路显式操作，不能当作自动同步证据。

## 4. 方案选择与组件分工

| 方案 | 收益 | 代价与取舍 |
| --- | --- | --- |
| 只增强提醒 | 开发范围小 | 无法可靠记录实际开始，错过后也没有剩余工作恢复，不能满足本轮目标 |
| 在现有能力上增加执行记录与协调层 | 直接启动、恢复、统计使用同一份事实 | 需要持久身份、事务、迁移和跨版本关联；采用此方案 |
| 重新建设专注系统和排程引擎 | 可以重新定义所有交互 | 扩大范围、重复计时与排程逻辑，本轮不采用 |

采用方案中的责任边界：

- `ExecutionService` 接收开始、结束、补记、稍后提醒和恢复操作，负责幂等、事务及状态检查。
- 执行仓储保存安排实例、事件、会话关联和进度检查点。业务事实保存在 SQLite 中。
- `FocusService` 继续负责单调计时与暂停，不另做一套计时器。
- 恢复协调器把执行意图翻译为现有排程输入，调用现有生成及应用服务。
- 通知协调器消费执行状态，统一遵守通知设置。不单独增加绕过设置的后台弹窗路径。
- 今日页显示操作与事实；统计层读取执行事实，不自行猜测完成情况。
- 学习偏好模块只消费符合原有证据规则的记录。选择了“精力不足”不自动修改精力或作息规则。

## 5. 核心数据与身份规则

### 5.1 执行实例

`executionOccurrenceId` 表示用户承诺执行的一次安排，与任务 ID、计时会话 ID、具体版本的块 ID 分开。

至少保存：

| 字段 | 语义 |
| --- | --- |
| `id`、`taskId` | 稳定执行实例身份及所属任务 |
| `originPlanVersionId`、`originBlockId` | 首次关联的已确认计划来源 |
| `baselineStartUtc`、`baselineEndUtc` | 该实例原始承诺窗口，创建后不覆盖 |
| `baselineTimeZoneId`、`baselineLocalDate` | 承诺时区及报告归属日，不能由当前时区反推历史 |
| `baselinePlannedDuration` | 原始时长，用于展示对比，不是再次扣减的工作量 |
| `currentPlanVersionId` | 当前恢复安排的版本，可为空 |
| `firstStartEvidenceId` | 有效首次启动证据；更正通过事件更新投影 |
| `withdrawalReason`、`withdrawnAtUtc` | 提前取消、提前改期或明确取消任务的事实 |
| `createdAtUtc`、`revision` | 排序、并发校验与审计 |

还需要版本块关联。一个实例在恢复拆分后可对应多个块，一个块引用的是具体计划版本中的身份。关联必须由计划应用时显式提交，不用标题相似、最近钟点或任务 ID 模糊匹配。

### 5.2 创建、移动、拆分、合并与撤销

1. 生成预览不创建正式执行实例。只有用户确认应用计划后才创建或更新关联。
2. 同一安排在新版本中未变化时沿用执行实例。不会因复制成新块 ID 而重复统计。
3. 用户在原开始时间之前确认改期或取消，原实例记为提前撤回。新时间形成新实例；旧实例保留但不进入启动率分母。报告单列提前调整数量，禁止悄悄删除。
4. 达到原开始时间之后的移动是恢复，沿用原实例与基准。即使下一个合法时段是明天，也不得把原始延迟清零。
5. 到点后拆成多个恢复片段仍只有一个启动率分母。首次实际启动只取其中最早的有效启动证据。
6. 同一任务不同原始安排不得通过合并伪造多次启动。一段计时只归属一个主执行实例。第一轮恢复操作不合并不同执行实例；普通重排若需要合并，必须提供明确的来源分配，否则不得自动应用该恢复提案。
7. 撤销计划只恢复安排，不撤销已经发生的实际投入。恢复旧计划版本时重建关联，不能复活已消费的工作量。
8. 同一任务已经完成或删除时，旧卡片操作必须重新校验。到点后删除或取消不追溯抹掉此前承诺，统计保留相应原因。

### 5.3 执行事件、会话来源与更正

事件至少包含实例 ID、操作 ID、事件类型、发生时间、写入时间、来源、版本、可选原因与备注。

来源区分实时计时、人工补记、崩溃恢复确认。补记不能冒充实时测量；历史记录无法确定归属时保留为“未关联”，不伪造实例。

更正使用新事件引用被更正记录，查询时只采用最新有效版本。重复提交相同操作 ID 返回原结果；同一会话不能重复计入任务进度或周期分钟。

## 6. 状态与时间判定

计时阶段与界面状态分开。界面状态来自持久事实和当前时间，不用每分钟写一条“状态变化”。

| 条件 | 今日页显示 | 可用动作 |
| --- | --- | --- |
| 原计划尚未开始，无执行记录 | 待开始 | 提前开始、调整、详情 |
| 已到开始时间，无执行记录 | 尚未记录开始 | 立即开始、先做5分钟、稍后提醒、调整、补记 |
| 实时会话运行中 | 执行中 | 暂停、结束本次 |
| 实时会话暂停中 | 已暂停 | 继续、结束本次 |
| 已有有效投入，剩余工作尚未安排 | 已记录投入，剩余待安排 | 继续、安排剩余、详情 |
| 结束一个会话，任务仍有剩余 | 本次已结束 | 安排剩余、继续工作 |
| 任务已明确完成 | 已完成 | 查看记录、更正记录 |
| 执行实例被明确提前撤回 | 提前调整或取消 | 查看历史 |

“逾期”“超过启动容差”“恢复观察期结束”是计算标签，不等于已经确认未学习。

时间规则：

- 事件保存 UTC，历史报告按实例的承诺时区和归属日展示。
- 第一轮启动容差固定为5分钟，界面解释口径；容差不触发强制操作。
- 恢复统计观察期固定为原始开始后24小时，按经过时长计算，与本地一天的长度分开。
- “稍后10分钟”按经过时长；原有“延后1天”继续按本地日历日规则。
- 运行中有效投入使用单调计时，暂停、系统休眠和无法证实的停机时间不得直接当有效学习。
- 关机、崩溃、重启后的未知时段需要用户确认，计时服务已有的崩溃恢复边界继续生效。

## 7. 今日页启动与5分钟体验

### 7.1 默认交互

任务到点后，今日页显示非模态执行卡片，不抢焦点，不强制打开窗口。主操作为“开始”和“先做5分钟”；次操作为“10分钟后提醒”“调整安排”，更多操作中提供“补记已做”。

示例：

```text
蓝桥杯竞赛课
原计划 13:40–14:25 · 尚未记录开始
可以先做5分钟，之后再决定是否继续。

[开始] [先做5分钟]
[10分钟后提醒] [调整安排]
```

用户此前明确不希望依赖专注功能。新入口直接在今日页完成开始操作，显示轻量执行条，独立计时页面作为可选入口。首轮不要求先填写原因、目标、备注或表单。

### 7.2 开始前检查

- 操作针对的任务仍存在且可执行，计划版本或实例没有失效。
- 没有另一段正在运行或等待恢复确认的会话。若已有同一实例会话，返回该会话；若属于另一实例，引导处理现有会话，不隐式切换。
- 当前片段满足硬约束。未来的课程、保护时间和锁定块会决定可执行片段的边界。
- 此刻不满足计划硬约束时，计划启动操作说明占用和下一个可用时段，不假称安排合法。用户仍可通过独立的“只记录实际”入口记录真实投入，即使实际发生在保护时间中；该记录标明偏离计划，不覆盖或放宽保护规则。事实记录与合法排程分开校验。

### 7.3 先做5分钟

1. 点击只创建实际开始记录并开启计时，不先扣5分钟，不改变预计时长、截止时间或周期目标。
2. 目标为5分钟的有效投入。暂停时间不计入目标。
3. 有效投入达到5分钟后，执行条显示“已做5分钟”，提供继续、休息、结束本次。计时持续运行，只有用户明确暂停或结束才停止；提示不重复弹出。
4. 如先遇到硬边界，按下节停止规则暂停，不把5分钟目标用作跨越保护时间的许可。
5. 可用连续时间不足5分钟时，不能先显示已开始再报错。卡片说明实际可用时间，提供“做这几分钟”与“换个时间”。前者是用户明确选择的实际短会话，不是引擎生成违反最短块长度的计划。
6. 剩余工作少于5分钟时显示“先做剩余时间”，不夸大需要量。低于一分钟的真实投入仍保存，进度按累计时长换算。

### 7.4 暂停、结束与硬边界

暂停立即生效，再允许可选记录原因。不能让原因表单使暂停时刻晚于真实操作。

遇到课程、保护时间或锁定安排开始时，应用内计时自动暂停并记录 `hardBoundaryReached`，用户实际行为不可被软件强制阻止。允许事后更正记录，但更正事实不修改保护规则。

自动暂停是应用运行时的目标行为。后台调度延迟、休眠或进程崩溃后，按已保存活动段与已知边界恢复，超过边界的未知时间不得自动入账；不能宣称已在进程不运行时准确检测用户行为。用户确实继续工作时，可以明确选择只记录实际或事后补记，偏离事实不会变成放宽授权。

遇到普通可移动任务的开始时间时，不自动打断当前执行。执行条显示冲突，并允许结束本次或继续后调整。已经运行的会话在重排输入中作为当前事实保护，不能被算法移回过去。

结束本次只结束这次会话，不能直接等价为完成任务。普通任务预计投入已耗尽时显示“预计时长已投入”，由用户确认完成或修正剩余。周期目标继续按既有有效分钟结算规则计算达标。

## 8. 稍后提醒、移动安排与跳过

| 操作 | 时间参照 | 写入结果 | 不应发生的副作用 |
| --- | --- | --- | --- |
| 10分钟后提醒 | 点击时刻 + 10分钟 | 持久化提醒意图 | 不改计划，不扣分钟，不重置延迟 |
| 现有延后本次 | 该块原计划开始 + 用户选择时长 | 生成块级延后预览 | 不改变旧接口时间参照 |
| 从现在起安排剩余 | 点击时刻为最早开始下界 | 生成局部恢复预览 | 不把下界当精确锁定点 |
| 跳过本次安排 | 当前实例/块 | 确认后移除本次占用，任务可继续重排 | 不取消任务、不算完成 |
| 今天不再安排该任务 | 所在本地日结束之前 | 确认一次性恢复限制 | 不永久修改最早开始属性或截止时间 |

“今天不再安排该任务”在第一轮作为调整面板中的显式选项，只影响尚未执行的剩余工作。同一任务已记录的实际投入、其他日期安排和未来周期不受影响。用户确认后，该一次性限制保存到事项时区次日00:00的精确 UTC 时刻；页面退出和应用重启不清除，过期后自动失效。取消预览不保存限制。

提醒关闭时，“10分钟后提醒”入口显示不可用及原因，提供打开提醒设置的入口；不得提示“已设置”却不发送，也不得自行开启总开关。

例如原计划13:40，用户14:00操作：稍后10分钟对应14:10；原有块级延后10分钟仍以13:40为参照。新面板使用前者语义，并用不同操作类型传入应用层。

## 9. 延迟后的局部恢复规则

### 9.1 进入条件与方案顺序

未记录开始本身不触发自动大范围重排。软件可以计算建议，用户通过“调整安排”或“安排剩余”进入预览。

按以下顺序尝试，并展示影响：

1. 当前时刻到原计划结束的空闲仍够剩余工作，保留其他安排。
2. 原结束后存在相邻合法空闲，且不突破边界时，给出延长本次的方案。
3. 寻找当天后续合法空闲，优先避免移动其他块。
4. 必须移动其他可移动任务时，复用既有优先级和局部修复规则，列出每个受影响块。
5. 当天放不下时，在原截止时间和周期边界内搜索后续日期，保留工作日/周末负载规则。
6. 无法完整安排时显示可安排部分、未安排分钟及结构化原因。无效方案不得应用；部分有效方案仍需明确授权。

“缩短本次”表示只排一部分，未安排工作继续存在，不下调任务总量。用户要减少工作量时，必须另行显式修正剩余。

### 9.2 排程不变量

- 保留既有硬约束和优先级；5分钟启动入口不产生新的高于所有任务的排程优先级。
- 固定日程、课程、保护时间、锁定块、不可拆分约束、截止时间与周期周界继续生效。
- 晚睡或自定义延长日继续走算法20的既有选择和授权流程。不能因为延迟自动推迟睡眠，更不能顺带推迟次日起床。
- 不能静默缩小剩余工作、放宽每日上限、删除冲突安排或推迟截止。
- 未确认预览不写计划。新流程的恢复/跳过草案只属于当前提案，取消后不能污染下一次普通生成。
- 确认时重验计划版本、任务进度版本、会话状态与当前时刻。用户看预览期间新增投入或修改任务后，旧提案必须失效重算。
- 执行中的有效投入与预留占用要分开。尚未结束的计时不能既作为已完成分钟，又作为完整待排工作重复占用。
- 当前事实导致无法继续沿用旧块时，预览明确列出旧占用如何释放、剩余分钟如何重新安排；历史事实不会被重排覆盖。

### 9.3 本次剩余与任务总剩余

恢复目标是所选执行实例的未做份额，并受任务总剩余限制。不能把整个任务所有剩余都塞进当前片段。

例如任务原需90分钟，已有两次各45分钟的安排。本次做5分钟后，任务剩余85分钟，本次恢复40分钟，另一次安排仍为45分钟；不能恢复85分钟并继续保留另一段45分钟。

每次提案同时校验任务级分钟守恒和实例级份额。未安排份额只计一次，计划预留不算实际投入。超额投入使其他尚未执行片段需要缩减时，显示局部调整；遇到锁定块则报明确冲突，不能静默删块或制造负剩余。

短会话不改变任务拆分模式。不可拆分任务允许用户真实做5分钟并记录，但系统不能因此把剩余工作自动拆成多段，也不能跳过最短连续长度约束来生成新计划。

## 10. 实际投入与剩余工作同步

### 10.1 唯一计量来源

实际投入来自有效会话的累计活动时长。实时会话、补记和恢复确认使用同一入账路径，每条会话只计一次。首次点击开始表示用户报告开始执行，不代表软件能够证明注意力；零投入且被用户撤销的误触会话不构成有效启动证据。

原始精度保存到既有计时支持的微秒或等价整数精度。换算分钟时先累计再取整，不能把两段各30秒都丢为0。不得把时间区间的全长当活动时长。

### 10.2 普通任务的进度检查点

为了保留人工修正，新增持久进度检查点，包含 `anchorRemainingMicros`、`anchorSequence`、创建时刻、原因及版本。每条投入事实保存不可变的首次入账序号 `firstAcceptedSequence`，更正保留该序号。

计算规则：

```text
eligibleCredits = 首次入账序号大于 anchorSequence，
                  且明确计入当前剩余的全部有效投入记录
remainingMicros = max(0, anchorRemainingMicros - sum(eligibleCredits.durationMicros))
remainingMinutesForScheduling = ceil(remainingMicros / 60,000,000)
```

时间量统一使用整数微秒，序号由数据库写事务分配。调度使用向上取整后的分钟，展示可同时保留秒数，不能把尚余30秒截成0而漏排。首次接入以当前真实剩余建立检查点，已有有效记录均落在序号边界之前，不再扣一次。

用户显式修正剩余时，先暂停并结算同任务的运行会话，再在一个事务中建立新的序号边界。修正前已入账记录的更正只更新实际统计，不自动改写这个较新的人工剩余；需要修正剩余时由用户另行确认。修正后新增记录的更正或撤销会重算当前剩余。

晚补记的发生时间早于检查点时，询问“这段投入是否已包含在上次剩余修正中”。选择已包含则仍保存实际记录，但不再扣当前剩余；选择未包含才计入。该选择属于记录版本，更正后可追溯。不能只靠发生时间或总累计分钟差猜测。

预计时长调整不会静默重设人工剩余。若用户同时要求修改剩余，沿用显式修正路径。

新流程结束本次后的自动同步只更新进度，不调用“剩余为0即自动完成普通任务”的旧组合入口。已有“按记录重算”入口接入同一计算来源；其完成确认在界面中明确，不允许两套入口采用不同累计口径。

### 10.3 周期目标

周期目标仍使用周期仓储的有效分钟账本。会话分钟不得先写普通任务进度，再额外补一次周期完成分钟。

跨周实际投入按事项时区的真实活动区间切分到对应周；不能只按会话结束时间把全部分钟算到新周。分配以活动段为来源，合计必须等于原有效投入；不能向两周各写整段。每周先累计微秒再取整为完成分钟，余秒保留在该周，不跨周搬运以凑整。旧周期截止和结转规则继续适用，新周不能自动替旧周刷达标。

旧周期补记改变实际完成量时，通过既有周期结转服务向后重算依赖链，并保留原因。已经确认的未来计划只标为进度变化待调整，不能直接静默重排。没有明确周归属的投入先保存为待分配事实，不计入达标，也不允许伪造新周期任务来吸收未知分钟。

崩溃恢复只有总分钟而没有可核实跨周活动区间时，要求用户分配到相应日期；未确认的分配不参与达标结算。

## 11. 事务、幂等与异常恢复

以下属于关键业务事实，必须事务提交，不能只放进 `FocusService.onFinished` 这类允许吞异常的附加回调：

- 开始：创建会话、关联执行实例、记录开始事件。
- 结束或补记：保存有效记录、更新进度检查点的投影或周期账本、记录结束事件。
- 计划应用：写计划版本、记录块来源关联和恢复意图兑现结果。

学习偏好证据、通知对账与统计缓存更新在关键事务之后执行。失败记为可重试附加操作，不能撤销已保存的真实执行记录，也不能重复扣减进度。

要求：

1. 同一操作 ID 只提交一次；重复点击开始或结束返回相同结果。
2. 一次只允许一个全局有效实时会话。并发入口、通知点击与独立计时页也受同一仓储约束。
3. 暂停/结束先校验会话版本，不能把“结束后到达的暂停请求”写回运行状态。
4. 崩溃后未确认的会话不直接结算未知时长。重启不假定停机时间都在学习。
5. 提案失效不会删除实际执行记录。用户可以保留记录后重新安排。
6. 数据库或磁盘写入失败时明确显示未保存，不显示“已开始”或“已完成”假成功。
7. 系统时钟回拨或跳跃时标注受影响记录；无法确定的启动延迟不进入精确均值，单列数量。
8. 版本更新沿用现有业务事务阻塞和未保存编辑机制。运行中的会话需先暂停并持久化；不能在无记录情况下直接安装退出。

## 12. 补记与障碍记录

### 12.1 补记

允许用户选择实际开始、结束、活动时长和对应安排。活动时长必须大于0，且不能超过开始到结束的经过时长。未来结束时间拒绝保存。

同一时间段已有其他有效工作记录时提示重叠，不自动双计；用户必须更正或确认拆分。补记有记录 ID 和来源，重复保存是更新或更正，不新建一份副本。

只有时长没有准确开始时刻的历史数据仍可用于投入汇总，不进入启动延迟计算。补记来源在复盘中可见，用户可以选择查看仅实时记录的指标。

### 12.2 执行障碍

延后、结束或复盘时允许一次选择原因，默认不选。可选值为临时有事、任务太难、精力不足、忘记、其他。原因可改，可清除，不影响开始按钮。

不选择原因显示未记录。不得根据晚启动、前台应用、空闲时间或重复延后自动推断“玩手机”。中断原因与未启动原因分开统计，避免把同一条事实算成两次障碍。

## 13. 提醒策略

- 今日页状态卡持续可见，用户主动打开软件即可操作；没有系统通知也可以完整使用。
- 系统通知复用总开关、任务开始类别和免打扰。不另建执行提醒特权类别。
- 每个执行实例只允许一个当前提醒意图，保存 `occurrenceId`、提醒修订号、目标时间、已处理状态和实际派发结果。
- 稍后提醒替换上一次尚未处理的提醒，不累积多个通知。开始、提前取消或任务完成后撤销旧提醒。
- 关闭通知后取消待发项；已经在队列里的点击回调也要重新校验状态，不得启动已完成任务。
- 同一实例重复对账、重启、切页面或重排，不重新生成已经处理的提醒。
- 免打扰结束或电脑重新开机时，不逐条补发过期执行通知；只在应用内汇总待处理安排。
- Windows 未提供可靠的“已看到”回执时，不声称用户已经看过提醒。调用调度成功仅表示排入系统，界面和日志必须区分。
- 通知点击仅导航到对应执行卡片。第一轮不在系统通知内提供未经同等校验的后台写入捷径。

## 14. 三项指标与记录完整性

### 14.1 公共集合

每次查询固定一个 `asOfUtc`，所有指标使用同一时刻和同一过滤条件。

统计对象是执行实例，不是任务条数、计时会话数或恢复后片段数。排除固定日程、课程、保护时间、未确认预览、提前撤回及升级前无法建立基准的历史记录。

旧安排到点后取消、跳过或改期仍保留在当时承诺集合。没有记录只能标为“未记录启动”，不能解释成确定没有做。

报告按原承诺日归属。重排、补记、更正会更新对应原日期的统计，不能把今天的迟到转移到明天隐藏。显示来源分布、缺失记录数量、提前调整数量及统计截止时刻。

### 14.2 准时启动率

设原始开始为 `S`，容差为5分钟，有效首次启动为 `A`。

- 分母为 `asOfUtc > S + 5分钟` 的有效实例，避免任务刚到点尚在容差内就先记失败。
- 分子为其中存在 `A <= S + 5分钟` 的实例。提前开始计准时。
- 无启动记录的实例不进入分子，另列数量。名称和说明明确为“按已记录启动计算”。
- 分母为0显示暂无数据，不显示0%或100%。

### 14.3 平均启动延迟

使用同一有效集合中有可信开始时刻的实例，逐项计算 `max(0, A - S)` 后求平均。

没有开始时刻的记录不填0，也不取当前时刻作为实际开始；必须同时显示“已记录启动 n 次，未记录 m 次”。时钟异常导致不可确定的记录另列，不能混进平均数。

### 14.4 延迟任务恢复率

观察终点为 `S + 24小时`。

- 只统计 `asOfUtc >= S + 24小时` 的已结束观察窗，未结束的显示待观察数量。
- 分母为该集合中未在5分钟容差内记录启动的实例。
- 分子为其中存在 `S + 5分钟 < A <= S + 24小时` 的实例。
- 超过24小时才开始仍记录真实投入，但不算此次观察窗内恢复，单列为更晚启动。
- 分母中含“未记录启动”的实例，因此说明这是记录到的恢复比例，不能宣称这些用户确定未执行。
- 同一实例迟到后做5分钟、暂停、再继续，只算恢复一次。只移动计划或点击提醒不算恢复。

### 14.5 试用验证

发布前证明行为与计算正确；是否改善拖延通过至少两周实际使用观察，不设没有依据的改善百分比门槛。

区分新增工具带来的记录增加和实际启动改善。比较期同时展示样本量、记录覆盖情况和补记占比。样本不足时仅展示事实，不宣称因果效果。

## 15. 数据迁移、备份与隐私

- 执行实例、块关联、事件、会话归属、进度检查点和提醒意图均持久化。精确表结构在实施计划中定义，不把重要事实仅保存在页面内存。
- 编写时数据库 schema 为10。实施时从届时最新 schema 做一次增量迁移，不提前占用可能与 `1.10.0` 冲突的编号。
- 旧计时记录可读取，不强行关联原始安排；旧计划不回填成已经错过的任务。首次启用只接入启用时刻之后尚未开始的当前安排，过去安排保持历史数据。
- 已有未结束会话先走既有恢复确认，不能因启用新功能创建第二段会话。
- 新版完整备份包含新增事实。恢复后不能重复扣减进度、重发提醒或改变既有任务状态。
- 数据迁移事务失败保留旧库；恢复应用备份遵守现有版本兼容校验。
- 数据本地保存，普通诊断日志不写任务标题、原因备注或完整个人目录。不增加分析上传。
- 用户删除数据时同步删除相关执行事实、通知意图和缓存。受影响统计重新计算，不能保留悬空关联。

## 18. 完成与交付口径

发布前必须满足：

1. 从今日页一次操作可以进入执行，不要求先使用独立专注页面。

3. 用户关闭通知后不再受到该功能的系统提醒；过期提醒不会反复出现。

7. 发布说明区分已完成行为与后续效果观察，不宣称已经解决拖延。
