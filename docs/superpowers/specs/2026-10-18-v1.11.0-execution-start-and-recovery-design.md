## 1. 用户目标与发布边界

用户反馈：当天原定的三项任务均未执行。安排时知道要做什么，也知道计划时间，到了时间却没有进入学习；错过开始时间后，后续安排缺少恢复入口，复盘也无法准确解释启动障碍。

本轮目标是帮助用户开始一段工作，并在错过安排后处理剩余工作。第一轮提供完整流程：

```text
已确认的一次安排
  → 今日页显示可开始卡片
  → 立即开始 / 先做5分钟 / 稍后提醒 / 调整安排
  → 实际开始、暂停和结束记录
  → 剩余工作同步
  → 必要时给出局部调整预览
  → 按原始承诺与实际记录复盘
```

一次个人经历用于发现问题，不作为“功能已改善拖延”的证据。本轮不承诺检测玩手机、推断注意力或保证任务完成。

发布约束：

- `1.10.x` 继续完成离线安装器、自更新落盘修复及其既定验收。本文件不得把这些修复并入 `1.11.0` 功能工作包，也不得用 `1.11.0` 绕过未完成的 `1.10.x` 发布门禁。
- `1.11.0` 只从最后一个通过发布门禁的 `1.10.x` 提交开始实施。2026-10-19 的仓库候选为 `1.10.2+51`，但若它未通过真实发布验收，不能把“候选”写成“稳定基线”。
- 包身份、Publisher 保持兼容；新增记录自动迁移，不要求用户手动转换数据。
- 本轮包含可见新功能，按 `docs/release/version-policy.md` 属于 Minor。只有实际出现破坏兼容性的变更，才重新评估 Major。
- 本文件不修改 `pubspec.yaml`、版本守卫或发布台账。版本一致性在本轮发布准备时统一处理。

## 2. 已确认范围

| 范围 | 交付行为 |
| --- | --- |
| 轻量启动 | 从今日页直接开始或选择先做5分钟，不要求进入独立专注页面 |
| 延迟恢复 | 错过开始时间后仍可开始、补记、稍后提醒或安排剩余工作 |
| 实际记录 | 记录具体一次安排的实际开始、有效投入、暂停、结束与数据来源 |

| 基础复盘 | 准时启动率、平均启动延迟、延迟恢复率，以及缺失记录数量 |
| 可选障碍记录 | 临时有事、任务太难、精力不足、忘记、其他；可以不填 |

本轮不包含手机监控、应用封锁、强制全屏、强制弹窗、积分惩罚、云端分析、自动改变作息、重写排程求解器或全新复盘图表系统。后续是否有效，以实际记录和用户反馈判断。

## 3. 现有能力与真实缺口

以下结论来自编写与2026-10-19复核时对工作树的读取，实施前需要基于 WP0 确认的最终 `1.10.x` 提交重新核对。

| 位置 | 已存在能力 | 本轮需要补齐 |
| --- | --- | --- |
| `lib/features/today/today_page.dart` | 当前安排动作、开始专注、延后本次、跳过本次等入口 | 直接启动、5分钟体验、未记录开始和恢复状态 |
| `lib/application/focus_service.dart` | 开始、暂停、继续、结束、补录、崩溃后确认 | 会话与具体安排关联、直接使用的启动入口、可靠进度同步 |
| `lib/data/repositories/drift_focus_entry_store.dart` | `time_entries` 持久化计时数据 | 与执行实例的关联、记录来源与更正；读取旧数据保持兼容 |
| `lib/application/pending_moves.dart` | 块级延后，分钟/小时/天，按原计划开始时间换算 | 新增“从点击时刻起”的提醒/恢复意图，不能改变旧延后语义 |
| `lib/application/pending_skips.dart` | 跳过一个块，任务继续参与重排 | 新流程使用提案作用域的意图；取消预览必须取消本次草案 |
| `lib/application/planning_service.dart`、`plan_application_service.dart` | 生成提案、输入校验、调整兑现检查、应用计划 | 携带执行实例来源及实际投入版本，防止过期提案覆盖新进度 |
| `lib/data/repositories/drift_plan_repository.dart` | 计划版本、历史块、撤销后创建新版本 | 跨计划版本的执行实例关联，不能拿块 ID 当永久身份 |
| `lib/application/notification_service.dart` | 通知总开关、类别、免打扰及对账 | 执行提醒的持久去重和过期抑制，避免重启后补发一堆通知 |
| `lib/application/task_service.dart` | 修正剩余时长、按累计投入重算 | 新执行入口自动同步进度且不重复扣减，不覆盖人工修正 |
| `lib/main.dart` | 计时结束回调中记录证据并触发重排信号 | 关键业务写入不能依赖可吞异常的附加回调 |

两个具体注意点：

1. 现有 `FocusSession` 有 `taskId`，没有永久执行实例身份。同一任务一天两段、跨版本重排和拆分后，单靠 `taskId` 不能确定实际启动属于哪段。
2. 当前 `onFinished` 装配会发重排信号，不能因此推定普通任务剩余分钟已经同步。任务详情里的“按专注记录重算”是另一路显式操作，不能当作自动同步证据。

## 4. 方案选择与组件分工

| 方案 | 收益 | 代价与取舍 |
| --- | --- | --- |
| 只增强提醒 | 开发范围小 | 无法可靠记录实际开始，错过后也没有剩余工作恢复，不能满足本轮目标 |
| 在现有能力上增加执行记录与协调层 | 直接启动、恢复、统计使用同一份事实 | 需要持久身份、事务、迁移和跨版本关联；采用此方案 |
| 重新建设专注系统和排程引擎 | 可以重新定义所有交互 | 扩大范围、重复计时与排程逻辑，本轮不采用 |

采用方案中的责任边界：

- `ExecutionService` 接收开始、结束、补记、稍后提醒和恢复操作，负责幂等、事务及状态检查。
- 执行仓储保存安排实例、事件、会话关联和进度检查点。业务事实保存在 SQLite 中。
- `FocusService` 继续负责单调计时与暂停，不另做一套计时器。
- 恢复协调器把执行意图翻译为现有排程输入，调用现有生成及应用服务。
- 通知协调器消费执行状态，统一遵守通知设置。不单独增加绕过设置的后台弹窗路径。
- 今日页显示操作与事实；统计层读取执行事实，不自行猜测完成情况。
- 学习偏好模块只消费符合原有证据规则的记录。选择了“精力不足”不自动修改精力或作息规则。

## 5. 核心数据与身份规则

### 5.1 执行实例

`executionOccurrenceId` 表示用户承诺执行的一次安排，与任务 ID、计时会话 ID、具体版本的块 ID 分开。

至少保存：

| 字段 | 语义 |
| --- | --- |
| `id`、`taskId` | 稳定执行实例身份及所属任务；普通删除转匿名墓碑后 `taskId` 可空，不能借此重新绑定到另一任务 |
| `originPlanVersionId`、`originBlockId` | 首次关联的已确认计划来源 |
| `baselineStartUtc`、`baselineEndUtc` | 该实例原始承诺窗口，创建后不覆盖 |
| `baselineTimeZoneId`、`baselineLocalDate` | 承诺时区及报告归属日，不能由当前时区反推历史 |
| `baselinePlannedDuration` | 原始时长，用于展示对比，不是再次扣减的工作量 |
| `currentPlanVersionId` | 当前恢复安排的版本，可为空 |
| `allocatedMicros`、`remainingAllocationMicros` | 该实例最初承担的精确工作量及尚未执行份额；均为非负整数微秒，后者不能超过前者 |
| `firstStartEvidenceId` | 有效首次启动证据；更正通过事件更新投影 |
| `withdrawalReason`、`withdrawnAtUtc` | 提前取消、提前改期或明确取消任务的事实 |
| `lifecycleState`、`privacyState` | 生命周期为 `planned`、`started`、`finished`、`withdrawn` 之一；隐私状态为 `linked` 或 `anonymized`，两者正交，合法转换见 §19.6 |
| `createdAtUtc`、`revision` | 排序、并发校验与审计；每次影响投影的提交使 `revision` 加1 |

还需要版本块关联。一个实例在恢复拆分后可对应多个块，一个块引用的是具体计划版本中的身份。关联必须由计划应用时显式提交，不用标题相似、最近钟点或任务 ID 模糊匹配。

### 5.2 创建、移动、拆分、合并与撤销

1. 生成预览不创建正式执行实例。只有用户确认应用计划后才创建或更新关联。
2. 同一安排在新版本中未变化时沿用执行实例。不会因复制成新块 ID 而重复统计。
3. 用户在原开始时间之前、且尚未发生实际执行时确认改期或取消，原实例记为提前撤回。新时间形成新实例；旧实例保留但不进入启动率分母。报告单列提前调整数量，禁止悄悄删除。已提前执行的实例保留实际启动，不得按提前取消豁免。
4. 达到原开始时间之后的移动是恢复，沿用原实例与基准。即使下一个合法时段是明天，也不得把原始延迟清零。
5. 到点后拆成多个恢复片段仍只有一个启动率分母。首次实际启动只取其中最早的有效启动证据。
6. 同一任务不同原始安排不得通过合并伪造多次启动。一段计时只归属一个主执行实例。第一轮恢复操作不合并不同执行实例；普通重排若需要合并，必须提供明确的来源分配，否则不得自动应用该恢复提案。
7. 撤销计划只恢复安排，不撤销已经发生的实际投入。恢复旧计划版本时重建关联，不能复活已消费的工作量。
8. 同一任务已经完成或删除时，旧卡片操作必须重新校验。到点后删除或取消不追溯抹掉此前承诺，统计保留相应原因。

实例份额按精确微秒守恒：`已有效入账 + 当前未完成份额 + 已明确减少的份额 = 原始分配份额`。预计时长调整、恢复拆分和人工剩余修正会产生可审计事件，不能直接覆盖旧值后失去差额来源。计划块只保存预留，不属于已投入；同一微秒不能同时算作两个实例的实际投入。

### 5.3 执行事件、会话来源与更正

事件至少包含实例 ID、操作 ID、事件类型、发生时间、写入时间、来源、版本、可选原因与备注。

来源区分实时计时、人工补记、崩溃恢复确认。补记不能冒充实时测量；历史记录无法确定归属时保留为“未关联”，不伪造实例。

更正使用新事件引用被更正记录，查询时只采用最新有效版本。重复提交相同操作 ID 返回原结果；同一会话不能重复计入任务进度或周期分钟。

## 6. 状态与时间判定

计时阶段与界面状态分开。界面状态来自持久事实和当前时间，不用每分钟写一条“状态变化”。

| 条件 | 今日页显示 | 可用动作 |
| --- | --- | --- |
| 原计划尚未开始，无执行记录 | 待开始 | 提前开始、调整、详情 |
| 已到开始时间，无执行记录 | 尚未记录开始 | 立即开始、先做5分钟、稍后提醒、调整、补记 |
| 实时会话运行中 | 执行中 | 暂停、结束本次 |
| 实时会话暂停中 | 已暂停 | 继续、结束本次 |
| 已有有效投入，剩余工作尚未安排 | 已记录投入，剩余待安排 | 继续、安排剩余、详情 |
| 结束一个会话，任务仍有剩余 | 本次已结束 | 安排剩余、继续工作 |
| 任务已明确完成 | 已完成 | 查看记录、更正记录 |
| 执行实例被明确提前撤回 | 提前调整或取消 | 查看历史 |

“逾期”“超过启动容差”“恢复观察期结束”是计算标签，不等于已经确认未学习。

时间规则：

- 事件保存 UTC，历史报告按实例的承诺时区和归属日展示。
- 第一轮启动容差固定为5分钟，界面解释口径；容差不触发强制操作。
- 恢复统计观察期固定为原始开始后24小时，按经过时长计算，与本地一天的长度分开。
- “稍后10分钟”按经过时长；原有“延后1天”继续按本地日历日规则。
- 运行中有效投入使用单调计时，暂停、系统休眠和无法证实的停机时间不得直接当有效学习。
- 关机、崩溃、重启后的未知时段需要用户确认，计时服务已有的崩溃恢复边界继续生效。

## 7. 今日页启动与5分钟体验

### 7.1 默认交互

任务到点后，今日页显示非模态执行卡片，不抢焦点，不强制打开窗口。主操作为“开始”和“先做5分钟”；次操作为“10分钟后提醒”“调整安排”，更多操作中提供“补记已做”。

示例：

```text
蓝桥杯竞赛课
原计划 13:40–14:25 · 尚未记录开始
可以先做5分钟，之后再决定是否继续。

[开始] [先做5分钟]
[10分钟后提醒] [调整安排]
```

用户此前明确不希望依赖专注功能。新入口直接在今日页完成开始操作，显示轻量执行条，独立计时页面作为可选入口。首轮不要求先填写原因、目标、备注或表单。

### 7.2 开始前检查

- 操作针对的任务仍存在且可执行，计划版本或实例没有失效。
- 没有另一段正在运行或等待恢复确认的会话。若已有同一实例会话，返回该会话；若属于另一实例，引导处理现有会话，不隐式切换。
- 当前片段满足硬约束。未来的课程、保护时间和锁定块会决定可执行片段的边界。
- 此刻不满足计划硬约束时，计划启动操作说明占用和下一个可用时段，不假称安排合法。用户仍可通过独立的“只记录实际”入口记录真实投入，即使实际发生在保护时间中；该记录标明偏离计划，不覆盖或放宽保护规则。事实记录与合法排程分开校验。

### 7.3 先做5分钟

1. 点击只创建实际开始记录并开启计时，不先扣5分钟，不改变预计时长、截止时间或周期目标。
2. 目标为5分钟的有效投入。暂停时间不计入目标。
3. 有效投入达到5分钟后，执行条显示“已做5分钟”，提供继续、休息、结束本次。计时持续运行，只有用户明确暂停或结束才停止；提示不重复弹出。
4. 如先遇到硬边界，按下节停止规则暂停，不把5分钟目标用作跨越保护时间的许可。
5. 可用连续时间不足5分钟时，不能先显示已开始再报错。卡片说明实际可用时间，提供“做这几分钟”与“换个时间”。前者是用户明确选择的实际短会话，不是引擎生成违反最短块长度的计划。
6. 剩余工作少于5分钟时显示“先做剩余时间”，不夸大需要量。低于一分钟的真实投入仍保存，进度按累计时长换算。

### 7.4 暂停、结束与硬边界

暂停立即生效，再允许可选记录原因。不能让原因表单使暂停时刻晚于真实操作。

遇到课程、保护时间或锁定安排开始时，应用内计时自动暂停并记录 `hardBoundaryReached`，用户实际行为不可被软件强制阻止。允许事后更正记录，但更正事实不修改保护规则。

自动暂停是应用运行时的目标行为。后台调度延迟、休眠或进程崩溃后，按已保存活动段与已知边界恢复，超过边界的未知时间不得自动入账；不能宣称已在进程不运行时准确检测用户行为。用户确实继续工作时，可以明确选择只记录实际或事后补记，偏离事实不会变成放宽授权。

遇到普通可移动任务的开始时间时，不自动打断当前执行。执行条显示冲突，并允许结束本次或继续后调整。已经运行的会话在重排输入中作为当前事实保护，不能被算法移回过去。

结束本次只结束这次会话，不能直接等价为完成任务。普通任务预计投入已耗尽时显示“预计时长已投入”，由用户确认完成或修正剩余。周期目标继续按既有有效分钟结算规则计算达标。

## 8. 稍后提醒、移动安排与跳过

| 操作 | 时间参照 | 写入结果 | 不应发生的副作用 |
| --- | --- | --- | --- |
| 10分钟后提醒 | 点击时刻 + 10分钟 | 持久化提醒意图 | 不改计划，不扣分钟，不重置延迟 |
| 现有延后本次 | 该块原计划开始 + 用户选择时长 | 生成块级延后预览 | 不改变旧接口时间参照 |
| 从现在起安排剩余 | 点击时刻为最早开始下界 | 生成局部恢复预览 | 不把下界当精确锁定点 |
| 跳过本次安排 | 当前实例/块 | 确认后移除本次占用，任务可继续重排 | 不取消任务、不算完成 |
| 今天不再安排该任务 | 所在本地日结束之前 | 确认一次性恢复限制 | 不永久修改最早开始属性或截止时间 |

“今天不再安排该任务”在第一轮作为调整面板中的显式选项，只影响尚未执行的剩余工作。同一任务已记录的实际投入、其他日期安排和未来周期不受影响。用户确认后，该一次性限制保存到事项时区“下一个本地日期开始”的精确 UTC 瞬间；不能用固定加24小时代替。若时区规则使本地午夜不存在或重复，使用时区库解析出的下一个本地日期第一个有效瞬间。页面退出和应用重启不清除，过期后自动失效。取消预览不保存限制。

提醒关闭时，“10分钟后提醒”入口显示不可用及原因，提供打开提醒设置的入口；不得提示“已设置”却不发送，也不得自行开启总开关。

例如原计划13:40，用户14:00操作：稍后10分钟对应14:10；原有块级延后10分钟仍以13:40为参照。新面板使用前者语义，并用不同操作类型传入应用层。

## 9. 延迟后的局部恢复规则

### 9.1 进入条件与方案顺序

未记录开始本身不触发自动大范围重排。软件可以计算建议，用户通过“调整安排”或“安排剩余”进入预览。

按以下顺序尝试，并展示影响：

1. 当前时刻到原计划结束的空闲仍够剩余工作，保留其他安排。
2. 原结束后存在相邻合法空闲，且不突破边界时，给出延长本次的方案。
3. 寻找当天后续合法空闲，优先避免移动其他块。
4. 必须移动其他可移动任务时，复用既有优先级和局部修复规则，列出每个受影响块。
5. 当天放不下时，在原截止时间和周期边界内搜索后续日期，保留工作日/周末负载规则。
6. 无法完整安排时显示可安排部分、未安排分钟及结构化原因。无效方案不得应用；部分有效方案仍需明确授权。

“缩短本次”表示只排一部分，未安排工作继续存在，不下调任务总量。用户要减少工作量时，必须另行显式修正剩余。

### 9.2 排程不变量

- 保留既有硬约束和优先级；5分钟启动入口不产生新的高于所有任务的排程优先级。
- 固定日程、课程、保护时间、锁定块、不可拆分约束、截止时间与周期周界继续生效。
- 晚睡或自定义延长日继续走实施基线中已经验收的选择和授权流程。本文复核时 `ScheduleEngine.algorithmVersion` 为 `19`；WP0 若读到后续版本，应记录实际值和对应回归，不得为了本功能擅自抬算法版本。不能因为延迟自动推迟睡眠，更不能顺带推迟次日起床。
- 不能静默缩小剩余工作、放宽每日上限、删除冲突安排或推迟截止。
- 未确认预览不写计划。新流程的恢复/跳过草案只属于当前提案，取消后不能污染下一次普通生成。
- 确认时重验计划版本、任务进度版本、会话状态与当前时刻。用户看预览期间新增投入或修改任务后，旧提案必须失效重算。
- 执行中的有效投入与预留占用要分开。尚未结束的计时不能既作为已完成分钟，又作为完整待排工作重复占用。
- 当前事实导致无法继续沿用旧块时，预览明确列出旧占用如何释放、剩余分钟如何重新安排；历史事实不会被重排覆盖。

### 9.3 本次剩余与任务总剩余

恢复目标是所选执行实例的未做份额，并受任务总剩余限制。不能把整个任务所有剩余都塞进当前片段。

例如任务原需90分钟，已有两次各45分钟的安排。本次做5分钟后，任务剩余85分钟，本次恢复40分钟，另一次安排仍为45分钟；不能恢复85分钟并继续保留另一段45分钟。

每次提案同时校验任务级分钟守恒和实例级份额。未安排份额只计一次，计划预留不算实际投入。超额投入使其他尚未执行片段需要缩减时，显示局部调整；遇到锁定块则报明确冲突，不能静默删块或制造负剩余。

短会话不改变任务拆分模式。不可拆分任务允许用户真实做5分钟并记录，但系统不能因此把剩余工作自动拆成多段，也不能跳过最短连续长度约束来生成新计划。

## 10. 实际投入与剩余工作同步

### 10.1 唯一计量来源

实际投入来自有效会话的累计活动时长。实时会话、补记和恢复确认使用同一入账路径，每条会话只计一次。首次点击开始表示用户报告开始执行，不代表软件能够证明注意力。在出现正时长的可靠活动段前，界面可以显示计时中，但统计中的启动证据仍待确认。零投入会话不构成有效启动证据；形成正活动量后，采用该会话真实开始时刻，不能改用心跳保存时刻。

原始精度保存到既有计时支持的微秒或等价整数精度。换算分钟时先累计再取整，不能把两段各30秒都丢为0。不得把时间区间的全长当活动时长。

### 10.2 普通任务的进度检查点

为了保留人工修正，新增持久进度检查点，包含 `anchorRemainingMicros`、`anchorSequence`、创建时刻、原因及版本。每条投入事实保存不可变的首次入账序号 `firstAcceptedSequence`，更正保留该序号。

计算规则：

```text
eligibleCredits = 首次入账序号大于 anchorSequence，
                  且明确计入当前剩余的全部有效投入记录
remainingMicros = max(0, anchorRemainingMicros - sum(eligibleCredits.durationMicros))
remainingMinutesForScheduling = ceil(remainingMicros / 60,000,000)
```

时间量统一使用整数微秒，序号由数据库写事务分配。调度使用向上取整后的分钟，展示可同时保留秒数，不能把尚余30秒截成0而漏排。首次接入以当前真实剩余建立检查点，已有有效记录均落在序号边界之前，不再扣一次。

用户显式修正剩余时，先暂停并结算同任务的运行会话，再在一个事务中建立新的序号边界。修正前已入账记录的更正只更新实际统计，不自动改写这个较新的人工剩余；需要修正剩余时由用户另行确认。修正后新增记录的更正或撤销会重算当前剩余。

晚补记的发生时间早于检查点时，询问“这段投入是否已包含在上次剩余修正中”。选择已包含则仍保存实际记录，但不再扣当前剩余；选择未包含才计入。该选择属于记录版本，更正后可追溯。不能只靠发生时间或总累计分钟差猜测。

预计时长调整不会静默重设人工剩余。若用户同时要求修改剩余，沿用显式修正路径。

新流程结束本次后的自动同步只更新进度，不调用“剩余为0即自动完成普通任务”的旧组合入口。已有“按记录重算”入口接入同一计算来源；其完成确认在界面中明确，不允许两套入口采用不同累计口径。

### 10.3 周期目标

周期目标仍使用周期仓储的有效分钟账本。会话分钟不得先写普通任务进度，再额外补一次周期完成分钟。

跨周实际投入按事项时区的真实活动区间切分到对应周；不能只按会话结束时间把全部分钟算到新周。分配以活动段为来源，合计必须等于原有效投入；不能向两周各写整段。每周先累计微秒再取整为完成分钟，余秒保留在该周，不跨周搬运以凑整。旧周期截止和结转规则继续适用，新周不能自动替旧周刷达标。

旧周期补记改变实际完成量时，通过既有周期结转服务向后重算依赖链，并保留原因。已经确认的未来计划只标为进度变化待调整，不能直接静默重排。没有明确周归属的投入先保存为待分配事实，不计入达标，也不允许伪造新周期任务来吸收未知分钟。

崩溃恢复只有总分钟而没有可核实跨周活动区间时，要求用户分配到相应日期；未确认的分配不参与达标结算。

## 11. 事务、幂等与异常恢复

以下属于关键业务事实，必须事务提交，不能只放进 `FocusService.onFinished` 这类允许吞异常的附加回调：

- 开始：创建会话、关联执行实例、记录开始事件。
- 结束或补记：保存有效记录、更新进度检查点的投影或周期账本、记录结束事件。
- 计划应用：写计划版本、记录块来源关联和恢复意图兑现结果。

学习偏好证据、通知对账与统计缓存更新在关键事务之后执行。失败记为可重试附加操作，不能撤销已保存的真实执行记录，也不能重复扣减进度。

要求：

1. 同一操作 ID 只提交一次；重复点击开始或结束返回相同结果。
2. 一次只允许一个全局有效实时会话。并发入口、通知点击与独立计时页也受同一仓储约束。
3. 暂停/结束先校验会话版本，不能把“结束后到达的暂停请求”写回运行状态。
4. 崩溃后未确认的会话不直接结算未知时长。重启不假定停机时间都在学习。
5. 提案失效不会删除实际执行记录。用户可以保留记录后重新安排。
6. 数据库或磁盘写入失败时明确显示未保存，不显示“已开始”或“已完成”假成功。
7. 系统时钟回拨或跳跃时标注受影响记录；无法确定的启动延迟不进入精确均值，单列数量。
8. 版本更新沿用现有业务事务阻塞和未保存编辑机制。运行中的会话需先暂停并持久化；不能在无记录情况下直接安装退出。

幂等不能只靠页面禁用按钮。所有会改变持久状态的命令都使用 `(dataEpoch, operationId)` 作为唯一键，并保存命令类型、规范化请求摘要及完整稳定结果。相同键和相同摘要返回原结果；相同键但摘要不同返回 `invalid/operationIdReused`；事务回滚时操作结果也回滚，允许原请求重试。页面超时、路由重建或进程重启不得生成一个新操作 ID 后盲目重复原写入。

## 12. 补记与障碍记录

### 12.1 补记

允许用户选择实际开始、结束、活动时长和对应安排。活动时长必须大于0，且不能超过开始到结束的经过时长。未来结束时间拒绝保存。

同一时间段已有其他有效工作记录时提示重叠，不自动双计；单纯点击“仍然保存”不能制造双份有效投入。用户必须选择缩短新区间、替换旧记录，或把重叠区间明确分配给其中一条记录。有效分配按区间并集计量，任何交叠微秒最多进入一个进度目标；若用户只想保留两条叙述性记录，重叠部分可以保存为不计入进度的备注事实。补记有记录 ID 和来源，重复保存是更新或更正，不新建一份副本。

只有时长没有准确开始时刻的历史数据仍可用于投入汇总，不进入启动延迟计算。补记来源在复盘中可见，用户可以选择查看仅实时记录的指标。

### 12.2 执行障碍

延后、结束或复盘时允许一次选择原因，默认不选。可选值为临时有事、任务太难、精力不足、忘记、其他。原因可改，可清除，不影响开始按钮。

不选择原因显示未记录。不得根据晚启动、前台应用、空闲时间或重复延后自动推断“玩手机”。中断原因与未启动原因分开统计，避免把同一条事实算成两次障碍。

## 13. 提醒策略

- 今日页状态卡持续可见，用户主动打开软件即可操作；没有系统通知也可以完整使用。
- 系统通知复用总开关、任务开始类别和免打扰。不另建执行提醒特权类别。
- 每个执行实例只允许一个当前提醒意图，保存 `occurrenceId`、提醒修订号、目标时间、已处理状态和实际派发结果。
- 稍后提醒替换上一次尚未处理的提醒，不累积多个通知。开始、提前取消或任务完成后撤销旧提醒。
- 关闭通知后取消待发项；已经在队列里的点击回调也要重新校验状态，不得启动已完成任务。
- 同一实例重复对账、重启、切页面或重排，不重新生成已经处理的提醒。
- 免打扰结束或电脑重新开机时，不逐条补发过期执行通知；只在应用内汇总待处理安排。
- Windows 未提供可靠的“已看到”回执时，不声称用户已经看过提醒。调用调度成功仅表示排入系统，界面和日志必须区分。
- 通知点击仅导航到对应执行卡片。第一轮不在系统通知内提供未经同等校验的后台写入捷径。

## 14. 三项指标与记录完整性

### 14.1 公共集合

每次查询固定一个 `asOfUtc`，所有指标使用同一时刻和同一过滤条件。

统计对象是执行实例，不是任务条数、计时会话数或恢复后片段数。排除固定日程、课程、保护时间、未确认预览、提前撤回及升级前无法建立基准的历史记录。

旧安排到点后取消、跳过或改期仍保留在当时承诺集合。没有记录只能标为“未记录启动”，不能解释成确定没有做。

报告按原承诺日归属。重排、补记、更正会更新对应原日期的统计，不能把今天的迟到转移到明天隐藏。显示来源分布、缺失记录数量、提前调整数量及统计截止时刻。

### 14.2 准时启动率

设原始开始为 `S`，容差为5分钟，有效首次启动为 `A`。

- 分母为 `asOfUtc > S + 5分钟` 的有效实例，避免任务刚到点尚在容差内就先记失败。
- 分子为其中存在 `A <= S + 5分钟` 的实例。提前开始计准时。
- 无启动记录的实例不进入分子，另列数量。名称和说明明确为“按已记录启动计算”。
- 分母为0显示暂无数据，不显示0%或100%。

### 14.3 平均启动延迟

使用同一有效集合中有可信开始时刻的实例，逐项计算 `max(0, A - S)` 后求平均。

没有开始时刻的记录不填0，也不取当前时刻作为实际开始；必须同时显示“已记录启动 n 次，未记录 m 次”。时钟异常导致不可确定的记录另列，不能混进平均数。

### 14.4 延迟任务恢复率

观察终点为 `S + 24小时`。

- 只统计 `asOfUtc >= S + 24小时` 的已结束观察窗，未结束的显示待观察数量。
- 分母为该集合中未在5分钟容差内记录启动的实例。
- 分子为其中存在 `S + 5分钟 < A <= S + 24小时` 的实例。
- 超过24小时才开始仍记录真实投入，但不算此次观察窗内恢复，单列为更晚启动。
- 分母中含“未记录启动”的实例，因此说明这是记录到的恢复比例，不能宣称这些用户确定未执行。
- 同一实例迟到后做5分钟、暂停、再继续，只算恢复一次。只移动计划或点击提醒不算恢复。

### 14.5 试用验证

发布前证明行为与计算正确；是否改善拖延通过至少两周实际使用观察，不设没有依据的改善百分比门槛。

## 15. 数据迁移、备份与隐私

- 执行实例、块关联、事件、会话归属、进度检查点和提醒意图均持久化。精确表结构在实施计划中定义，不把重要事实仅保存在页面内存。
- 2026-10-19 复核时数据库 schema 为10。实施时从最后批准的 `1.10.x` 基线读取最新 schema，再分配下一号；不在本文预占编号，也不能与并行迁移共用同一版本。
- 旧计时记录可读取，不强行关联原始安排；旧计划不回填成已经错过的任务。首次启用只接入启用时刻之后尚未开始的当前安排，过去安排保持历史数据。
- 已有未结束会话先走既有恢复确认，不能因启用新功能创建第二段会话。
- 新版完整备份包含新增事实。恢复后不能重复扣减进度、重发提醒或改变既有任务状态。
- 备份保存原始代次仅供审计；恢复成功后在恢复事务中生成新的本机 `dataEpoch`，并把导入行关联到新代次。备份创建后的旧系统通知、深链接、outbox claim和operationId不能在恢复后的数据集上生效；恢复完成后只根据当前设置重新建立仍未过期的通知意图。
- 数据迁移事务失败保留旧库；恢复应用备份遵守现有版本兼容校验。
- 数据本地保存，普通诊断日志不写任务标题、原因备注或完整个人目录。不增加分析上传。
- “普通删除任务”与“清除执行历史”是两个独立动作。普通删除任务采用 §5.2 的匿名墓碑，保留无个人文本的承诺样本；清除执行历史则删除所选范围内的实例、操作结果、事件、会话关联、活动段、进度分配、提醒、dayHold和outbox，并撤销对应系统通知，受影响统计从剩余事实重算。
- `time_entries` 是既有共享账本。清除界面必须另设“同时删除这些实际投入记录”复选项，默认关闭，并在确认页显示记录数量和影响范围。关闭时只解除并删除本模块元数据，原计时记录变为 `legacyUnlinked`，不再进入启动指标；开启时才删除对应 `time_entries`，并按事务重新计算普通任务或周期账本。两种结果都要可测试，不得让“清除执行历史”暗中删除用户原有专注记录。
- 清除属于不可撤销隐私操作，不能因为统计、审计或外键限制拒绝。它使用新的 `dataEpoch` 使旧通知回调、旧恢复草案、旧操作ID和异步outbox全部失效；数据库提交成功后再尽力取消外部通知，取消失败只记录不含个人内容的待清理标识。

## 19. 固定工程契约

### 19.1 数据类型与唯一计量

- 所有时刻使用带 UTC 语义的整数微秒。所有活动量使用非负整数微秒；禁止浮点累计。
- `operationId`、`dataEpoch`、`processEpoch`、实例/事件/活动段ID使用仓库统一ID生成器产生的128位随机不透明标识，落库和比较时区分大小写并按完整字符串匹配。不得用当前毫秒、标题、任务ID拼接或可预测计数器生成跨进程唯一身份。
- 有效活动段为半开区间 `[startUtc, endUtc)`，结束必须大于开始。同一全局实时会话的活动段不重叠。
- 运行样本包含 `wallUtc`、`monotonicMicros`、`processEpoch`。跨进程不比较单调时钟数值。
- 事项时区使用已有时区数据库解析。保存 `timeZoneId` 与归属本地日，修改当前显示时区不改历史基准。
- 活动来源固定为 `realtime`、`manual`、`recoveryConfirmed`、`legacyUnlinked`。历史格式不认识的值进入隔离查询，不猜测成实时来源。
- 模式固定为 `planned` 与 `actualOnly`。后者仅记录事实，不创建新的合法计划占用。
- 备注长度为0至500个Unicode码点；除换行和制表符外的控制字符拒绝。其他原因附注使用同一限制。任务标题继续使用任务模块原约束，不在本模块复制一套。

### 19.2 逻辑持久表及数据库约束

所有新表遵守现有命名与迁移机制。表名和以下约束是本轮契约，Drift生成类与SQL一致。现有 `time_entries` 继续保存会话基础事实，不复制成第二份独立计时账。

| 表 | 主键与约束 | 内容及用途 |
| --- | --- | --- |
| `execution_runtime_state` | 单行 `id=1`，`dataEpoch`非空，`activeSessionId`可空，`revision>=1` | 功能启用时间、当前会话槽位、数据代次；开始必须在同一事务中占用空槽，每次槽位或代次变化使revision加1 |
| `execution_write_sequence` | 单行 `id=1`，非负单调整数 | 为已提交执行事实分配序号，不用时间戳替代顺序 |
| `execution_operations` | `(dataEpoch, operationId)`主键；`requestHash`、`commandType`、`subjectKind`非空，`subjectId`可空 | 保存改变持久状态的命令摘要、清除作用域及完整稳定结果；与业务写入同事务提交，供断线、重启和重复点击重放结果 |
| `execution_occurrences` | `id`主键；基准结束大于开始；`revision>=1` | §5.1字段、匿名历史标记、撤回原因、原份额及恢复状态投影 |
| `execution_block_links` | `(dataEpoch, planVersionId, blockId)`唯一；每条指向一个实例 | 已提交块与实例关联，拆分为多条链接，记录来源块和预留量 |
| `execution_events` | `eventId`主键；`operationId`与子事件序号唯一 | 领域事件、来源、入账序号和原事件引用；请求摘要及命令结果只保存在 `execution_operations`，避免两套幂等事实 |
| `execution_session_links` | `sessionId`唯一且关联 `time_entries`；`occurrenceId`可空；`revision>=1` | 会话主归属、来源、planned/actualOnly、首次入账序号及当前有效修订 |
| `execution_activity_segments` | `segmentId`主键；同会话序号唯一；区间正长 | 精确活动段、暂停边界、恢复确认与失效原因 |
| `execution_progress_anchors` | `(taskId, revision)`唯一；每任务只有一个当前检查点 | 人工剩余、序号边界、创建原因；历史检查点保留可追溯 |
| `execution_credit_allocations` | `(segmentId, targetKind, targetId, allocationIndex, recordRevision)`唯一 | 活动段分配到普通任务或周期；有效分配量之和不得超过有效活动量 |
| `execution_reminder_intents` | `(occurrenceId, revision, dataEpoch)`唯一；每实例最多一个当前意图 | 目标时间、稳定系统通知ID、排入系统/未知/取消状态 |
| `execution_day_holds` | `(taskId, localDate, timeZoneId)`唯一 | 已确认的今天不再安排、准确UTC失效边界、来源提案 |
| `execution_outbox` | `effectId`唯一；来源事务及目标修订非空 | 统计缓存失效、偏好证据和通知对账等附加操作的重试 |

任务普通删除时，历史实例转为匿名墓碑：`taskId`、`originPlanVersionId`、`originBlockId`、`currentPlanVersionId`置空，删除标题、备注和其他可反查原任务的字段；同时删除块链接、dayHold和提醒，解除会话到实例的直接链接，并把保留事件裁剪为指标所需的基准时间、事项类型、时区、状态及聚合份额。操作结果中的subject也要匿名化或随作用域删除，不能经历史计划块、`time_entries.taskId`或operation result重新拼回原任务。显式数据清除则删除这些行。外键不得让普通删除意外抹掉历史分母，也不得让清除隐私数据留下无法删除的引用。

数据库约束处理唯一性和引用关系。跨行时长守恒、区间重叠、来源完整性由同一写事务内查询和验证完成，禁止假称SQL行级CHECK已经覆盖跨行不变量。

全局会话槽位在暂停及待恢复确认状态继续被该会话占用；结束或明确丢弃后才能释放。不能通过暂停旧会话再开一个新会话绕过“最多一个未结束实时会话”。迁移时若旧库存在多个未结束会话，全部标记待处理，禁止任意挑一条后继续启动，用户明确处理后再占用唯一槽位。

### 19.3 命令与返回结果

所有会改变持久状态的命令包含 `operationId`、`dataEpoch` 和下表指定的并发令牌。客户端生成操作ID；重试使用原ID，新的用户动作使用新ID。开始的实际时刻由服务执行时采样，不采信可篡改的页面时间。只读查询不需要操作ID；生成和取消未应用预览只改变进程内草案，使用 `draftId + processEpoch`，应用重启后统一视为已取消。

| 命令 | 固定输入 | 必须比较的并发令牌 | 返回语义 |
| --- | --- | --- | --- |
| `start` | taskId、可空occurrenceId、mode、可空目标时长 | taskInputHash、可空occurrenceRevision、runtimeRevision | 同一实例已有会话返回其身份；其他实例占用返回activeSessionConflict |
| `pause` | sessionId、可选系统原因、采样 | sessionRevision、runtimeRevision | 立即切断活动段；用户原因事后单独保存 |
| `resume` | sessionId、mode | sessionRevision、runtimeRevision、hardBoundaryInputHash | 重验硬边界与全局槽位，不创建第二段会话 |
| `finish` | sessionId、采样 | sessionRevision、runtimeRevision | 原子结束、入账、释放全局槽位；重复调用返回原结果 |
| `recordManual` | taskId、可空occurrenceId、活动段、检查点包含选择 | taskInputHash、可空occurrenceRevision、progressAnchorRevision | 提交有效事实；重叠或跨周待分配时返回needsConfirmation，不先扣分钟 |
| `correctRecord` | recordId、更正活动段、归属与原因 | recordRevision、原目标和新目标的progressAnchorRevision | 新版本替代旧版本，双边进度更新与新事件同事务提交 |
| `setSnooze` | occurrenceId、elapsedDuration | occurrenceRevision、reminderRevision、notificationSettingsHash | 点击时刻加经过时长；旧提醒失效，新提醒意图持久化 |
| `requestRecovery` | occurrenceId、notBeforeUtc、目标份额、今天限制选项 | occurrenceRevision、planVersionId、taskInputHash、progressAnchorRevision、processEpoch | 返回一次性预览，不写计划或dayHold |
| `applyRecovery` | draftId、proposalId、输入hash、授权模式 | requestRecovery保存的全部快照令牌及当前processEpoch | 重新校验，原子写计划、来源关联和已确认dayHold |
| `cancelRecovery` | draftId、processEpoch | 草案自身revision | 释放本次草案及关联临时限制，重复取消无副作用；重启后的旧draft返回stale |

`setSnooze`第一轮UI固定10分钟，服务只接受1至1440整分钟的经过时长。小时和天的旧计划延后继续使用原服务，不混用这个范围。

`applyRecovery.authorizationMode` 只允许复用既有 `PlanApplyMode.completeOnly` 与 `PlanApplyMode.allowPartial`。默认和所有自动路径固定为 `completeOnly`；只有页面已经展示每项未安排分钟并取得本次明确确认后，才传 `allowPartial`。用户强制选择某个候选只表示选择一个已经通过硬约束校验的候选，不产生绕过冲突、保护时间、截止或来源校验的第三种模式。

结果使用封闭枚举：`applied`、`alreadyApplied`、`stale`、`notFound`、`activeSessionConflict`、`blockedByHardBoundary`、`outsidePlanBoundary`、`needsConfirmation`、`notificationsDisabled`、`invalid`、`storageFailed`、`sourceMappingMissing`。结果另带封闭 `reasonCode` 和可空安全参数，例如边界时刻或缺少分钟；用户文案映射集中维护，不能把内部枚举、异常文本、SQL或个人内容直接显示出来。

请求摘要使用确定的字段顺序、UTC整数微秒和枚举稳定值计算 SHA-256，不包含界面文案、Map迭代顺序或当前区域格式。同一操作ID请求摘要不同，返回 `invalid`，原因 `operationIdReused`。结果不存在且事务没有提交时允许重试；事务已提交但客户端断线时返回 `execution_operations` 保存的原结果。

`taskInputHash`、`hardBoundaryInputHash` 与 `notificationSettingsHash` 不是数据库中并不存在的假revision：分别由任务排程相关字段、当前时窗内硬边界来源、通知总开关/类别/免打扰规则按确定顺序序列化后计算。实现必须复用或扩展现有输入哈希工具，不能把 `updatedAtUtc` 当成无冲突保证。应用命令时重新计算并逐项比较；不一致返回 `stale`，且不写任何业务表。

生产入口固定为以下端口；所有命令和值对象放在 `lib/application/execution/execution_commands.dart`，稳定结果放在 `lib/domain/execution/execution_result.dart`。页面、通知点击、原专注页和测试驱动只能调用这些端口，不能直接写执行表。

```dart
abstract interface class ExecutionService {
  Future<ExecutionCommandResult> start(StartExecutionCommand command);
  Future<ExecutionCommandResult> pause(PauseExecutionCommand command);
  Future<ExecutionCommandResult> resume(ResumeExecutionCommand command);
  Future<ExecutionCommandResult> finish(FinishExecutionCommand command);
  Future<ExecutionCommandResult> recordManual(RecordManualCommand command);
  Future<ExecutionCommandResult> correctRecord(CorrectExecutionRecordCommand command);
  Future<ExecutionCommandResult> setSnooze(SetExecutionSnoozeCommand command);
}

abstract interface class ExecutionRecoveryService {
  Future<ExecutionRecoveryDraftResult> requestRecovery(
    RequestExecutionRecoveryCommand command,
  );
  Future<ExecutionCommandResult> applyRecovery(
    ApplyExecutionRecoveryCommand command,
  );
  Future<ExecutionCommandResult> cancelRecovery(
    CancelExecutionRecoveryCommand command,
  );
}
```

返回对象不可只带布尔值：至少包含稳定status、reasonCode、operationId或draftId、提交后的实体revision、可安全展示的结构化参数。异常只用于编程错误；预期的stale、冲突、未找到、通知关闭、需要确认和存储失败均以结果返回，并由统一文案映射处理。

`needsConfirmation` 必须返回由冲突记录ID及revision、请求摘要和dataEpoch生成的 `confirmationToken`，但不能先写进度或执行事实。用户选择处理方式后使用新的operationId提交带token的新命令；服务重新读取冲突集合，token不再匹配则返回stale并要求重新确认。禁止复用原operationId并修改请求，也禁止页面传一个没有服务签发依据的“已确认=true”。

恢复预览遵守以下生命周期：`requestRecovery` 先建立只存在于当前进程代次的作用域，现有 `PendingMoveDrafts`、`PendingSkipDrafts` 和规则覆盖只能挂在该作用域；生成的 `draftId` 与 `proposalId` 一一对应。`applyRecovery` 或 `cancelRecovery` 后立刻关闭作用域；路由离开、窗口关闭、生成异常或进程重启也必须清除。旧草案不能被另一轮普通生成读取。应用阶段只接收当前打开的草案，不允许页面提交任意旧 `ScheduleProposal` 对象。

### 19.4 关键事务不能建立在现有回调上

适配现有计时服务采用准备、提交、接纳三个阶段：

```text
读取执行快照和版本
  → 用同一计时规则准备会话转换，尚不修改运行中内存
  → 数据库事务校验版本和槽位
  → 同时保存会话、活动段、事件、进度、关联与outbox
  → 事务成功后接纳内存状态
  → 刷新界面，异步处理outbox
```

禁止先让旧 `FocusService.start()` 独立落库，再另外写实例关联。若后一步失败，会产生已开始但无法归属的孤立记录。

为了保留单一计时实现，可以提取现有状态转换为无副作用的 `FocusTransitionDraft`，交给执行仓储统一事务提交。原计时页的入口也必须进入相同协调路径，不能保留能绕过全局会话槽位的第二条生产写路径。

数据库提交成功后，数据库立即成为唯一事实来源。若进程在“提交成功、内存接纳之前”退出，或内存接纳抛错，下一次启动必须从 `execution_runtime_state`、会话和最后可靠活动段重建状态；不得因为内存仍是旧状态而执行补偿删除，也不得再次提交同一活动段。该故障点纳入 EXE-56 和 EXE-66。

原有未关联计时入口允许 `occurrenceId=null`，仍更新任务投入，但不凭空制造计划承诺或启动率样本。实施计划必须测试这一兼容路径。

### 19.5 稳定身份与来源验证

旧 `continuedFromId` 只属于提案期信息，不能假定它已经作为永久执行身份保存。本轮在应用提案前验证来源，再将执行链接和计划版本同事务写入。

- 无变化延续必须明确引用旧版本块。
- 移动/拆分保存旧实例及各新块份额，合计不能超过实例剩余。
- 首次新安排生成新实例；到点前替换旧安排时保留替换事件。
- 启动后的安排不得被标记为“提前撤回”，即使实际启动早于计划S。已发生事实优先。
- 到点之前的自动全量生成不自动豁免旧样本。只有用户确认且预览明确列出的实质改期才形成提前替换；单纯版本重写沿用旧实例。
- 来源缺失时可以显示未关联历史，但影响恢复或基准的写入必须返回 `sourceMappingMissing`。不得为追求可应用而自动删除旧实例。

### 19.6 持久状态机与非法转换

执行实例生命周期固定为：

```text
planned --首次正时长有效活动--> started --任务份额结清或用户结束承诺--> finished
planned --原开始前且没有任何有效活动，用户明确改期/取消--> withdrawn
```

`withdrawn` 与 `finished` 是终态。`finish` 命令只结束当前实时会话；只要实例仍有未完成份额，它保持 `started`，不会因为“结束本次”变成 `finished`。只有份额结清，或用户明确选择“放弃本实例剩余”并保存原因事件时，实例才进入 `finished`。更正记录后即使有效投入变为0，已经发生过的 `started` 事实也不能倒退为 `planned` 或改成 `withdrawn`；统计通过有效证据投影说明当前没有可计启动，而不是篡改生命周期。隐私状态只允许 `linked -> anonymized`，不可反转；普通删除执行该转换但不改变生命周期，显式清除才删除实例。

实时会话状态固定为：

```text
running <-> paused
running|paused -> recoveryPending
running|paused|recoveryPending -> finished
recoveryPending -> paused       （用户确认未知区间但不继续）
recoveryPending -> running      （用户确认并继续，先建立新的活动段）
```

`finished` 是终态。系统休眠、进程代次变化或无法证明连续活动时进入 `recoveryPending`；确认未知区间不会改写最后可靠活动段，而是另建 `recoveryConfirmed` 记录。任何命令若不在允许的起始状态，返回 `stale` 或 `invalid/illegalTransition`，不得部分写入。

提醒修订状态固定为 `pending -> claimed -> scheduled|suppressed|expired|unknown -> cancelled|handled`。`unknown` 不自动退回 `pending`；只有用户新建提醒才产生更高修订。外部回调必须同时匹配 `dataEpoch`、`occurrenceId`、提醒修订和稳定通知ID。

恢复草案状态只存在于当前 `processEpoch`：`open -> applied|cancelled|expired`。`applied`、`cancelled`、`expired` 都不能再次应用；相同应用操作ID在已提交时返回原结果，新的应用操作ID返回 `alreadyApplied`。进程结束视为全部 `open` 草案过期。

每个状态转换测试至少断言四件事：旧状态允许或拒绝、提交后的新状态、关联事件只写一次、失败时所有相关表保持事务前快照。仅断言页面文字变化不构成状态机验收。

## 20. 暂停、恢复、重排与并发的精确行为

### 20.1 时钟与可靠活动段

心跳在应用运行且有活动会话时，每15秒保存一次可靠检查点。这个间隔用于故障恢复，不意味着每15秒才响应暂停；用户暂停与结束使用当前采样即时截断。

进程退出、系统休眠/恢复和会话切换由平台适配器提供信号。现有Stopwatch不等于已证明排除了休眠，必须通过平台信号和故障注入验证。墙钟经过量与同一进程单调经过量之差的绝对值超过2秒时标记clockAnomaly；小于等于2秒允许采样误差，不人为校正实际开始时间。进程代次变化或无法确认间隔时，停止自动增加未知活动量，并显示待确认区间。

可靠的系统挂起信号先切断活动段，恢复后处于暂停或待确认状态。最小化或收进托盘不会被推断为停止工作；不得新增“无键鼠操作就是没学习”的判据。应用锁锁定或用户会话离开时暂停，恢复操作需重新解锁和校验。

定时回调迟到时，计划模式活动段不得超过已知硬边界。只有用户后续确认的 `actualOnly` 记录可以保存边界之外的真实投入。分段时不要把墙钟跳变造成的时长当活动段。

### 20.2 当前预留与实际进度

生成提案前，执行事务产生一致快照：已提交活动量、当前会话占用、任务剩余版本及实例份额。读取中的计时继续变化不会修改这份快照；应用时必须重验并按当前时刻重算，不能无限等待快照不变。

用户主动请求调整时，系统先提示并暂停本次会话，结算后再生成可确认预览。这样确认期间不持续制造必然过期的投入版本。用户恢复计时后，旧预览立即失效。

普通后台重排可以计算建议，但不得把运行中的会话当作未执行的完整块再次分配，也不得自动应用会移动当前执行窗口的提案。

普通任务精确剩余与排程分钟按§10.2向上换算。多实例预留总量以同一任务为单位控制舍入尾差，不能每个片段各自向上后凭空增加总工作量。不可分割的尾量由确定顺序中的最后一个可移动片段吸收；不满足块长则以现有短余量规则处理或保留缺口，不能伪造0分钟块。

### 20.3 过期、完成与重新打开

- 超过原截止/周界后，允许录入真实投入，但排程仍显示逾期/周期边界原因。新安排需要用户显式改变截止或选择既有结转规则。
- 普通任务精确剩余为0但尚未明确完成时，不进入待排池；今日页显示预计时长已投入，允许确认完成或增加剩余。
- 更正实际记录不得自动取消用户已经明确做出的完成决定。若更正后剩余大于0，显示不一致，用户可以重新打开任务。
- 重新打开时由用户确认新剩余并建立检查点。不能复活旧会话、旧提醒或旧恢复草案。
- 更改活动记录归属必须在同一事务内撤回原分配、写新分配、更新双方进度和周期依赖。已归属其他任务的时间不能直接复制。

### 20.4 可重试错误与失败回退

| 失败位置 | 持久结果 | 用户结果 | 重试 |
| --- | --- | --- | --- |
| 开始事务前或中途 | 无新会话、无开始事件 | 显示未保存 | 原operationId重试 |
| 开始已提交、界面未收到 | 唯一会话和开始事件已存在 | 刷新后恢复运行状态 | 返回原会话 |
| 暂停/结束写失败 | 最后可靠段保留，内存暂存待提交段 | 显示保存失败，阻止退出更新 | 原operationId及同一采样重试，不能把重试等待算活动量 |
| 进程在失败后被终止 | 只信最后可靠检查点 | 重启要求确认未知区间 | 走恢复确认，不猜测 |
| 恢复提案生成失败 | 实际投入保留，计划不变 | 展示结构化原因 | 新生成动作可重试 |
| 恢复提案应用失败 | 计划、链接、dayHold全部回滚 | 保留预览或提示过期 | stale必须重算，非stale按原操作重试 |
| 偏好/统计缓存失败 | 业务记录已提交，outbox待处理 | 不假称记录丢失 | 幂等重试附加效果 |
| 更新前安全暂停失败 | 会话仍待保存，安装不启动 | 更新入口显示阻塞原因 | 先保存或明确处理会话 |

对任务、会话、计划和检查点的比较更新使用版本号。跨进程由SQLite写事务和全局槽位保证互斥，内存锁只用于单进程操作串行，不能当成跨进程保证。

## 21. 提醒故障、隐私与交互边界

### 21.1 不承诺外部通知恰好一次

数据库提交和Windows通知调度不是同一事务。第一轮对同一提醒修订采用稳定系统通知ID和保守防重策略：

1. 创建新意图并提交，旧修订变为失效，同时写通知对账outbox。
2. 派发前持久化claim，保存 `claimedAtUtc`、`notificationId`、修订和数据代次。
3. 查询同一通知ID是否已排队；存在则更新状态，不再调度第二份。
4. 调度返回后保存结果。若调度发生后、结果提交前崩溃，恢复时先查询；无法确认时显示派发状态未知，不自动再发。
5. 开始、取消、关闭提醒和数据清除后，先提交新状态，再取消系统通知。旧点击回调按代次、修订和任务状态检查后失效。

采用这一策略可能漏掉一次无法确认的系统提醒，但不反复催促。应用内卡片继续可见，不能用额外弹窗补偿未知派发。

### 21.2 免打扰和关闭应用

目标时刻落入免打扰时，保存 `suppressedByQuietHours`，不自动推迟到免打扰结束发送。过去目标不调用现有通用的“过去时间加一分钟”兜底；执行提醒需要自己的已处理判定。

对账时目标时刻已经过去，则记为过期，只保留应用内状态；用户可以主动重新选择10分钟后提醒。界面在提交前显示下一次目标时刻及可能被抑制原因。

应用完全退出时，不保证动态计算与自动暂停继续运行；已交给系统的提醒是否可达取决于已验证的平台能力。能力不可用时明确显示，不能把“写了意图”当成“已经设好系统提醒”。不新增未获授权的启动项或常驻进程。

### 21.3 用户数据和权限

只保存完成此功能所需的任务关联、时间、活动量和自选原因。不读取手机、浏览记录、其他应用内容、键盘输入或屏幕截图。不增加管理员权限、联网出口、遥测或云上传。

系统通知遵守已有隐私设置，锁屏不额外暴露原因备注；若已有设置无法控制正文，第一轮使用通用标题“有一项安排待处理”，点击后在软件内查看具体任务。

应用锁启用时，通知点击先经过原锁屏路由，解锁后重新验证目标身份。不能通过深链接绕过应用锁。

执行草稿、未保存补记和运行会话接入已有更新安全机制。单纯存在一条未来提醒不阻止更新安装。

键盘可以完成所有主要动作；状态通过语义标签而非仅颜色表达。5分钟提示仅通知一次，不每秒向屏幕阅读器播报。200%缩放与窄窗布局下按钮、错误和取消入口保持可用。

## 22. 固定算例与模型检查

### 22.1 指标算例

以下5个实例均已到 `S+24小时`，无提前撤回，时间可靠，来源过滤为全部有效来源：

| 实例 | 相对S的首次有效启动 | 分类 |
| --- | --- | --- |
| A | 提前2分钟 | 准时，延迟0 |
| B | 晚5分钟 | 准时，延迟5分钟 |
| C | 晚20分钟 | 延迟并在24小时内恢复，延迟20分钟 |
| D | 未记录 | 未记录启动，不计算延迟均值 |
| E | 晚25小时 | 延迟且更晚启动，未在24小时内恢复 |

预期准时率 `2/5=40%`。平均延迟按有记录的4个实例计算，`(0+5+20+1500)/4=381.25分钟`，同时显示4次有记录和1次未记录。成熟观察窗中的恢复率 `1/3`，不能把更晚启动E计作24小时内恢复。

如果增加一个尚未到 `S+5分钟` 的实例，它不进入当前准时率分母；如果增加一个已经迟到但尚未到24小时终点的实例，它进入准时率分母，但只进入恢复率的待观察数量。报表必须分别显示各指标样本数，不能假定三个分母相同。

来源筛选规则：全部来源视图采用有效的精确实时或人工开始；仅实时视图只使用可靠实时证据计算A。若一个实例只有补记，筛选后显示“实时启动未记录”，仍属于该视图有效承诺分母，不能把它直接排除来提高准时率。无法关联/时钟异常另列，不能自动归为实时成功。

### 22.2 进度算例

| 输入 | 结果 |
| --- | --- |
| 初始剩余45分钟；本轮新增有效5分钟 | 剩余40分钟 |
| 初始剩余45分钟；新增30秒两次 | 精确剩余44分钟，调度44分钟 |
| 初始剩余1分钟；新增30秒 | 精确剩余30秒，调度1分钟 |
| 新人工检查点剩余30分钟；随后新增5分钟 | 剩余25分钟 |
| 在上一行基础上，将检查点之前的旧记录少算10分钟 | 统计减少10分钟，当前剩余仍25分钟，提示可另行修正 |
| 将检查点之后的5分钟改成3分钟 | 剩余27分钟 |
| 已做5分钟，重复提交同operationId | 仍只扣5分钟 |

| 同一补记选未包含 | 当前剩余再减少10分钟，最小为0 |

### 22.3 要求生成式/故障注入检查的性质

- 任意暂停、继续、结束、重复请求和崩溃位置，最多一个有效实时会话。
- 任意顺序的更正，所有有效分配活动量不超过真实有效活动量，任务精确剩余不为负。
- 只更改计划版本、不改变承诺和实际记录时，三项指标不变。
- 只取消未应用预览时，计划、进度、dayHold和下一次普通生成结果不变。
- 相同输入、固定时钟和固定生成ID序列，恢复提案结果确定。
- 所有比例满足 `0<=numerator<=denominator`；空分母返回无数据，不能出现NaN或无穷。
- 使用固定随机种子生成事件序列，测试报告记录种子。失败序列必须能作为确定回归用例重放。

### 24.3 真实安装态驱动的边界

`tool/execution_e2e.ps1` 至少支持 `-Mode Plan|Run|Verify`、`-EvidenceDirectory`、`-CandidateMsix`、`-ExpectedPackageVersion`。默认Mode为Plan；Run在涉及覆盖安装时还必须显式给 `-AllowInstall`。

驱动顺序固定如下，`<...>` 由执行者替换为实际绝对路径；证据目录必须位于仓库和所有工作树之外：

```powershell
pwsh -NoProfile -File .\tool\execution_e2e.ps1 `
  -Mode Plan `
  -EvidenceDirectory '<outside-worktree-evidence-directory>' `
  -CandidateMsix '<absolute-path-to-candidate-msix>' `
  -ExpectedPackageVersion '1.11.0.0'

pwsh -NoProfile -File .\tool\execution_e2e.ps1 `
  -Mode Run `
  -EvidenceDirectory '<same-evidence-directory>' `
  -CandidateMsix '<same-candidate-msix>' `
  -ExpectedPackageVersion '1.11.0.0' `
  -AllowInstall

pwsh -NoProfile -File .\tool\execution_e2e.ps1 `
  -Mode Verify `
  -EvidenceDirectory '<same-evidence-directory>' `
  -CandidateMsix '<same-candidate-msix>' `
  -ExpectedPackageVersion '1.11.0.0'
```

Plan不得安装、卸载、启动候选应用或修改证书；Run没有 `-AllowInstall` 必须在任何系统变更前退出。Verify只读证据和候选文件，重新计算哈希并核对安装态包身份。脚本不能把仓库内的开发EXE、`flutter run`进程或复制到沙箱中的假包当成已安装MSIX。

Plan只检查依赖、包身份、签名、版本、证据路径与必要授权。Run通过正式包身份启动候选应用，在显式选择的测试数据集内驱动真实页面，不能用 `flutter test -d windows` 的开发进程冒充安装态。

EXE-43须至少实际运行一次5分钟体验，并验证边界时刻暂停、重启恢复、关闭通知、同一提醒防重及更新阻塞。加速的假时钟用于单元和组件测试，不能替代这次真实时长的安装态抽查。

如果没有安全隔离的数据入口，Run停止，先完成测试数据集装配。不能为了获得PASS覆盖个人数据库或默默清除已有任务。
