# M4 「跳过本次」规格（用户 2026-10-07 定义）

> 本节补上路线图 §8 里唯一未通过的一项。**行为以用户的原话为准**，我不自行发挥。
> 三个动作**必须分开**，不得互相代替。

## 1. 用户给的定义（原文要点）

**「跳过本次安排，但不直接指定明天」**：

1. 当前时间块从今天的"待执行时间线"中移除。
2. 任务本身**仍然是未完成待办**，剩余时长不变；**如果已经专注了一段时间，只扣除实际完成的部分**。
3. 系统重新寻找**截止时间前的下一个合理空档**。
4. **默认显示调整预览**；开启"信任自动调整"时可直接应用。
5. 新时间可能是**今天稍后、明天或其他日期，不能无条件塞到明天**。
6. 找不到可行时间时，把任务标记为**"待安排／有逾期风险"**，并说明**缺少多少时间**。

**三个动作分开**：

| 动作 | 语义 |
| --- | --- |
| **跳过本次** | 只放弃当前时间块，任务**继续存在并参与重排** |
| **延后到明天** | 用户**明确要求**明天再做，设置新的**最早开始时间为明天** |
| **取消任务** | 整个任务**不再需要完成**，退出排程 |

## 2. 与现有能力的关系（逐条核对用户要求）

| 用户要求 | 现有能力 | 差距 |
| --- | --- | --- |
| 1 当前块移出时间线 | `plans.current()` 给已确认计划；来源按块投影 | **需要"跳过"意图**（见 §3） |
| 2 任务仍是待办、剩余时长不变、只扣已专注部分 | `TaskService.applyFocusRecompute` 已按专注记录扣减 `remainingMinutes` 且**不改状态**；`status` 保持 `open` | **无差距**，直接复用，不重算 |
| 3 重找截止前空档 | 引擎已按 `dueAtUtc` / `availableFromUtc` / 优先级排程 | **无差距**，交给引擎 |
| 4 默认预览；信任自动调整时直接应用 | `plan_preview_page.dart` 与 `AutoAdjustStore` 都已存在 | **需要接线**（按 `autoAdjustStore.enabled` 分流） |
| 5 不无条件塞到明天 | 引擎按可用时间寻找，不接受"指定明天" | **无差距**——关键是**不要**把它实现成 `availableFrom = 明天` |
| 6 排不下时报"待安排／有逾期风险 + 缺多少" | `proposal.unscheduled` 带 `shortageMinutes`；预览页「未安排」分组已显示"还缺 N 分钟" | **无差距**（M4 P5 刚补齐） |

**结论**：这条要新增的核心只有两处——**"跳过"意图的表示**与**今日页的入口 + 预览接线**。
其余全部复用既有能力。**尤其不要新造剩余时长或逾期逻辑。**

## 3. 设计：跳过意图

**形状**：与 `PendingMoveDrafts` 同一套做法（`lib/application/pending_moves.dart` 是既有先例），
新增 `PendingSkipDrafts`：

```dart
final class RequestedSkip {
  const RequestedSkip({required this.blockId});
  /// 被跳过的**已确认计划块** id（`schedule_blocks.id`），不是任务 id。
  final String blockId;
}

abstract interface class SkipDraftSink {
  void setRequestedSkip(RequestedSkip skip);
}

final class PendingSkipDrafts implements SkipDraftSink { ... }
```

**为什么粒度是"块"而不是"任务"**：用户点的是今天时间线上的**某一个块**。
同一个任务今天有两段时，跳过一段不应把两段都丢掉。

**为什么不落库**：与 `PendingMoveDrafts` 同一取舍——意图只在"点跳过 → 生成 → 确认"
这一次里有效；落地时计划块 id 会被改写成 `<提案 id>:<块 id>`，旧 id 再也匹配不上，
意图**自动失效**。为此开一张表要付一次 schema 迁移，收益只是"重启后还记得一次没确认的跳过"。

## 4. 设计：如何让引擎不再把那个块排回原处

`RepositoryScheduleProblemSource` 已经有一套"按块钉住"的机制（`pinnedByBlockId`）。
**跳过是它的反面**：不是把块钉到新位置，而是**把这个块整个拿掉**。

做法：跳过时，把该块**从 `lockedBlocks` 与 `existingBlocks` 两处都排除**，
并且**不加任何钉住**——于是：

- 该块的旧位置**不再被占用**（后续任务/本任务都能用这段空档，满足"空出来"）；
- 该任务**仍在 `tasks` 里**（满足"仍是待办、继续参与重排"）；
- 引擎**自行**在截止前寻找空档（满足"不无条件塞到明天"）。

**不引入"禁止区间"**：有人可能会想把"被跳过的那段时间"标成不可用，那是**错的**——
用户跳过的是"这件事现在不做"，不是"这段时间不许安排别的事"。把它锁成禁区会让
"跳过之后那段空着"变成"跳过之后那段浪费掉"，与要求 1、3 都相悖。

## 5. 强制测试

| 要求 | 测试 |
| --- | --- |
| 1 块从时间线移除 | 跳过意图生效后，装配出的 `ScheduleProblem` 里**不含**该块（`lockedBlocks` 与 `existingBlocks` 都没有它） |
| 1 但时段**没有**被锁成禁区 | 断言该块的旧时间段**不在** `fixedIntervals` / `protectedIntervals` 里 |
| 2 任务仍是待办、剩余时长不变 | 跳过前后 `TaskRepository` 里该任务 `status == open`、`remainingMinutes` 不变 |
| 3/5 交给引擎、不指定明天 | 断言装配出的 `SchedulableTask.availableFromUtc` **未被改成明天**（跳过不得触碰这个字段） |
| 4 默认预览 / 信任时直接应用 | 页面测试：`autoAdjustStore.enabled == false` 时走"进预览"分支；`== true` 时走"直接应用"分支 |
| 6 排不下报缺多少 | 既有 `unscheduled` + 预览「未安排」分组（M4 P5 已覆盖）；补一条"跳过导致排不下时仍然如实报缺口" |
| 三动作分开 | 断言「跳过本次」**不修改** `dueAtUtc`（那是「延后」）、**不修改** `status == cancelled`（那是「取消任务」） |
