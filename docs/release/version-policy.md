# 版本号规则与历史回填（2026-10-06 定）

**本文是版本号的权威说明**；`pubspec.yaml` 的 `version` 是**唯一数值来源**，其余两处（MSIX、备份清单
常量）都必须与它一致，并被测试守着（见第 6 节）。

## 1. 为什么重算：`1.0.16` 是失真的

三条证据，都可在仓库里复核：

1. **号段被当成了构建计数器。** `release/` 下 `1.0.6` → `1.0.16` 共 **11 个安装包，全部产自
   2026-10-06 的 5 小时内**（08:20–13:05）；而当天只有 13 次提交（功能 5、修复 4、杂项 4）。
   也就是说这 11 个号里大多数只是"同一批改动重新打了一次包"，**不对应任何独立的修复批次**。
2. **第 2 段从未被使用。** 11 个号全是 `1.0.x`，可同期有三次明确的新功能波次——任务「延后」、
   领域分类与本地课表导入、外观与领域配色。按"兼容性判据"（新增功能且向后兼容 → 抬第 2 段），
   它们本该各自抬一次。
3. **`+N` 与第 3 段的关系本身在漂移。** `docs/release/windows-release.md` 记的是 `1.0.4+5`（差 1），
   而 `release/` 里是 `1.0.6+8` … `1.0.16+18`（差 2）。同一个项目里两套计数各记各的，说明这两个
   数字实际上是同一个东西被抄了两遍。

**结论**：`1.0.16` 既不是"第 16 个补丁版本"，也不表示"补丁很多"，它是一个**每次重打包就 +1 的计数器**。

## 2. 规则：一个版本号 = 一个发布批次

"批次"指**一次对外发布的完整改动集**，不是单条提交，也不是每次构建。

| 段位 | 名称 | 什么情况下 +1 | 谁决定 |
| --- | --- | --- | --- |
| 第 1 段 | Major | **数据不兼容**：需用户手工迁移数据库/备份、或换包身份（等于换应用） | 人工，必须写进本文 |
| 第 2 段 | Minor | 批次里含**用户可感知的新功能**，且向后兼容 | 人工 |
| 第 3 段 | Patch | 批次里**只有修复**（Bug、崩溃、文案/视觉纠错） | 人工 |
| 第 4 段（MSIX） | Revision | **同一批次的重复打包**（签名、清单、打包参数修正） | 发布时定 |

配套的两条：

- **`+N` 是构建号**，只用于追溯"这个包是第几次构建"，**永不参与语义**，且**全局单调递增**
  （不随版本号归零）；
- **同一批次重打包不占新版本号**——这正是第 4 段存在的意义。此前把构建计数器放进第 3 段，
  等于把两个概念塞进一个数字。

**为什么不用"每条提交累计"**：那样算出来的当前版本**至少是 `1.12.0`**——`92efcf3` 之后有 12 条 feat、
9 条 fix，每条 feat 抬一次 minor、fix 之间再抬 patch（全部 325 次提交里 feat 有 115 条）。
那条规则适用于**库**（每个 API 变更都要对下游可见），本项目是**单体桌面应用**，用户看到的是
发布批次，不是提交。版本号应当描述"用户拿到手的差别"。

## 4. 当前取值：`1.5.0+34` / MSIX `1.5.0.6`

- `pubspec.yaml` → `version: 1.5.0+34`
- `msix_config.msix_version` → `1.5.0.6`，`output_name` → `personal_planner_1.5.0.6_x64`
- `lib/app/backup_assembly.dart` → `appVersion = '1.5.0+34'`

**为什么抬第 2 段（这是第 2 节规则的应用，不是偏好）**：本批次含**用户可感知的新功能**——统计复盘
新增「领域×周期」矩阵（领域时间分配的横向纵向对比）。第 2 节写得很直白："第 2 段：批次里含用户可
感知的新功能，且向后兼容 → 人工 +1"。它向后兼容（无数据库结构变更、无包身份变更、无迁移），所以
是 Minor 而不是 Major。

**为什么不是继续挂在 `1.4.2` 上**：`1.4.2` 是一个 **Patch 批次**（"批次里只有修复"）。它虽然从未
对外发布，但批次语义是"只修视觉"。往里面塞一个新功能，就违反了第 2 节第 3 段的定义；而把新功能
压着不抬段，等于让版本号对用户说谎——用户拿到的新包多了整整一节统计视图，号却只从 `.5` 到 `.6`。
因此**开新批次 `1.5.0`**，并把未发布的 `1.4.2` 全部改动并进来一起交付。

**第四段为什么从 `0` 走到 `1`**：第 4 段是"同一批次的重复打包"。`1.5.0.0` 是该批次的首个包
（`+28`）；随后同一批次里又改了一批内容（移除计划/实际、拆成横向占比与纵向总计、图型可选、
三项休息指标、领域覆盖缺口），而**本机已经装过 `1.5.0.0`**、同一个号不能重发不同内容
（`Add-AppxPackage` 只升不降），因此按"同批次重打包"抬第四段 → `1.5.0.1`（`+29`）。
后续同一批次内的重打包同理：`1.5.0.2`（`+30`）、`1.5.0.3`（`+31`）、`1.5.0.4`（`+32`）、
`1.5.0.5`（`+33`）。

**批次内容在宣告之后扩充过（2026-10-07 当日）**：本批次后来又装进了**新手教程**（七步、真实界面
截图、首次启动触发 + 设置入口）、**七日日历的 昨天/今天/明天 列**、**设置页版本号**，以及日期／
时间选择器的可见性与中文化修复、"重排后历史消失"与"已完成待办重复"两处修复。

按第 2 节，一个版本号 = 一个**发布批次**；本批次**从未对外发布**（只装过开发者本机），因此这些改动
并入同一批次、只动第 4 段——这正是第 3 节里 `1.4.2` 并入 `1.5.0` 的同一条做法。**第 3 位仍为 `0`**：
第 2 节规定它只用于"批次里只有修复"，而本批次含新功能。

**这条并入是人工决定**（第 2 节"谁决定"一列写明第 2 段由人工定）。2026-10-07 已把"是否改判成新批次
（`1.6.0`）"交给用户选择，**用户选择继续并入 `1.5.0`**。**一旦本批次的任意 `.x` 到了别人手上，后续
改动就必须抬第 2 段或第 3 段**，不得再并入。**

**为什么第 2 段不再抬**：第 2 节的规则按"**批次里**含用户可感知的新功能"定段，而 `1.5.0` 已经
因为"统计复盘改版含新功能"抬过一次。这一批还没交付出去，后续改动属于同一批次的继续，
只加构建号与第四段。

> **边界（会咬人的那条）**：一旦某个 `1.5.0.x` 交付给了任何人，后续任何内容改动都必须抬第 2 段
> 或第 3 段，**不能再拿第四段当补丁计数器**。`1.4.2` 之所以能连抬五次第四段，前提正是它从未
> 对外发布。

**`1.4.2` 批次的第四段为什么曾一路走到 `5`（历史，留档备查）**：该批次在**对外发布之前**连续重打包
了五次，每次保持批次语义不变。它从未交付给任何人，因此这五次重打包**不构成发布**：

| 构建 | MSIX | 与上一版的差别 |
| --- | --- | --- |
| `1.4.2+22` | `1.4.2.0` | 首版：填充比例 `0.26` |
| `1.4.2+23` | `1.4.2.1` | 用户实测反馈"仍偏淡" → 填充比例降到 `0.18` |
| `1.4.2+24` | `1.4.2.2` | 用户实测发现今日页左侧强调条不见了 → 修掉两处零高度装饰件 |
| `1.4.2+25` | `1.4.2.3` | 用户实测反馈"太亮了" → 填充 `0.18`→`0.12`、描边 `0.32`→`0.16` |
| `1.4.2+26` | `1.4.2.4` | 用户实测反馈"颜色比老版的浅还淡，看着还亮" → 派生方式改为「色相+限饱和度+求解明度」 |
| `1.4.2+27` | `1.4.2.5` | 用户实测反馈：勾完成后卡片变成「已安排任务」→ 修回退分支；新增「已完成」标记；修设置页卡片贴边 |

那两次重打包当时的两条依据是：① 批次语义没变（用户看到的仍是"日程卡片视觉修复"）；② 同一个号不能
重发不同内容，而本机已逐次装过更低的第四段（`Add-AppxPackage` 只升不降）。

> **这条判断的边界，以及它为什么现在失效了**：第 4 段能连续抬的前提是"批次**从未对外发布**、且每一版
> 都只在开发机上安装"。这个前提现在被**本批次自身的内容变化**打破了——不是因为它被交付了，而是因为
> 批次里出现了新功能，批次语义变了，所以必须开新批次而不是继续抬第四段。这条边界保留在这里，供
> 以后判断：**一旦内容跨过"只有修复"这条线，就不再是重打包，而是新批次。**

**上一个批次**：`1.4.1+21` / MSIX `1.4.1.0`（开发构建／待验收）。
**本批次之前、同批次内被取代的构建**（全部属于未发布的 `1.4.2`，都只在开发机安装过）：
`1.4.2+22` / `1.4.2.0`（比例 `0.26`）、`1.4.2+23` / `1.4.2.1`（比例 `0.18`，今日页两处装饰件仍画不出来）、
`1.4.2+24` / `1.4.2.2`（比例 `0.18`/`0.32`，卡片偏亮）、`1.4.2+25` / `1.4.2.3`（比例 `0.12`/`0.16`，
卡片够暗但掉了彩度、发灰）、`1.4.2+26` / `1.4.2.4`（勾完成后计划块变成「已安排任务」）、
`1.4.2+27` / `1.4.2.5`（末版，含「已完成」标记与设置页间距修复）。

**为什么不是别的号**：

- **不是 `0.x`**：本机已装过 `1.0.0.0` / `1.0.4.0` 等，MSIX 不接受降级，`0.x` 已不可能；
- **不是 `2.0.0`**：第 1 段的门槛是"数据不兼容或换身份"。历史上从未达到——数据库迁移由 drift
  在启动时自动执行，备份读取对旧格式向后兼容，包身份（`ShuoZhuang.PersonalPlanner` + 同一张
  证书）从未变更；
- **不是 `1.0.17`**：那等于承认 `1.0.5`–`1.0.16` 这 12 个号里没有任何功能波次，与实际提交主题矛盾；
- **不是 `1.4.3`**：`1.4.3` 仍是 Patch 段，而本批次含新功能——按第 2 节该抬的是第 2 段。
  这是本轮**改正**的一处判断：`1.4.2` 期间连续抬第四段是对的（那时批次里只有修复），但一旦
  加入新功能，就既不能抬第四段、也不能只抬第三段；
- **不是 `1.4.1.1`**：那会落回上一个已交付批次 `1.4.1`，比本机已装的 `1.4.2.x` 更低，装不上；
- **不是 `2.0.0`**：见上一条，第 1 段的门槛是数据不兼容或换身份，本批次两者都没有。

## 5. 一条操作约束（会咬人的那条）

`Add-AppxPackage` **不接受比已安装版本更低的包**。因此：

- 一旦 `1.5.0.1` 被安装，**回退到 `1.5.0.0` 或更早是不可能的**，只能继续往上；
  （`1.5.0.0` 高于本机装过的 `1.4.2.5`，所以这次原位升级是允许的——Minor 抬段顺带把第四段归零，
  不会造成"版本倒退装不上"。）
- 抬版本前先想清楚，必要时**先不安装**，只在免安装 EXE 上验证。

## 7. 什么才算正式发布

普通代码提交、测试通过、生成临时 EXE 或建立“开发构建／待验收”目录，都**不算正式发布**。
一个批次只有同时满足以下条件，才在发布记录中改为“已发布”：

1. 同时选定唯一的最终 Release 便携包与已签名 MSIX 安装包；
2. 补齐面向用户的更新说明；
3. 记录产物校验值和最终验证结果；
4. 在发布台账中把该批次状态登记为“已发布”。

完成上述登记后，后续改动才开始判断新的 Major／Minor／Patch 批次。此前即使重复构建，也仍属于
当前待验收批次，只增加全局构建号；若仅改变签名、清单或打包参数，则同时增加 MSIX Revision。

## 8. 可体验版本的交付下限

从 `1.4.1+21` 起，每个交给用户体验的版本必须同时包含：便携目录、ZIP、已签名 MSIX、签名公钥
证书和使用说明。发布台账必须记录 EXE、ZIP、MSIX 的 SHA-256，以及 MSIX 签名、覆盖安装和启动
验证结果。任一产物或验证缺失时，只能记为内部构建，不能作为可体验版本交付。
