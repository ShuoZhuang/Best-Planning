# 版本号规则与历史回填（2026-10-06 定）

**本文是版本号的权威说明**；`pubspec.yaml` 的 `version` 是**唯一数值来源**，其余两处（MSIX、备份清单
常量）都必须与它一致，并被测试守着（见第 6 节）。

## 1. 为什么重算：`1.0.16` 是失真的

三条证据，都可在仓库里复核：

1. **号段被当成了构建计数器。** `release/` 下 `1.0.6` → `1.0.16` 共 **11 个安装包，全部产自
   2026-10-06 的 5 小时内**（08:20–13:05）；而当天只有 13 次提交（功能 5、修复 4、杂项 4）。
   也就是说这 11 个号里大多数只是"同一批改动重新打了一次包"，**不对应任何独立的修复批次**。
2. **第 2 段从未被使用。** 11 个号全是 `1.0.x`，可同期有三次明确的新功能波次——任务「延后」、
   领域分类与本地课表导入、外观与领域配色。按"兼容性判据"（新增功能且向后兼容 → 抬第 2 段），
   它们本该各自抬一次。
3. **`+N` 与第 3 段的关系本身在漂移。** `docs/release/windows-release.md` 记的是 `1.0.4+5`（差 1），
   而 `release/` 里是 `1.0.6+8` … `1.0.16+18`（差 2）。同一个项目里两套计数各记各的，说明这两个
   数字实际上是同一个东西被抄了两遍。

**结论**：`1.0.16` 既不是"第 16 个补丁版本"，也不表示"补丁很多"，它是一个**每次重打包就 +1 的计数器**。

## 2. 规则：一个版本号 = 一个发布批次

"批次"指**一次对外发布的完整改动集**，不是单条提交，也不是每次构建。

| 段位 | 名称 | 什么情况下 +1 | 谁决定 |
| --- | --- | --- | --- |
| 第 1 段 | Major | **数据不兼容**：需用户手工迁移数据库/备份、或换包身份（等于换应用） | 人工，必须写进本文 |
| 第 2 段 | Minor | 批次里含**用户可感知的新功能**，且向后兼容 | 人工 |
| 第 3 段 | Patch | 批次里**只有修复**（Bug、崩溃、文案/视觉纠错） | 人工 |
| 第 4 段（MSIX） | Revision | **同一批次的重复打包**（签名、清单、打包参数修正） | 发布时定 |

配套的两条：

- **`+N` 是构建号**，只用于追溯"这个包是第几次构建"，**永不参与语义**，且**全局单调递增**
  （不随版本号归零）；
- **同一批次重打包不占新版本号**——这正是第 4 段存在的意义。此前把构建计数器放进第 3 段，
  等于把两个概念塞进一个数字。

**为什么不用"每条提交累计"**：那样算出来的当前版本**至少是 `1.12.0`**——`92efcf3` 之后有 12 条 feat、
9 条 fix，每条 feat 抬一次 minor、fix 之间再抬 patch（全部 325 次提交里 feat 有 115 条）。
那条规则适用于**库**（每个 API 变更都要对下游可见），本项目是**单体桌面应用**，用户看到的是
发布批次，不是提交。版本号应当描述"用户拿到手的差别"。

## 4. 当前取值：`1.6.2+37` / MSIX `1.6.2.0`（**M9 收口版本，2026-10-08 已发布**）

- `pubspec.yaml` → `version: 1.6.2+37`
- `pubspec.yaml` `msix_config.msix_version` → `1.6.2.0`，`output_name` → `personal_planner_1.6.2.0_x64`
- `lib/app/backup_assembly.dart` → `appVersion = '1.6.2+37'`

### 4.00 为什么收口在 `1.6.2`（2026-10-07 M9 的决定）

现行口径（4.0 节）把第二段**固定为 `1.6`**：M1～M9 是**同一个发布批次**的内部里程碑，
不为任何单个里程碑抬号、也不单独发布。因此收口时三段里可用的是**第 3 段与第 4 段**：

| 项 | 取 | 为什么 |
| --- | --- | --- |
| 第 2 段 | `1.6` | **固定**。抬它就是 `1.7`，路线图 §13 明令禁止 |
| 第 3 段 | `2`（`1.6.1` → `1.6.2`） | 第 3 段原本只用于"纯修复"，但这里它是**唯一还剩的可用段位**，而收口必须让版本**向前走**——同一个号不能重发不同内容 |
| 第 4 段 | `0` | **收口批次的首个（也是唯一交付的）包。** 见 §4.02：收口期间我曾把它一路抬到 `3`，那是**误用**——那三次都改了内容 |
| 构建号 `+N` | `37` | **全局单调递增**（`+36` 之后是 `+37`），不随版本号归零。三次重打包都**没有**再抬它——第四段才是"重打包"的计数位 |

**MSIX 必须严格大于本机已装版本**（第 5 节的操作约束）：本机在本次收口前装的是 `1.6.1.0`
（`1.6.1+36`，旧口径下的中间候选），因此收口包取 `1.6.2.0`（`1.6.2` 批次的首个交付包；见 §4.02，收口期间那几次递增已撤回）——**严格高于本机已装的 `1.6.1.0`，可原位升级**。

> **一处诚实的说明**：第 3 段在此处的语义与第 2 节表格（"第 3 段 = 只有修复"）**不完全对应**。
> 这是 4.0 节把第 2 段钉死之后**必然的取舍**，不是笔误。若将来要恢复"第 3 段只装修复"的语义，
> 就得允许抬第 2 段——那等于放弃"一个 `1.6` 发布线"的口径。
>
> 另一条**不能做**的事：不该把 M1～M9 当成九个批次各发一版。那正是 4.0 节要避免的结果。

#### 4.02 **一条被我自己违反过的规则**：第 4 段只在"内容一字未改"时抬（2026-10-08）

**用户的质询**："为什么一直是在改第四位版本号"，并重述了分段规则。**他是对的。**

收口期间我把第 4 段从 `0` 一路抬到 `3`，理由是"收口包已经装到本机，同一个号不能重发不同内容"。
**那个理由只说明"必须换号"，不说明该换第 4 段。** 三次改动实际是：

| 抬的那次 | 实际改了什么 | 按分段规则应归 |
| --- | --- | --- |
| `1` | **代码**：备份页把异常里的完整路径打到界面上 | **修复** → 并进批次（第 3 段） |
| `2` | **代码**：用户实测的两处缺陷 | **修复** → 并进批次（第 3 段） |
| `3` | **代码**：M8 操作式引导 | **用户可感知的新功能** → 第 2 段 |

**三次都改了内容，因此三次都不是"重打包"。** 第 4 段的定义是"**同一批次重打包**"，
典型情形是签名、清单或打包参数修正——**代码一个字都没变**。

#### 这次撞上的一条真冲突（需要总口径拍板）

分段规则说"有新功能 → 第 2 段"，而路线图 §13 说"**不得把第二段升到 `1.7`**"。
M8 是用户可感知的新功能，按规则该是 `1.7.0`，按路线图不许。

**用户 2026-10-08 的裁定是 A 案**：这一批从 M1 起就定在 `1.6`，M8 是路线图内**承诺过的里程碑**
而不是新增需求，因此**不算新批次**；`1.6` 保持不动，第三段吸收为 `1.6.2`，
**第 4 段停止内部递增**——未发布的包不该一路占号。

**落地的做法**：把 `msix_version` 改回 `1.6.2.0`，并**卸载本机已装的 `1.6.2.3` 再装 `1.6.2.0`**
（`Add-AppxPackage` 不接受降级，因此这一步必须卸载；**卸载不动用户数据**，已实测验证）。
此后**未发布期间任何内容改动都不再抬任何段**，只在 M9 真正定稿时按当时基线定一次。

> **留给下一个人的判据**：
> 抬第 4 段之前先问一句——**代码改了没有？**
> 改了就不是重打包，别动第 4 段。

### 4.1 保留备查：为什么曾经是 `1.6.1`（旧口径，**不再适用**）

> **`1.6.1+36` / `1.6.1.0` 是 `1.6` 发布线的中间开发候选，不是一次独立发布。**

### 4.0 现行口径：一个 `1.6` 发布线，九个内部里程碑（2026-10-07 起生效）

**用户明确决定**：M1～M9 全部并入 `1.6` 发布线。因此：

| 事项 | 现行做法 |
| --- | --- |
| 第二段（Minor） | **固定为 `1.6`**，任何 Agent 不得擅自升到 `1.7` |
| 里程碑是否单独抬版本 | **否**。完成单个里程碑**不改变 Minor**，也不分配 Patch 号 |
| 里程碑是否单独发布 | **否**。期间只生成**内部验证构建**，不创建 GitHub Release、不登记"正式发布" |
| 第三段、MSIX 第四段、构建号 `+N` | **只在 M9 收口时**按届时基线确定；且最终 MSIX 必须**严格高于**本机已安装版本 |
| 最终交付物 | 便携目录、ZIP、已签名 MSIX、`.cer`、安装脚本、安装说明、SHA-256、对应用户指南（§3、§14） |

**那么现有这些号怎么办**：`1.6.0+35` / `1.6.0.0`、`1.6.1+36` / `1.6.1.0` 以及收口期间的 `1.6.2.0`（`1.6.2+37`）都是**在旧口径或收口途中**

- 它们**继续作为本机的验证用构建**，供人工验收与回归复现使用；
- 它们**不被登记为任何里程碑的对外交付**，也不改写 `release/` 下的历史目录名

- **`1.6.1+36` 之后的中间构建不再抬任何号段**：若还需本机验证，只递增构建号 `+N`
  （例如 `1.6.1+37`），并保持第二段 `1.6` 与 MSIX 第四段不变；

于是同一条发布线被拆成九个"批次"——那正是现行口径要避免的事。

### 4.0.1 保留备查：为什么当时是 `1.6.1`（旧口径，**不再适用**）

**为什么抬第 3 段（第 2 节规则的应用）**：本次内容是**纯修复**——"作息规律性"这张图在范围里
只有一天有安排时会画出一根横轴重复同一天日期的柱子，用户 2026-10-07 报的"横轴日期都是 10/7"
就是它。第 2 节第 3 段："批次里**只有修复** → 第 3 段 +1"。**没有新功能**（不改指标口径、不加
新图表、不改范围选项），因此不是 Minor；没有数据不兼容或换身份，因此不是 Major。

**为什么不能并入 `1.6.0`**：`1.6.0+35` / MSIX `1.6.0.0` **已经交付给用户做体验确认**。第 4 段
能连续抬的前提是"批次**从未对外发布**、每一版都只在开发机上安装"——这个前提在 `1.5.0.6` 时被
打破过一次（于是开了 `1.6.0`），现在 `1.6.0.0` 同样已经交付，因此当时开了新批次 `1.6.1`。

**第四段为什么回到 `0`**：`1.6.1` 是（当时的）新批次首个包，因此从 `0` 起；构建号全局单调递增，
所以 `+35` 之后是 `+36`（不随版本号归零）。

**为什么不是别的号**（当时的判断，仅留档）：

- **不是 `1.6.0.1`**：那会把一个**新批次的内容**塞进已经交付出去体验的批次里，等于让版本号说谎；
- **不是 `1.7.0`**：本次没有用户可感知的新功能，抬 Minor 会虚报——**这一条正好与现行口径一致**；
- **不是 `2.0.0`**：没有数据不兼容、没有换包身份。

**上一个批次**：`1.6.0+35` / MSIX `1.6.0.0`（开发构建／待验收，已交付用户做体验确认）。

### 4.1 `1.5.0` 批次内的第四段为什么一路走到 `6`（历史，留档备查）

`1.5.0.0`（`+28`）是该批次首个包；此后同一批次里又改了几批内容（移除计划/实际、拆成横向占比与
纵向总计、图型可选、三项休息指标、领域覆盖缺口；后来又并入新手教程、七日日历的昨天/今天/明天列、
设置页版本号、日期时间选择器中文化、两处修复与两张教程截图重拍）。而**本机已经装过 `1.5.0.0`**、
同一个号不能重发不同内容（`Add-AppxPackage` 只升不降），因此按"同批次重打包"依次抬第四段：
`1.5.0.1`（`+29`）、`1.5.0.2`（`+30`）、`1.5.0.3`（`+31`）、`1.5.0.4`（`+32`）、`1.5.0.5`（`+33`）、
`1.5.0.6`（`+34`）。

> **这条边界的两次失效，两次都按规则开了新批次**：第 4 段能连续抬的前提是"批次**从未对外发布**、
> 且每一版都只在开发机上安装"。① `1.5.0` 期间它被**内容变化**打破过一次（统计复盘改版含新功能，
> 于是从 `1.4.2` 开新批次 `1.5.0`）；② 现在它又被**交付**打破了一次——`1.5.0.6` 已交给用户确认，
> 于是从 `1.5.0` 开新批次 `1.6.0`。判据始终是同一句：**一旦内容跨过"只有修复"这条线、或批次
> 已经交付出去，就不再是重打包，而是新批次。**

**`1.4.2` 批次的第四段为什么曾一路走到 `5`（更早的历史）**：该批次在**对外发布之前**连续重打包
了五次，每次保持批次语义不变。它从未交付给任何人，因此这五次重打包**不构成发布**：

| 构建 | MSIX | 与上一版的差别 |
| --- | --- | --- |
| `1.4.2+22` | `1.4.2.0` | 首版：填充比例 `0.26` |
| `1.4.2+23` | `1.4.2.1` | 用户实测反馈"仍偏淡" → 填充比例降到 `0.18` |
| `1.4.2+24` | `1.4.2.2` | 用户实测发现今日页左侧强调条不见了 → 修掉两处零高度装饰件 |
| `1.4.2+25` | `1.4.2.3` | 用户实测反馈"太亮了" → 填充 `0.18`→`0.12`、描边 `0.32`→`0.16` |
| `1.4.2+26` | `1.4.2.4` | 用户实测反馈"颜色比老版的浅还淡，看着还亮" → 派生方式改为「色相+限饱和度+求解明度」 |
| `1.4.2+27` | `1.4.2.5` | 用户实测反馈：勾完成后卡片变成「已安排任务」→ 修回退分支；新增「已完成」标记；修设置页卡片贴边 |

那两次重打包当时的两条依据是：① 批次语义没变（用户看到的仍是"日程卡片视觉修复"）；② 同一个号不能
重发不同内容，而本机已逐次装过更低的第四段（`Add-AppxPackage` 只升不降）。

**本批次之前、同批次内被取代的构建**（全部属于未发布的 `1.4.2`，都只在开发机安装过）：
`1.4.2+22` / `1.4.2.0`（比例 `0.26`）、`1.4.2+23` / `1.4.2.1`（比例 `0.18`，今日页两处装饰件仍画不出来）、
`1.4.2+24` / `1.4.2.2`（比例 `0.18`/`0.32`，卡片偏亮）、`1.4.2+25` / `1.4.2.3`（比例 `0.12`/`0.16`，
卡片够暗但掉了彩度、发灰）、`1.4.2+26` / `1.4.2.4`（勾完成后计划块变成「已安排任务」）、
`1.4.2+27` / `1.4.2.5`（末版，含「已完成」标记与设置页间距修复）。

**为什么不是 `0.x` / `1.0.17`**：本机已装过 `1.0.0.0` / `1.0.4.0` 等，MSIX 不接受降级，`0.x` 已不可能；
而 `1.0.17` 等于承认 `1.0.5`–`1.0.16` 这 12 个号里没有任何功能波次，与实际提交主题矛盾。

## 5. 一条操作约束（会咬人的那条）

`Add-AppxPackage` **不接受比已安装版本更低的包**。因此：

- 一旦 `1.5.0.1` 被安装，**回退到 `1.5.0.0` 或更早是不可能的**，只能继续往上；
  （`1.5.0.0` 高于本机装过的 `1.4.2.5`，所以这次原位升级是允许的——Minor 抬段顺带把第四段归零，
  不会造成"版本倒退装不上"。）
- 抬版本前先想清楚，必要时**先不安装**，只在免安装 EXE 上验证。

## 6. 维护：三处同步 + 一条守卫测试

版本号出现在三个地方，其中一处是**硬编码在源码里的常量**：

| 位置 | 内容 | 谁改 |
| --- | --- | --- |
| `pubspec.yaml` `version` | `1.6.2+37` | **人工，唯一来源** |
| `pubspec.yaml` `msix_config.msix_version` | `1.6.2.0` | 随前者同步 |
| `lib/app/backup_assembly.dart` `appVersion` | `1.6.2+37`，写进备份清单 | 随前者同步 |

`test/app/version_consistency_test.dart` 守这些一致性，且**刻意不依赖任何运行时依赖**（本项目没有
`package_info`，运行时读不到真实版本——这是已知的诚实下限）：改了 `pubspec.yaml` 忘了改另外两处，
测试会红。该文件里还有一条**钉住当前候选批次**的用例（`1.6.2+37` / `1.6.2.0` / `1.6.2.0_x64`）：
它让"静默改号"无法通过，抬版本时**故意**改那一行就是流程本身，必须与本文第 4 节、工作区
`版本号规则.md` 的"当前值"以及 `docs/release/build-ledger.md` 的新条目一起改。

> 未做且**刻意不做**的事：不改旧产物名（`release/`、`可运行程序/` 下的目录与 zip 保持原样）。
> 那些包已经装过、可能已经发出去，改名只会破坏"包 ↔ 当时的号"这一条追溯链。回填只写在本文里。

## 7. 什么才算正式发布

普通代码提交、测试通过、生成临时 EXE 或建立“开发构建／待验收”目录，都**不算正式发布**。
一个批次只有同时满足以下条件，才在发布记录中改为“已发布”：

1. 同时选定唯一的最终 Release 便携包与已签名 MSIX 安装包；
2. 补齐面向用户的更新说明；
3. 记录产物校验值和最终验证结果；
4. 在发布台账中把该批次状态登记为“已发布”。

完成上述登记后，后续改动才开始判断新的 Major／Minor／Patch 批次。此前即使重复构建，也仍属于
当前待验收批次，只增加全局构建号；若仅改变签名、清单或打包参数，则同时增加 MSIX Revision。

## 8. 可体验版本的交付下限

从 `1.4.1+21` 起，每个交给用户体验的版本必须同时包含：便携目录、ZIP、已签名 MSIX、签名公钥
证书和使用说明。发布台账必须记录 EXE、ZIP、MSIX 的 SHA-256，以及 MSIX 签名、覆盖安装和启动
验证结果。任一产物或验证缺失时，只能记为内部构建，不能作为可体验版本交付。
